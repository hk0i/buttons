# Product Requirements — Open-Source Stream Deck Alternative

| Doc Type | Author | Date | Status |
|---|---|---|---|
| PRD | Gregory McQuillan | 2026-09-05 | Draft |

---

## Problem Statement

Physical macro-pad hardware (Elgato Stream Deck and similar) is expensive,
proprietary, and single-purpose. Most people already own a touchscreen-capable
smartphone that is more than capable of serving as the same kind of programmable
control surface — it's idle on a desk or in a pocket most of the day anyway. There
is no widely-used, open-source way to turn that phone into a Stream-Deck-style
controller for a nearby computer without manual network configuration.

## Goals

- Let a user turn their existing smartphone into a programmable button-grid remote
  for their computer, with no dedicated hardware purchase required.
- Make setup effectively zero-configuration: discover and pair over the local
  network without the user ever typing an IP address.
- Keep the desktop component lightweight enough to run continuously in the
  background without being a resource concern.
- Ship as open source (source-available, inspectable, self-buildable) while
  sustaining the real costs of mobile distribution (Apple/Google developer fees)
  through a paid app store listing.

## Non-Goals (v1)

- Remote/off-LAN control (phone on cellular, desktop on a different network).
- A general home-automation platform — this is a computer control surface, not a
  smart-home hub, though individual buttons may trigger webhooks that reach one.
- A hardware product.
- A third-party plugin marketplace or ecosystem (the action engine should be
  designed to allow this later — see the EDD — but it is not user-facing in v1).

## Target Users

- **Streamers / content creators** who want Stream-Deck-style scene, recording, and
  media control without buying dedicated hardware.
- **Developers / power users** who want quick-action buttons for launching apps,
  running scripts, or triggering local dev workflows from their phone.
- **Open-source-first users** who want a transparent, self-hostable alternative to
  closed commercial tools, and are comfortable with a LAN-only v1.

## Use Cases

1. Start/stop streaming or recording software with one tap.
2. Trigger an OBS (or similar) scene change.
3. Launch an application or run a local script.
4. Control media playback (play/pause, volume, mute, next/previous track).
5. Trigger a custom HTTP webhook (e.g. a smart-home action, a CI job, a home
   server command).

## Functional Requirements

**Desktop**
1. Runs continuously in the background (tray/menu-bar app), not a foreground window
   the user must keep open.
2. Advertises itself on the local network so it can be discovered without a manual
   IP entry.
3. Provides a UI to create, edit, delete, and reorder buttons in a grid.
4. Each button is assigned exactly one action, chosen from a defined set of action
   types (see Use Cases above for the v1 set).
5. Persists button configuration across restarts.
6. Accepts a pairing request from a new mobile device via a one-time QR code /
   token exchange, and stores paired-device credentials for future reconnects.

**Mobile**
7. Discovers nearby desktop instances on the same network without the user typing
   an IP address.
8. Pairs with a discovered desktop instance by scanning a QR code shown by the
   desktop app.
9. Reconnects automatically to a previously-paired desktop instance on app launch,
   without re-pairing.
10. Displays a grid mirroring the desktop's current button configuration.
11. Sends a button-press event to the desktop when a button is tapped, and reflects
    the resulting success/failure state back to the user.

## Success Metrics

Since this is an open-source project rather than a funded product, "success" is
framed accordingly:

- Button-press round-trip latency on LAN is low enough to feel instantaneous
  (target: comfortably under 150ms end-to-end).
- Desktop app's idle background resource usage stays low enough that a user has no
  reason to quit it (qualitative target set once the Tauri skeleton exists — see
  the EDD).
- Pairing succeeds without the user ever needing to type an IP address or consult
  documentation, in first-run testing.
- Mobile app revenue at minimum covers the Apple Developer Program and Google Play
  registration fees on an ongoing basis.

## Open Questions

- Should v1 support multiple mobile devices paired to one desktop simultaneously,
  or is single-device sufficient to start?
- Is the button configuration desktop-authoritative only (mobile is read/press-only),
  or should mobile eventually be able to edit the grid too? Current EDD design
  assumes desktop-authoritative.
- Minimum supported OS versions for macOS/Windows/Linux and iOS/Android?
- Of the five v1 use cases above, which is the one the product must nail first for
  a usable demo — i.e. what's the actual MVP slice?
