# Product Requirements — Open-Source Stream Deck Alternative

| Doc Type | Author | Date | Status |
|---|---|---|---|
| PRD | Gregory McQuillan | 2026-09-05 | Draft |

---

## Problem Statement

Physical macro-pad hardware (Elgato Stream Deck and similar) is expensive,
proprietary, and single-purpose. Most people already own a touchscreen-capable
smartphone that is more than capable of serving as the same kind of programmable
control surface — it's idle on a desk or in a pocket most of the day anyway. There
is no widely-used, open-source way to turn that phone into a Stream-Deck-style
controller for a nearby computer without manual network configuration.

## Goals

- Let a user turn their existing smartphone into a programmable button-grid remote
  for their computer, with no dedicated hardware purchase required.
- Make setup effectively zero-configuration: discover and pair over the local
  network without the user ever typing an IP address.
- Keep the desktop component lightweight enough to run continuously in the
  background without being a resource concern.
- Ship as open source (source-available, inspectable, self-buildable) while
  sustaining the real costs of mobile distribution (Apple/Google developer fees)
  through a paid app store listing.

## Non-Goals (v1)

- Remote/off-LAN control (phone on cellular, desktop on a different network).
- A general home-automation platform — this is a computer control surface, not a
  smart-home hub, though individual buttons may trigger webhooks that reach one.
- A hardware product.
- A third-party plugin marketplace or ecosystem (the action engine should be
  designed to allow this later — see the EDD — but it is not user-facing in v1).

## Target Users

- **Streamers / content creators** who want Stream-Deck-style scene, recording, and
  media control without buying dedicated hardware.
- **Developers / power users** who want quick-action buttons for launching apps,
  running scripts, or triggering local dev workflows from their phone.
- **Open-source-first users** who want a transparent, self-hostable alternative to
  closed commercial tools, and are comfortable with a LAN-only v1.

## Use Cases

Researched against common Stream Deck usage (Elgato's own plugin marketplace,
streamer community sources — see links at the end of this doc) and the author's own
usage. Use cases are tiered by implementation cost, since each tier beyond the
first requires integrating against a separate third-party system:

**Tier 1 — MVP (no third-party integration; OS-level only)**
1. Launch an application or run a local script.
2. Simulate a keyboard shortcut / hotkey.
3. Media key control (play/pause, mute, next/previous track).

This tier is the MVP slice: it validates the entire pipeline (grid UI → discovery →
pairing → button press → action → result) end-to-end using only OS APIs, before any
third-party integration work begins.

**Tier 2 — high-value integrations (single external protocol each)**
4. OBS control: scene switching, start/stop recording, start/stop streaming, replay
   buffer trigger — via the obs-websocket v5 protocol. The author's own top use
   case; requires OBS running with its websocket server enabled.
5. Per-app volume mixer (fader-style control) — via platform audio APIs (Core Audio
   / WASAPI / PulseAudio). No external network integration, but platform-specific
   code per OS. Matches the author's Stream Deck+ dial usage.

**Tier 3 — deferred (heavier integration cost relative to value)**
6. Stream metadata updates (Twitch/YouTube title + game/category) and chat mode
   toggles (sub-only/follower-only/emote-only) — requires the platform's API plus
   an OAuth flow (app registration, token refresh). Common among streamers but the
   highest integration overhead of any use case here.
7. Discord control (mute/deafen/push-to-talk) — matters mainly for co-hosted
   streams.

**Tier 4 — long tail / generic escape hatch**
8. Trigger a custom HTTP webhook (e.g. a smart-home action, a CI job, a home
   server command) — also serves as a generic extension point for use cases not
   explicitly built in.

## Functional Requirements

**Desktop**
1. Runs continuously in the background (tray/menu-bar app), not a foreground window
   the user must keep open.
2. Advertises itself on the local network so it can be discovered without a manual
   IP entry.
3. Provides a UI to create, edit, delete, and reorder buttons in a grid.
4. Each button is assigned exactly one action, chosen from a defined set of action
   types (see Use Cases above for the v1 set).
5. Persists button configuration across restarts.
6. Accepts a pairing request from a new mobile device via a one-time QR code /
   token exchange, and stores paired-device credentials for future reconnects.

**Mobile**
7. Discovers nearby desktop instances on the same network without the user typing
   an IP address (see Network Assumptions below).
8. Pairs with a discovered desktop instance by scanning a QR code shown by the
   desktop app.
9. Reconnects automatically to a previously-paired desktop instance on app launch,
   without re-pairing.
10. Displays a grid mirroring the desktop's current button configuration.
11. Sends a button-press event to the desktop when a button is tapped, and reflects
    the resulting success/failure state back to the user.

## Network Assumptions

The primary supported topology is a **wired desktop and a Wi-Fi mobile device on
the same router/subnet** — e.g. the computer plugged into Ethernet, the phone on
the household Wi-Fi. Discovery and pairing must work by default in this topology,
not just when both devices happen to be on Wi-Fi.

This is a known risk area, not a solved problem: some routers/access points apply
client isolation, VLAN segmentation, or IGMP snooping configurations that block
multicast traffic (which mDNS relies on) from crossing between the wired and
wireless segments, even though both devices are technically "on the same network."
v1 targets typical home/small-office router setups; it does not attempt to work
around enterprise-grade network segmentation. If mDNS discovery fails outright, a
manual-IP-entry fallback path is a reasonable mitigation to keep in mind for the
EDD, rather than something v1 needs to solve at the protocol level.

## Success Metrics

Since this is an open-source project rather than a funded product, "success" is
framed accordingly:

- Button-press round-trip latency on LAN is low enough to feel instantaneous
  (target: comfortably under 150ms end-to-end).
- Desktop app's idle background resource usage stays low enough that a user has no
  reason to quit it (qualitative target set once the Tauri skeleton exists — see
  the EDD).
- Pairing succeeds without the user ever needing to type an IP address or consult
  documentation, in first-run testing.
- Mobile app revenue ideally covers the Apple Developer Program and Google Play
  registration fees on an ongoing basis.
- App core functionality stays free forever

## Decisions

- **Device pairing scope (v1):** single mobile device paired per desktop instance.
  Multi-device support is deferred.
- **Grid authority:** desktop-authoritative. Mobile is read/press-only — editing the
  grid from mobile would add setup complexity without serving the product's goal of
  controlling the desktop machine.
- **Minimum OS versions:**
  - **iOS/macOS:** Apple requires apps to be *built* with the iOS 26 / Xcode 26 SDK
    as of April 28, 2026, but this does not force a minimum deployment target — that
    stays a developer choice. Recommend targeting the last ~2 major OS versions
    (iOS/macOS 17+) for broad reach without excess legacy-support burden; revisit
    once mobile development actually starts.
  - **Android:** not expected to be a significant constraint given Android's app
    compatibility layer; pick a reasonable minimum API level once Android
    development starts rather than fixing it now.
  - **Windows:** 11 minimum (Microsoft ended Windows 10 support in October 2025).
  - **Linux:** no fixed minimum; support whatever the Tauri toolchain and Rust mDNS/
    audio crates support.
- **MVP slice:** Tier 1 use cases (generic system actions: launch app, run script,
  hotkey, media key) — see Use Cases above for the full tiering and rationale.
