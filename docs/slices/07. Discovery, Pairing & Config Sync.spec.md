## Scope

**In:**
1. **Wire envelope schema** (`protocol/wire.proto`, new) — `Envelope` +
   `PairRequest` / `PairResponse` / `ConfigSync`, per Interface section below.
   This is the first content in the buttons.proto docstring's "designed at
   roadmap step 7" note.
2. **Desktop: real prost codegen wired into `desktop/src-tauri`** — a
   `build.rs` invocation (mirrors `protocol/verify-rust/build.rs`) compiling
   `wire.proto` (which imports `buttons.proto`) into `buttons::` /
   `wire::` modules. First real (non-prototype) consumer of `/protocol`.
3. **Desktop: canonical proto3 JSON codegen** (`pbjson` + `pbjson-build`)
   alongside prost, so the generated types get `Serialize`/`Deserialize`
   matching canonical proto3 JSON's field-name mapping (camelCase) — needed
   for the JSON-over-WebSocket decision (EDD §5.2) to interoperate with
   swift-protobuf's `jsonString()` on the other end. This is a real
   asymmetric cost: Rust pays one extra build-dep for JSON that binary
   wouldn't (`prost` alone is binary-only); Swift pays nothing either way.
   Accepted per EDD §5.2 anyway — the switch to binary later is two call
   sites (`serde_json` ↔ `encode_to_vec`, `Message::Text` ↔
   `Message::Binary`), already proven end-to-end by the network-poc spike,
   so this stays cheap to revisit and isn't worth reopening over dependency
   count. Only a measured latency number reopens it (EDD §5.2's own
   trigger).
4. **Desktop: mDNS advertise** (`mdns-sd`) — `_buttons._tcp.local.`, a
   stable `device_id` (generated once, persisted) in the TXT record.
5. **Desktop: WebSocket server** (`tokio` + `tokio-tungstenite`), background
   task spawned from Tauri's `.setup()` hook. One *live* connection at a
   time (PRD/EDD §5.4: single paired mobile device in v1) — held as
   `Mutex<Option<ConnectionHandle>>`, not a boolean. A newly-authenticated
   connection evicts (closes) whatever is currently held, rather than being
   rejected — see Implementation Notes for why occupancy alone can't be the
   gate (half-open connections from a backgrounded/killed phone) and why
   eviction is still safe (only a valid-token connection can evict).
6. **Desktop: pairing flow** — one-time pairing token (in-memory, TTL'd,
   regenerated each time the QR is (re)requested), a single persisted
   pairing slot (`device.json` beside `buttons.json`: `device_id` +
   optional `{ auth_token, paired_at }`), `PairRequest` validation against
   either the live one-time token or the stored persistent token, unified
   through one code path (see Implementation Notes).
7. **Desktop: pairing UI** — a view in the existing Svelte app rendering the
   QR (SVG, generated server-side by the `qrcode` crate, returned as a
   string from a Tauri command — no client-side QR library). Reachable from
   the existing header, **behind a click, not shown by default anywhere
   else in the app.** This isn't just convenience: the QR is generated
   only while this view is deliberately open, which is what lets the
   token stay short-lived (Implementation Notes #1's 90s TTL) — an
   always-visible QR forces a choice between a token that never
   practically expires or silent background rotation (the mid-scan race
   already rejected above). On-demand generation is structural to the TTL
   working at all. The consequence, not the reason: it also bounds
   *visual* exposure — a screen recording/stream capturing it (Scope →
   Out item 9), or someone glancing over a shoulder in public — to the
   brief window it's deliberately open, rather than however long the app
   sits idle. (This doesn't address being on a hostile LAN itself; the
   token's short life and single use are what limit that, regardless of
   who can see the screen.) Two states, not just "show the QR":
   1. **Live** — the QR plus its remaining validity (even just "expires in
      ~90s" is enough — exact countdown isn't required).
   2. **Expired** — at the 90s TTL (Implementation Notes #1), the QR is
      visibly replaced/dimmed (not left looking scannable) with a
      "Generate new code" button. Clicking it issues a fresh one-time
      token exactly like opening the view fresh does — no silent
      background auto-rotation (see Implementation Notes for why: it
      would swap the token out from under a scan already in flight,
      trading a visible stale-QR problem for an invisible race). Modeled
      on LINE Desktop's QR-refresh pattern — same underlying reason
      (avoid a scan that's guaranteed to fail).
8. **Desktop: `config_sync` on connect** — after a successful pair (fresh or
   reconnect), the server reads the current `Config` via the existing
   `config::load_config` and sends it as `ConfigSync`, converted to the wire
   `buttons::Config` shape (small `From`/`to_wire()` mapping — see
   Implementation Notes; `config.rs`'s hand-written structs are not
   replaced this slice).
9. **iOS: discovery** (`NWBrowser`, adapted from the spike's
   `DesktopDiscovery.swift`) — browse `_buttons._tcp.local.`, read
   `device_id` from the TXT record.
10. **iOS: QR scan** (`DataScannerViewController`, VisionKit, iOS 16+) —
    parse the space-delimited payload (`device_id ip port pairing_token`),
    connect, send `PairRequest`.
11. **iOS: connection** (`URLSessionWebSocketTask`, adapted from the spike's
    `DesktopConnection.swift`) — send/receive `Envelope` as JSON text
    frames (not the spike's binary frames — wire format decision, EDD
    §5.2).
12. **iOS: pairing storage** — `device_id` + `auth_token` in Keychain.
13. **iOS: reconnect on launch** — Keychain has a stored pair → mDNS browse,
    match by `device_id`, connect, send `PairRequest{token: auth_token}` —
    no QR, no camera permission prompt.
14. **iOS: real data** — on a successful `ConfigSync`, decode into the
    generated `Buttons_Config` and drive the existing `ContentView` /
    `PageGrid` / `ButtonGrid` / `DeckButton` views from it directly, deleting
    `ButtonModel.swift` per its own "superseded at step 6/7" comment.
    `MockConfig.swift` is **rewritten, not deleted**: renamed
    `PreviewFixtures.swift`, same fixture data (2-level folders, every
    action kind, the nil-label edge case), rebuilt against `Buttons_Config`/
    `Buttons_Button` instead of `ButtonModel`. One shared fixture backs all
    four `#Preview` blocks instead of each hand-rolling `Buttons_Button`'s
    oneof-init boilerplate, and it's reusable later for `XCTest` view-logic
    tests that don't need a real connection.
15. **`protocol/wire.proto` comments as the canonical wire-protocol
    reference** — `protocol/README.md` already promises this directory is
    home to "the message catalog, field shapes, and pairing sequence";
    satisfied by the `.proto` file's own doc-comments plus one short
    `protocol/PAIRING.md` for the sequence diagram (a concrete version of
    EDD §5.1's, with real field names) — not a second schema doc to drift.
16. **EDD updates** — `buttons.proto`'s header comment and
    `protocol/README.md`'s "aren't in `buttons.proto` yet" line both
    updated to point at `wire.proto` now that it exists.

**Out:**
1. **`nav_request` / `nav_cursor` (live navigation-cursor mirroring).**
   Confirmed out of this slice (2026-09-11) — designed and built once live
   nav mirroring is actually being added, not bundled into the initial
   handshake just because EDD's Open Questions ties its *design* to "step 7
   on." This slice's `ConfigSync` carries no navigation position.
2. **`button_press` / `action_result` / `state_push` / `profile_switch`.**
   Roadmap steps 8-10. The `Envelope` oneof adding a case later for these is
   non-breaking — no need to stub them now.
3. **Multiple simultaneous mobile connections / a device roster.** PRD v1 is
   one desktop, one paired phone. The single-slot `device.json` and
   one-active-connection server behavior both hard-code this; don't
   generalize early.
4. **Token rotation.** Once a persistent `auth_token` is issued it's reused
   indefinitely across reconnects in v1 — no expiry, no refresh. Revisit
   only if a real security need shows up.
5. **Binary wire encoding.** JSON-over-WebSocket per EDD §5.2, unconditionally,
   this slice. The switch is deferred until a measured latency number
   justifies it — not guessed at here.
6. **Android.** Roadmap step 12. `wire.proto` must still compile under
   `protocol/verify-kotlin`'s existing `wire` codegen (it's on the schema
   lock's "all three languages" hook), but no Android app code is touched.
7. **Manual IP entry / QR redisplay-for-reconnect fallback.** Roadmap step
   11. This slice's reconnect path is mDNS-only; if it fails, the only
   recovery is re-scanning a freshly-generated QR (the normal first-pair
   flow), not a dedicated fallback UI.
8. **WebSocket ping/pong keepalive.** Bounds how long a half-open ghost
   connection (backgrounded/killed phone, no FIN/RST) lingers before the
   server notices and frees it — a resource/hygiene concern, worth adding
   once the server exists. Explicitly **not** what prevents the reconnect
   lockout described in Implementation Notes #9 — pings take ~30-60s to
   detect death, and newest-authenticated-wins eviction is what makes the
   legitimate device's reconnect succeed immediately regardless of
   whether the ghost has been noticed yet. Don't let a later pass "fix"
   #9's bug by adding pings and stop there.
9. **Desktop-side "approve this connection" dialog.** Deliberately deferred
   (2026-09-11), not overlooked — recording the reasoning here since the
   UI isn't built. Threat considered: this app's own users routinely
   screen-capture/stream (OBS), so the pairing QR can end up visible to a
   viewer, not just the operator. A confirm dialog wouldn't *prevent* that
   attacker from pairing (an absent or inattentive streamer just doesn't
   see it, or reflexively approves) — its actual value would be making a
   successful attack **visible** after the fact, a detection property, not
   a prevention one. The real mitigation already in this slice is the
   one-time token's 90s TTL (Implementation Notes #1): usable only in a
   short window after the QR renders, on the LAN, which is what actually
   bounds the exposure. A numeric Bluetooth-style verification code was
   considered and rejected — displayed on the same screen that leaked the
   QR, it leaks identically, so it adds no real property. Revisit the
   confirm dialog if it's ever wanted purely for its detection value; EDD
   §7's security paragraph should eventually absorb this threat model
   properly (it doesn't mention screen capture today) — that's an EDD gap,
   not fixed here.
10. **Rewriting `desktop/src-tauri/src/config.rs`'s hand-written structs to
    the generated `buttons::` types.** They coexist on purpose this slice —
    see Scope → In item 8 and Implementation Notes. A full repoint, if it
    ever happens, is its own slice.
11. **Observability beyond local `println!`/`eprintln!`-style logging** on
    both ends. EDD §7's "minimum bar is local logging" is satisfied by
    console output for now; a real log file/rotation is explicitly TBD there.
12. Light-mode styling — still deferred project-wide.

## Interface / Data Contract

```mermaid
sequenceDiagram
  participant D as Desktop
  participant M as Mobile
  Note over D: mDNS advertise: _buttons._tcp.local, TXT{device_id}
  D->>D: generate one-time pairing_token (TTL), render QR
  M->>M: NWBrowser discovers D (fresh pair: unknown device_id)
  M->>M: scan QR: "device_id ip port pairing_token"
  M->>D: Envelope{ PairRequest{ token: pairing_token } }
  D->>D: validate: matches live one-time token?
  D->>M: Envelope{ PairResponse{ ok: true, auth_token } }
  D->>M: Envelope{ ConfigSync{ config } }
  M->>M: store device_id + auth_token in Keychain
  Note over D,M: --- later launch ---
  M->>M: NWBrowser discovers D by stored device_id
  M->>D: Envelope{ PairRequest{ token: stored auth_token } }
  D->>D: validate: matches persisted auth_token?
  D->>M: Envelope{ PairResponse{ ok: true, auth_token } }
  D->>M: Envelope{ ConfigSync{ config } }
```

`protocol/wire.proto`:
```proto
syntax = "proto3";
package buttons;
import "buttons.proto";

message Envelope {
  string protocol_version = 1; // "1" for this slice; bumped on breaking change
  oneof message {
    PairRequest pair_request = 2;
    PairResponse pair_response = 3;
    ConfigSync config_sync = 4;
  }
}

message PairRequest {
  string token = 1; // the QR's one-time token, OR a stored persistent auth_token
}

message PairResponse {
  bool ok = 1;
  optional string auth_token = 2; // present iff ok — same value on every
                                   // successful reconnect, no rotation (v1)
  optional string error = 3;      // present iff !ok
}

message ConfigSync {
  Config config = 1; // buttons.Config from buttons.proto — the whole thing,
                      // every Profile, per EDD §5.2's decision
}
```

QR payload (not protobuf — a bootstrap string, parsed before any connection
exists): `"<device_id> <lan_ip> <port> <pairing_token>"`, space-delimited,
extending the spike's 3-field format by one. **Four space-delimited fields,
not `ip:port` colon-joined** — considered and rejected: `mdns-sd` can hand
back a link-local IPv6 address with a zone index (`fe80::1%en0`), which
would force bracket-aware parsing (`[ip]:port`) on the Swift side for a
purely cosmetic gain; `split(separator: " ")` into a 4-element array,
validated by count, also fails more predictably than a 3-element array
where one element needs its own second parse. Don't "clean this up" later
without re-reading this note.

## Implementation Notes

1. **One validator, two acceptable tokens.** `pairing.rs` exposes a single
   `validate(token: &str) -> Option<AuthResult>` checked against (a) the
   live in-memory one-time token if not expired, or (b) `device.json`'s
   stored `auth_token` if present. Same code path for first-pair and
   reconnect — the server doesn't need to know which case it's in.
   **One-time token TTL: 90 seconds** from the moment the QR is
   (re)rendered, not from server start — a number, not just "TTL'd,"
   since an unenforced-in-practice TTL is exactly the class of
   declared-but-unverified property `protocol_version` (item 2) was fixed
   for. This is the real mitigation for the QR-visible-on-a-livestream
   scenario in Scope → Out (item 9): the token is only usable for a short
   window after being displayed, so a captured stream frame is only a
   live threat while that window is still open and the attacker is also
   on the LAN. See Out item 9 for what this doesn't cover.
2. **`protocol_version` is checked, not just carried.** Before the token
   validator runs, the server compares the incoming `Envelope`'s
   `protocol_version` against its own compiled-in constant (`"1"` this
   slice). A mismatch is rejected through the same path as the
   single-connection guard below —
   `Envelope{PairResponse{ok:false, error:"protocol version mismatch"}}`,
   then close — so it's not a field that's declared and silently ignored.
   EDD §5.2's "desktop and mobile releases will inevitably drift" is the
   reason it exists; this slice is the only version that will ever exist,
   so the check can't be *exercised* end-to-end yet, but it must be *wired*
   now rather than added later once there's a real second version to test
   against.
3. **`device.json` shape:** `{ "device_id": "...", "paired": { "auth_token":
   "...", "paired_at": "..." } | null }`. `device_id` is generated once (on
   first launch that finds no file) and never changes — mobile's reconnect
   matching depends on that stability.
4. **`device.json` lives beside `buttons.json`**, same directory, same
   `serde_json` pattern — per EDD §5.3's "genuine device-local settings get
   a JSON file beside `buttons.json`" rule (04b's precedent), not
   `localStorage` (that's the webview's, and this is Rust-side state the
   frontend never needs directly).
5. **QR is SVG, server-rendered, no client QR library.** `qrcode`'s
   `render::<svg::Color>()` returns a `String` of SVG markup; the Tauri
   command hands it straight to the frontend, which inlines it — sidesteps
   picking a client-side QR-rendering package entirely.
6. **`buttons::Config` (wire) vs. `config::Config` (local persistence) stay
   two distinct types this slice.** The conversion lives in one place
   (`proto.rs`), one direction (local → wire, for `ConfigSync`). No reverse
   mapping needed yet — nothing on the wire writes back into local config
   this slice (that's `button_press`/`profile_switch`, steps 8-10).
7. **pbjson, not hand-rolled JSON.** Canonical proto3 JSON field-casing
   (camelCase) has real rules (well-known-type special cases, `oneof`
   representation) that swift-protobuf's `jsonString()` already implements
   correctly; `pbjson-build` generates matching Rust `Serialize`/
   `Deserialize` from the same `.proto` so the two sides agree on parsing
   each other's output without either one hand-coding the mapping.
8. **What JSON actually buys here, restated accurately.** EDD §5.2's
   debuggability case for JSON ("plain browser devtools / a WebSocket
   inspector") assumes a browser in the path — there isn't one; this
   connection is `tokio-tungstenite` ↔ `URLSessionWebSocketTask` directly.
   The real, still-genuine win: `websocat` (already documented in the
   spike's README) can inspect/inject frames as plain readable text, and
   server-side log lines can print the payload directly with no decoder —
   both are lost the day this switches to binary. Restating this so a
   later reader doesn't conclude the original rationale was simply wrong.
9. **Single-connection slot is `Mutex<Option<ConnectionHandle>>` in
   `server.rs`, newest-authenticated-connection-wins — not a reject-second
   boolean.** A boolean guard has a real lockout bug: a phone that goes out
   of Wi-Fi range, gets force-quit, or is merely backgrounded (iOS
   suspends the socket routinely, not just on crash) leaves no FIN/RST —
   the desktop's connection looks alive for a long time (default TCP
   keepalive doesn't probe for ~2 hours), so the flag stays set and the
   *legitimate* device's own reconnect gets rejected as "already
   connected." Only fix would be restarting the desktop app — worst-case UX
   for the one paired device.

   Fix: don't reject the second connection — authenticate it first (same
   `PairRequest` validator, item 1/2 above), and only on success evict
   (close) whatever the slot currently holds, then store the new handle.
   This is safe *because* nothing reaches `ConfigSync` without a valid
   token — an unauthenticated connection can never evict, and a
   valid-token connection is by definition the paired device (or holds its
   secret, at which point the occupancy guard was never the real security
   boundary anyway). Evict **after** the new connection authenticates, not
   on raw TCP accept, or a stranger's bare connection attempt could knock
   the real phone off before ever proving it belongs there.

   `Mutex<Option<ConnectionHandle>>` also generalizes directly to the
   `Map<deviceId, _>` the EDD's multi-device note (Open Questions §3.5)
   already anticipates — no data-structure rewrite when that lands. The
   rejection path (`PairResponse{ok:false, error:...}`) still exists, just
   repointed at actual auth failure (bad/expired token, version mismatch —
   item 2 above) instead of occupancy.
10. **iOS QR scanning needs `NSCameraUsageDescription`** in `Info.plist` —
    easy to forget, silently crashes on scan attempt without it.
11. **`DataScannerViewController` requires a real device or a Simulator with
    a virtual camera feed** — plain Simulator QR scanning from a laptop
    webcam doesn't work out of the box; the DoD walk below needs a real
    iPhone against the built desktop app on the same LAN.
12. **Point every generated-type reference at `Buttons_` directly.** Per EDD
    §5.2's swift_prefix decision (slice 06): no repo-wide typealias. A
    single file with several long names can add its own local `typealias
    Config = Buttons_Config` at the top — decide file-by-file during
    implementation, not here.

## Definition of Done

1. [ ] Desktop launches → advertises mDNS → pairing view shows a QR (SVG),
       distinct payload each time it's (re)opened.
2. [ ] Fresh iOS install (no Keychain entry) → "Scan to Pair" screen; scan
       desktop's QR → connects, receives `ConfigSync`, renders the **real**
       `buttons.json` content (not `MockConfig`) in the existing
       page/folder navigation.
3. [ ] A Page with no `name` and a Button with no `label`/`icon` (the
       `.back` cell, or any authored button left blank) survive the
       `ConfigSync` round trip and render their fallback (icon-only cell /
       ⬅ "Back") — not an empty string. This is the case canonical JSON's
       "omit absent optionals" behavior can silently break if the Rust or
       Swift side ever diverges from it; `PreviewFixtures.swift`'s nil-label
       button and nil-name page don't cover it once they're preview-only,
       so this has to be checked against the real wire.
4. [ ] Edit a button's label in the desktop editor, force-quit + relaunch
       the iOS app (or trigger a reconnect) → sees the updated label — no
       stale cache.
5. [ ] Force-quit + relaunch iOS app after a successful pair → reconnects
       via mDNS + stored token automatically, **no QR scan, no camera
       permission prompt**.
6. [ ] Stale/reused one-time token (generate a new QR on desktop, then scan
       a screenshot of the *old* one) → iOS shows a pairing-failed state, no
       config received.
7. [ ] One-time token actually expires on its own timer, not just on
       regeneration. The desktop UI hides/replaces the QR at expiry (item
       7's pairing-UI states), so this can't be walked as "leave the
       stale QR on screen and scan it" — instead: screenshot the live QR

## Rollback

Higher risk than prior slices — first slice touching two runtimes' network
stacks at once. If pairing or sync misbehaves close to done:
1. Desktop and iOS are independently revertable — the desktop server can
   ship (advertising + accepting + QR) even if iOS-side pairing isn't
   working yet, since nothing else depends on the connection existing.
2. `wire.proto` additions are new files/messages, not edits to
   `buttons.proto`'s existing messages — reverting is deleting `wire.proto`
   and the generated-code wiring, no schema migration.
3. Deleting `ButtonModel.swift` (and repointing views off it) is the one
   destructive step with no easy partial-revert — do it last, only once
   `ConfigSync` is confirmed rendering real data through the existing views.
   `MockConfig.swift`'s rename to `PreviewFixtures.swift` carries no such
   risk — it's not depended on by the real data path either way.
