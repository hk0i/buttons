without real demand. Closed 2026-09-20.

## Already shipped, satisfies this step

1. **On-demand QR redisplay.** `desktop/src/routes/pairing/+page.svelte`
   is reachable any time via the "Pair device…" link
   (`desktop/src/routes/+page.svelte:54`), not gated to first-run. Each
   visit calls the `get_pairing_qr` Tauri command
   (`desktop/src-tauri/src/lib.rs:206-221`), which issues a fresh one-time
   token and re-renders the QR. PRD § Desktop item 10 is satisfied today.
2. **Rescan-to-reconnect.** `PairingView.failedView`
   (`ios/Buttons/Views/PairingView.swift:189-204`) offers "Scan QR Again"
   on any pairing/reconnect failure, routing back through the same
   `checkCameraAndAdvance()` → scan → `session.pair(scannedQR:)` path used
   for a fresh pair. `Pairing::validate`
   (`desktop/src-tauri/src/pairing.rs:104-123`) already accepts either the
   live one-time token (fresh pair) or the persisted `auth_token`
   (reconnect) through the same code path — rescanning a freshly-generated
   QR already recovers a reconnect. PRD § Mobile item 7's primary recovery
   path is satisfied today.

## Why the cameraless fallback is closed, not built

PRD § Network Assumptions names manual IP entry as a secondary fallback
"only for mobile devices without a usable camera" — a narrow edge case
with no observed demand yet. Building it securely turned out to cost
more than that edge case currently justifies:

1. Raw manual IP entry (type the desktop's IP/port and some credential
   directly, no discovery) was the original framing, but doesn't actually
   need solving on its own — see § Deferred design for what it would
   have required and why that was rejected in favor of a lighter design.
2. Even the lighter design (§ Deferred design) still needs new backend
   surface — an additive `PairResponse.device_id` field, a PIN-as-
   alternate-token-representation mechanism, and a wrong-guess lockout —
   for a fallback of a fallback (no camera, and unable/unwilling to fix
   that, which is itself already rare).
3. Decision: don't build it now. Camera-based QR pairing needs no
   fallback until real usage shows otherwise. Cheap to revisit — nothing
   below gets harder to build later than it would be now.

## Deferred design (not built): mDNS discovery + PIN

If a cameraless fallback is ever revisited, this is the shape to reuse
rather than re-deriving from scratch — and specifically **not** raw
manual IP entry:

1. Rely on mDNS discovery exactly as auto-reconnect already does
   (`PairingSession.attemptAutoReconnect`,
   `ios/Buttons/Networking/Pairing.swift:181-200`) to find the desktop's
   IP/port. A cameraless device on the same LAN doesn't need to *type*
   an address it can discover — manual IP entry only ever mattered for
   the doubly-rare case of mDNS *also* being broken, which isn't worth
   solving here (item 3 below).
2. Replace the camera scan with a **typed PIN** — not a pasted
   `device_id`/`auth_token` blob, not a user-set standing password.
   Rejected alternatives and why:
   - Pasting the full QR payload string: displaying a real
     `auth_token`/`device_id` on screen for anyone to read, and making a
     human type a long opaque token, is bad UX and needlessly exposes a
     credential that would otherwise never appear as on-screen text.
   - A user-set standing password (checked as a third branch in
     `Pairing::validate`): unlike the QR's one-time token, a password is
     a long-lived secret needing brute-force defenses, *and* — separate
     from transport encryption (EDD Open Question 9) — carries a risk a
     random token doesn't: humans reuse passwords across services, so a
     sniffed pairing password can compromise more than this app.
   - A short-lived numeric PIN isn't a new secret at all: it's an
     alternate, human-typable *representation* of the same ephemeral
     one-time token the QR already encodes, shown as digits instead of a
     QR image. Inherits the QR flow's already-accepted threat model
     (ephemeral, single-use, ~90s window, LAN-only) instead of creating a
     new one. Needs one new defense the QR path doesn't: a wrong-guess
     lockout, since 6 digits is brute-forceable within 90s if left
     unthrottled.
3. **Explicitly still out, even if this gets built:** raw manual IP entry
   for the case where mDNS is *also* broken (not just camera-unavailable)
   — that's two simultaneous failures, and PRD's manual-IP framing was
   never meant to cover it alone without discovery working. If that
   double-failure case ever becomes real, it needs its own design pass,
   not an assumption this one covers it.
4. **Known follow-on cost, not decided here:** mobile needs the desktop's
   `device_id` for Keychain storage, and mDNS TXT is the only current
   source — fine, since this design keeps mDNS in the loop (unlike raw
   manual IP entry, which would have needed an additive
   `PairResponse.device_id` field instead). Re-verify this is still true
   before building, in case `Pairing.swift`/`server.rs` have changed by
   then.
5. QR payload reshaped into a URL scheme / universal link so stock Camera
   can deep-link into the app — [[project_qr_url_handler_idea]] — is a
   separate, independent idea from this one. Not addressed by this design
   either way.
