## Already shipped, not this slice's work

1. **On-demand QR redisplay.** `desktop/src/routes/pairing/+page.svelte`
   is reachable any time via the "Pair device…" link
   (`desktop/src/routes/+page.svelte:54`), not gated to first-run. Each
   visit calls the `get_pairing_qr` Tauri command
   (`desktop/src-tauri/src/lib.rs:206-221`), which issues a fresh one-time
   token and re-renders the QR. PRD § Desktop item 10 is satisfied today.
2. **Rescan-to-reconnect.** `PairingView.failedView`
   (`ios/Buttons/Views/PairingView.swift:189-204`) offers "Scan QR Again"
   on any pairing/reconnect failure, routing back through the same
   `checkCameraAndAdvance()` → scan → `session.pair(scannedQR:)` path used
   for a fresh pair. `Pairing::validate`
   (`desktop/src-tauri/src/pairing.rs:104-123`) already accepts either the
   live one-time token (fresh pair) or the persisted `auth_token`
   (reconnect) through the same code path — rescanning a freshly-generated
   QR already recovers a reconnect. PRD § Mobile item 7's primary recovery
   path is satisfied today.

## Scope

**In:**
1. Desktop: render the `payload` string already returned by
   `get_pairing_qr` (`desktop/src-tauri/src/lib.rs:206-221`,
   `desktop/src/routes/pairing/+page.svelte`) as selectable/copyable text
   alongside the QR — today only the `svg` field is displayed, `payload`
   is discarded. Same lifecycle as the QR: expires with the same 90s
   token, replaced by "Generate new code" on expiry, no separate timer.
2. iOS: a manual-entry UI in `PairingView.swift` — a single paste field
   accepting the same space-delimited `"<device_id> <lan_ip> <port>
   <token>"` string the QR already encodes (`PairingPayload`,
   `ios/Buttons/Networking/Pairing.swift:11-25`), parsed with the same
   struct and handed to the existing `session.pair(scannedQR:)`
   (`Pairing.swift:131-146`) unchanged. No new pairing/reconnect logic —
   this is an alternate way to produce the same `PairingPayload` a camera
   scan produces.
3. iOS: two entry points into that manual-entry UI —
   1. From `.landing` (`PairingView.swift:87-97`), alongside "Scan QR
      Code," for a device that never had camera access to begin with.
   2. From `.cameraDenied` (referenced in `PairingState`,
      `PairingView.swift:23-30`), alongside "Open Settings," for the
      PRD's explicit "devices without a usable camera" case (§ Network
      Assumptions).

**Out:**
1. Any new wire/protobuf message. Manual entry produces the same
   `PairingPayload` a QR scan produces; `PairRequest` is unchanged.
2. QR payload reshaped into a URL scheme / universal link so stock Camera
   can deep-link into the app — floated in
   [[project_qr_url_handler_idea]], deferred again. Revisit only if manual
   entry proves too error-prone in practice.
3. `auth_token` rotation on reconnect — unchanged v1 behavior
   (`pairing.rs:98-103`).
4. A distinct "reconnect failed" vs. generic "pairing failed" UI state.
   `failedView` stays generic; PRD doesn't require the copy to
   distinguish the two, only that a recovery path exists.
5. USB tethering fallback — explicitly deferred past v1 (PRD §
   Non-Goals).
6. Any change to the desktop pairing page's 90s token expiry/regenerate
   behavior (`+page.svelte:10, 17-31`) — the new payload text rides the
   existing timer, not a second one.
7. Validating manual-entry input beyond what parsing already rejects
   (`PairingPayload`'s field-count check) — a malformed paste fails the
   same way a malformed/foreign QR already fails today, through the
   existing `.failed` state. No new inline field validation UI.

> **Rule for agent:** stay inside this scope. If something out of scope
> blocks you, stop and flag it — don't silently expand scope to route
> around it.

## Definition of Done

1. [ ] Desktop `/pairing` page shows the raw payload string as
       selectable/copyable text alongside the QR, expiring together with
       it.
2. [ ] iOS `.landing` offers "Enter code manually" next to "Scan QR
       Code."
3. [ ] iOS `.cameraDenied` offers the same manual-entry path next to
       "Open Settings."
4. [ ] Pasting a valid, freshly-generated payload string into manual
       entry pairs a new device successfully.
5. [ ] Pasting a valid payload string for an already-paired device
       (desktop's `device.json` already holds its `auth_token`)
       reconnects successfully — same `Pairing::validate` path a rescan
       already exercises.
6. [ ] Pasting a malformed string surfaces the existing `.failed` state,
       not a crash.
7. [ ] Existing "Scan QR Again" rescan-to-reconnect flow still works
       unmodified (regression check only — no code change expected here).
