**TL;DR:** on-demand QR redisplay and rescan-to-reconnect are already

one piece PRD § Mobile item 7 still requires: a manual-entry fallback for
mobile devices without a usable camera. Settled 2026-09-20, after
discussion: manual entry is **IP + port + a short-lived numeric PIN**, not
a pasted `device_id`/`auth_token` blob — see § Design decision below for
why.

## Design decision: PIN, not pasted token

Three options were weighed for what a cameraless user actually types:

1. Paste the full QR payload string (`device_id lan_ip port token`) —
   rejected: displaying a real `auth_token`/`device_id` on screen for
   anyone to read, and making a human type a long opaque token, is both
   bad UX and needlessly exposes a credential that would otherwise never
   appear as on-screen text.
2. A user-set standing password, checked as a third branch in
   `Pairing::validate` — rejected: unlike the QR's one-time token, a
   password is a long-lived secret, so it needs brute-force defenses
   (rate limit/lockout) *and* — independent of transport encryption
   (EDD Open Question 9) — carries a real risk a random token doesn't:
   humans reuse passwords across services, so a sniffed pairing password
   can compromise more than this app.
3. **A short-lived numeric PIN — chosen.** Not a new secret at all: it's
   an alternate, human-typable *representation* of the same ephemeral
   one-time token the QR already encodes, shown as digits instead of a QR
   image, alongside IP + port (which mobile still needs to know where to
   connect, since manual entry is precisely for when mDNS can't tell it).
   Inherits the QR flow's already-accepted threat model (ephemeral,
   single-use, ~90s window, LAN-only) instead of creating a new one.
   Needs one new defense the QR path doesn't: a wrong-guess lockout,
   since 6 digits is brute-forceable within 90s if left unthrottled —
   the QR's un-guessability came from length/randomness, the PIN's comes
   from a bounded number of tries instead.

One consequence: today's typed payload string carries `device_id`; a
3-field IP/port/PIN entry doesn't. Mobile needs the desktop's
`device_id` to store in Keychain after a successful pair, and mDNS TXT
(the fallback source) is unavailable precisely when manual entry is
needed. So this slice adds one additive field to `PairResponse`
(`protocol/wire.proto`) — `device_id`, present iff `ok` — rather than
relying on the QR-only path to supply it. No new message type.

## Already shipped, not this slice's work

1. **On-demand QR redisplay.** `desktop/src/routes/pairing/+page.svelte`
   is reachable any time via the "Pair device…" link
   (`desktop/src/routes/+page.svelte:54`), not gated to first-run. Each
   visit calls the `get_pairing_qr` Tauri command
   (`desktop/src-tauri/src/lib.rs:206-221`), which issues a fresh one-time
   token and re-renders the QR. PRD § Desktop item 10 is satisfied today.
2. **Rescan-to-reconnect.** `PairingView.failedView`
   (`ios/Buttons/Views/PairingView.swift:189-204`) offers "Scan QR Again"
   on any pairing/reconnect failure, routing back through the same
   `checkCameraAndAdvance()` → scan → `session.pair(scannedQR:)` path used
   for a fresh pair. `Pairing::validate`
   (`desktop/src-tauri/src/pairing.rs:104-123`) already accepts either the
   live one-time token (fresh pair) or the persisted `auth_token`
   (reconnect) through the same code path — rescanning a freshly-generated
   QR already recovers a reconnect. PRD § Mobile item 7's primary recovery
   path is satisfied today.

## Scope

**In:**
1. `protocol/wire.proto`: add `optional string device_id = 4;` to
   `PairResponse`, present iff `ok` — see § Design decision. Additive
   field, no new message, safe post-schema-lock.
2. Desktop: alongside the existing QR, display IP, port, and a short
   numeric PIN — an alternate representation of the same one-time secret
   `get_pairing_qr` already mints (`desktop/src-tauri/src/lib.rs:206-221`,
   `pairing.rs:81-88`), not a second secret. Same 90s lifecycle as the QR
   — expires and regenerates together, one timer.
3. Desktop: a wrong-PIN attempt lockout in `Pairing::validate`
   (`pairing.rs:104-123`) — bound the number of guesses accepted per
   issued token before it's invalidated early. Exact threshold is an
   implementation detail, not decided here; note the chosen value in this
   file's Implementation Notes once picked.
4. Desktop: populate `PairResponse.device_id` on every successful
   pair/reconnect (`server.rs`'s response construction).
5. iOS: a manual-entry UI in `PairingView.swift` — three fields (host,
   port, PIN), constructing a `PairRequest{token: pin}` sent to the typed
   host/port directly (bypassing mDNS resolution entirely — manual entry
   exists for when mDNS can't help). On success, store `device_id` from
   `PairResponse` (new field) into Keychain via the existing
   `PairingStore` (`Pairing.swift:39-97`) — same storage, new source for
   `device_id` instead of parsing it from a scanned/pasted string.
6. iOS: two entry points into that manual-entry UI —
   1. From `.landing` (`PairingView.swift:87-97`), alongside "Scan QR
      Code," for a device that never had camera access to begin with.
   2. From `.cameraDenied` (referenced in `PairingState`,
      `PairingView.swift:23-30`), alongside "Open Settings," for the
      PRD's explicit "devices without a usable camera" case (§ Network
      Assumptions).

**Out:**
1. Any new message type on the wire — one additive field on the existing
   `PairResponse` covers it (§ In item 1).
2. QR payload reshaped into a URL scheme / universal link so stock Camera
   can deep-link into the app — floated in
   [[project_qr_url_handler_idea]], deferred again. Independent of the
   PIN decision; revisit only if manual entry proves too error-prone in
   practice.
3. `auth_token` rotation on reconnect — unchanged v1 behavior
   (`pairing.rs:98-103`).
4. Transport encryption / replacing `auth_token` with a device-identity
   keypair — see EDD Open Question 9. The PIN inherits the QR's
   already-accepted cleartext threat model; this slice doesn't change
   that model in either direction.
5. A user-settable standing password — considered and rejected, § Design
   decision option 2.
6. A distinct "reconnect failed" vs. generic "pairing failed" UI state.
   `failedView` stays generic; PRD doesn't require the copy to
   distinguish the two, only that a recovery path exists.
7. USB tethering fallback — explicitly deferred past v1 (PRD §
   Non-Goals).
8. Any change to the desktop pairing page's 90s token expiry/regenerate
   behavior beyond adding the PIN/IP/port display to it
   (`+page.svelte:10, 17-31`) — one timer, not a second one.
9. Inline field validation beyond what parsing already rejects — a wrong
   PIN or unreachable host fails the same way a malformed/foreign QR
   already fails today, through the existing `.failed` state. No new
   validation UI.

> **Rule for agent:** stay inside this scope. If something out of scope
> blocks you, stop and flag it — don't silently expand scope to route
> around it.

## Definition of Done

1. [ ] Desktop `/pairing` page shows IP, port, and a PIN alongside the
       QR, all expiring together on the same 90s timer.
2. [ ] iOS `.landing` offers "Enter code manually" next to "Scan QR
       Code."
3. [ ] iOS `.cameraDenied` offers the same manual-entry path next to
       "Open Settings."
4. [ ] Entering a valid, freshly-generated IP/port/PIN into manual entry
       pairs a new device successfully, and Keychain ends up with the
       correct `device_id` (from `PairResponse`, not typed).
5. [ ] Entering a valid IP/port/PIN for an already-paired device
       reconnects successfully — same `Pairing::validate` path a rescan
       already exercises.
6. [ ] A wrong PIN is rejected; N wrong guesses invalidate that token
       early (exact N recorded in Implementation Notes once picked).
7. [ ] An unreachable host/port surfaces the existing `.failed` state,
       not a crash or hang.
8. [ ] Existing "Scan QR Again" rescan-to-reconnect flow still works
       unmodified (regression check only — no code change expected here).
