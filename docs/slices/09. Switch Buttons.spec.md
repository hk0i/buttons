**Implements:** `01. Architecture Overview.edd.md`, Testing & Rollout Plan
step 9; Open Questions → "Stateful buttons — Switch button type +
`state_push` design."
**TL;DR:** A new two-state `Switch` button type, researched against
Elgato's own "Multi Action Switch" (see Sources). Each state owns its own
icon/label/action array; a press runs the current state's actions and
flips to the other one. Desktop is authoritative on which actions run;
mobile flips its display the instant it's tapped (matching Elgato's own
hardware behavior) and rolls back if the press failed. No wire envelope
change — the flip rides the existing `config_sync`. Sets up slice 09a
(`state_push`) for the case this slice doesn't cover: a state changing
without the observing device's own press to explain it.

## Scope

**In:**

1. `buttons.proto`: `ButtonContent` gains a `switch_content` case
   (`SwitchContent`, sibling to `actions`/`folder`/`back`) — two
   `SwitchState { label, icon, actions }`, named `off`/`on`. `Button`
   gains `bool is_active = 7` — the *current* state, wire-only (see Scope
   → In #3).
2. Desktop: `config::ButtonContent::Switch` mirrors the proto shape 1:1,
   persists in `buttons.json` like any other button content — this half
   is ordinary authored config, no different from `.actions`.
3. Desktop: a **local-only** `switch_state.json` (button_id → current
   `bool`), sibling to the existing `device.json`, loaded at launch,
   never touched by `save_config`/`get_config`, never exported. This is
   the *only* place "which state is this Switch showing right now" lives
   durably.
4. Desktop: one shared function decides what a press does — real
   `ButtonPress` (`server.rs`) and the editor's `Test` button (`lib.rs`)
   both call it, so there is exactly one definition of "what pressing
   this button does," not two that can drift apart.
5. Desktop: `config_sync` merges `switch_state.json`'s current values
   into the freshly-built proto `Config` at send time — a reconnecting
   mobile client sees the real current state immediately, not a
   hardcoded default.
6. Desktop: `ButtonEditor` gains a real content-type choice (Actions /
   Folder / Switch — see Implementation Notes) and a tabbed "State A" /
   "State B" editor for a Switch's two states, each reusing the existing
   icon/label/action-list sub-forms unchanged.
7. Desktop: `Test`, for a Switch button, simulates a full real press —
   runs the current state's actions and flips on success, using the same
   shared function as Scope → In #4.
8. Desktop: its own preview grid (`DeckButton.svelte`, `PreviewPane`)
   shows a Switch button's *current* state's icon/label live, via a new
   query command + Tauri event — verifiable with no paired phone.
9. Mobile: tapping a `.switch` button sends `ButtonPress` (same as
   `.actions` today) and **flips its own display immediately**, before
   any reply — it already has both states' icon/label from `config_sync`
   (Scope → In #1/#2), so nothing about the flip needs the network. Fires
   haptic immediately, same as slice 08's `.actions` case.
10. Mobile: on `ActionResult{ok:false}`, flips back — a two-state toggle
    means "undo the optimistic guess" and "flip again" are the same
    operation, no remembered prior value needed.
11. Mobile: the existing press-flash checkmark/x-mark overlay (slice 08)
    still fires for a Switch button, unchanged — it's an orthogonal
    channel (corner icon overlay vs. the button's own icon/label swap).

**Out:**

1. **`state_push` and the broadcast/runtime-map machinery it needs** —
   slice 09a. This slice has no case where a Switch's state changes
   without the pressing device already knowing the answer (desktop's own
   `Test` click is exactly that case, and is 09a's real, available-today
   driver — see EDD Open Question 8, Note 6).
2. Any real Tier 1/2/3 integration reporting external drift (OS mute
   state, OBS scene, …) — no Tier 1 use case produces real external
   state; a mute-toggle Switch is Tier 1-realizable on its own (two
   hotkey arrays), no reporter needed. A real reporter is step 13's work.
3. More than two states (`MultiSwitch`) — capped at two, matching
   Elgato's own limit exactly (their SDK docs call more than two "not
   fully supported"). Add a sibling variant later if a real need shows
   up; don't reshape `SwitchContent`.
4. A generic background-tint "active" indicator (the channel slice 08
   Out #7 reserved) — **not needed by this slice.** A Switch's two states
   already carry distinct authored icon/label; there's no separate
   generic flag left to render. Still available later if 09a or a Tier 2
   integration ever wants an indicator orthogonal to a button's own
   authored appearance.
5. `profile_switch` — step 10, unrelated message.
6. Live nav-cursor mirroring — unrelated wire channel, step 7's own
   deferred design (EDD §5.2 Open Question 3).
7. The edit-churn `config_sync` debounce/dirty-check (EDD §5.2 Corollary
   #2) — unrelated; this slice's `config_sync` change is a merge-at-
   send-time read, not a new push trigger.
8. A real design-token/color palette — unaffected either way (Out #4).

> **Rule for agent:** stay inside this scope. If something out of scope
> blocks you, stop and flag it — don't silently expand scope to route around
> it.

## Interface / Data Contract

`protocol/buttons.proto` — new content case, next free tags:

```protobuf
message Button {
  string id = 1;
  optional string label = 2;
  optional string icon = 3;
  // 1. new — current state, wire-only; see switch_state.json below, not
  // config::Button. Snapshot at send time, never itself persisted on
  // mobile.
  bool is_active = 7;
  oneof content {
    ActionList actions = 4;
    FolderContent folder = 5;
    Back back = 6;
    // 2. new — named switch_content, not switch: `switch` is a reserved
    // word in Swift, and every other language's codegen would have to
    // special-case escaping it for no benefit.
    SwitchContent switch_content = 8;
  }
}
// 3. new
message SwitchContent {
  SwitchState off = 1;
  SwitchState on = 2;
}
// 4. new
message SwitchState {
  optional string label = 1;
  optional string icon = 2;
  repeated Action actions = 3;
}
```

1. Plain `bool`, not `optional` — no meaningful "unset" state; a button
   with no recorded press yet is `off` (state 0), same default
   `switch_state.json` itself uses.
2. See comment — a real cross-language keyword collision, not
   theoretical, worth writing down so nobody "simplifies" it back to
   `switch` later.
3. `SwitchContent` holds exactly two named fields, `off`/`on`, not
   `stateA`/`stateB` — every real use case this slice or 09a will ever
   carry (mute, a GoXLR route, a light) is genuinely binary; `is_active`
   reads directly as "the `on` state is showing."
4. `SwitchState` deliberately mirrors `Button`'s own `label`/`icon` shape
   plus a bare `actions` list — no nested `ActionList` wrapper needed,
   since this isn't a oneof case competing with `Folder`/`Back`.

**Desktop-side signatures** — one Rust snippet spanning the three touched
files, since they're one cohesive unit (config shape → press logic →
config_sync merge):

```rust
// config.rs
pub enum ButtonContent {
    Actions { actions: Vec<Action> },
    Folder { buttons: Vec<Button> },
    Back,
    // 1. new
    Switch { off: SwitchState, on: SwitchState },
}
// 2. new
pub struct SwitchState {
    pub label: Option<String>,
    pub icon: Option<String>,
    pub actions: Vec<Action>,
}

impl Config {
    // 3. new — replaces actions_for_button (slice 08) with a superset:
    // which actions a press should run right now, and (for a Switch)
    // what a successful run flips to. current_states supplies live
    // Switch indices (button_id -> is "on" showing); absent means off,
    // matching switch_state.json's own default.
    pub fn press_target<'a>(
        &'a self,
        button_id: &str,
        current_states: &HashMap<String, bool>,
    ) -> Option<PressTarget<'a>> { ... }
}
// 4. new
pub struct PressTarget<'a> {
    pub actions: &'a [Action],
    // Some(new_value) for a Switch (flip iff the run succeeds); None
    // for a plain .actions button — nothing to flip.
    pub flips_to: Option<bool>,
}

// switch_state.rs
// 5. new — button_id -> is "on" showing, loaded from switch_state.json
// at launch, saved after every successful flip. Local file, sibling to
// device.json, never touches save_config/get_config, never exported.
pub type SwitchStates = std::sync::Arc<std::sync::Mutex<
    std::collections::HashMap<String, bool>,
>>;

// proto.rs
// 6. new — merges live SwitchStates into an already-built proto
// Config, for ConfigSync. From<&config::Config> stays pure/persisted-
// only (it has no access to SwitchStates and shouldn't gain one); this
// post-pass runs immediately after, at every config_sync send site.
pub fn apply_switch_states(config: &mut buttons::Config, states: &SwitchStates) { ... }
```

1. `Switch` — same `off`/`on` shape as the wire's `SwitchContent` above,
   kept in sync by hand (this file is written, not generated).
2. `SwitchState` mirrors `Button`'s own `label`/`icon` shape plus a bare
   `actions` list, matching the wire `SwitchState` exactly.
3. One function, not two call sites hand-rolling "pick actions, maybe
   flip." `server.rs`'s real `ButtonPress` handler and `lib.rs`'s `Test`
   command both call `press_target`, then (only on a successful run)
   apply `flips_to` and save `switch_state.json` — the single place this
   slice's "what does pressing this button do" logic lives. A plain
   `.actions` button's `flips_to` is always `None`, so the shared path
   costs that button type nothing.
4. `PressTarget` is `press_target`'s return type — plain data, no
   behavior of its own beyond what Note 3 already covers.
5. `Mutex<HashMap<...>>`, not a `watch`/`RwLock` — writes are rare (a
   press or a `Test` click) and reads happen once per `config_sync`; no
   contention this design needs to optimize for. Same reasoning the
   generic design this replaces already used.
6. **The seam this whole slice turns on**, carried over unchanged from
   the design it replaces: `From` stays pure, a post-pass merges runtime
   state in. A future reader reaching for "just thread the map into
   `From`" should land here instead of rediscovering the wall.

**Mobile-side signatures:**

```swift
// Connection.swift
// 1. new — button_id -> is "on" showing. Seeded from configSync's
// Button.isActive on every fresh sync (overwrites unconditionally — see
// Implementation Notes' precedence rule); flipped optimistically by
// PageGrid on tap, flipped again (not "reverted to X") on failure.
private(set) var stateOverrides: [String: Bool] = [:]

// 2. new
func applyOptimisticFlip(buttonId: String) {
    stateOverrides[buttonId, default: false].toggle()
}
```

1. `stateOverrides` — the local source of truth mobile renders from,
   corrected unconditionally by any later `config_sync` (Implementation
   Notes' precedence rule) or, from slice 09a on, any `state_push`.
2. `applyOptimisticFlip` is a toggle method, not a setter — with exactly
   two states, "the user tapped it" and "the press failed, undo" are the
   identical operation (flip), so there is no separate rollback code path
   to keep in sync with the optimistic one, and no prior-value
   bookkeeping.

## Implementation Notes

1. **Content-type selection needs a real 3-way choice.** `ButtonEditor`
   currently derives content type from a single `isFolder` boolean
   (`.actions` vs `.folder`). A third case doesn't fit a boolean — this
   becomes an explicit `contentType: "actions" | "folder" | "switch"`
   `$state`, with `isFolder`'s existing folder-buttons-preservation
   behavior (keep nested buttons around even while toggled off, per
   slice 4's spec) carried over for `"folder"` specifically, and the
   same "preserve while not selected" treatment extended to a Switch's
   two states.
2. **Why the index isn't "just persist it in `buttons.json` like
   everything else"** — restated briefly here since it's the load-
   bearing decision (full argument in EDD Open Question 8, Note 3): a
   Tier 1 Switch (the mute-toggle case) has no feedback API, ever.
   Resetting to `off` on every desktop restart is a guess that's wrong
   about half the time and never self-corrects. Persisting it in
   `buttons.json` instead would be worse in the other direction — it
   would ship inside an exported Profile, meaning "the mic happened to
   be muted at export time" travels into someone else's shared config.
   `switch_state.json`, local-only, is the one place that's neither.
3. **Precedence: `config_sync` always wins, unconditionally, over
   mobile's optimistic guess** — same "remove the invariant, don't
   maintain it" move as the EDD's other two precedence calls. No "is my
   press still in flight" check: a fresh sync (a reconnect, a future
   09a correction) simply overwrites `stateOverrides` for that id.
4. **The `Test` button's existing `run_actions` command becomes
   `test_button`, content-type-aware.** For a plain `.actions` button it
   behaves exactly as before (runs its one array). For a `.switch`
   button it calls the same `press_target`/flip path a real
   `ButtonPress` uses — Scope → In #7's "simulates a full real press,"
   not a separate testing-only code path that could drift from what a
   real press actually does.
5. **`server.rs`'s `handle_button_press` shape barely changes** — it
   already re-loads `Config` fresh on every press (slice 08 Implementation
   Note 3) and already runs actions via `spawn_blocking` (slice 08
   Implementation Note 2); this slice's addition is calling
   `press_target` instead of `actions_for_button`, and — only when
   `actions::run` returns `Ok(())` and `flips_to` is `Some(v)` — writing
   `v` into `SwitchStates` and saving `switch_state.json`. `ActionResult`
   itself is unchanged (`{button_id, ok, error}`); it doesn't need to
   carry the new state at all, because mobile already flipped optimistically
   the moment it sent the press.
6. **`is_active` on the wire `Button` is scoped to `.switch_content`
   buttons only** — a plain `.actions`/`.folder`/`.back` button always
   reports `false` (the proto default) and mobile never reads it, since
   `stateOverrides` is only ever consulted for `.switch` content. Not
   worth a `hasIsActive`-style presence check to enforce this; nothing
   reads the field for a non-Switch button in the first place.

## Definition of Done

1. [ ] `buttons.proto` changes compile in all three generated languages
   (schema-lock check, same as slice 08 DoD 5):
   `android/gradlew --project-dir protocol/verify-kotlin test`.
2. [ ] Creating a Switch button in the desktop editor, giving each state
   a distinct icon/label/action array, and clicking `Test` runs state A's
   actions (observable effect) and flips the live preview to state B's
   icon/label; clicking `Test` again runs B's actions and flips back —
   no mobile device needed to observe this.
3. [ ] With mobile paired and connected, tapping the Switch button flips
   its icon/label on mobile **immediately** (before the round trip
   completes — verify by eye, not just by final state) and fires haptic
   immediately, matching slice 08's `.actions` timing.
4. [ ] Pressing a Switch button whose current state's action is made to
   fail (e.g. an invalid hotkey) flips mobile's display optimistically,
   then flips it back when `ActionResult{ok:false}` arrives; desktop's
   `switch_state.json` entry for that button is unchanged (confirms the
   flip-on-success-only rule in Interface Note 7-8).
5. [ ] **Restart persistence.** Flip a Switch to `on`, quit and relaunch
   the desktop app, reconnect mobile: the button shows `on` correctly
   (not reset), and `buttons.json` contains no current-state key anywhere
   for it — only `switch_state.json` does. Confirms EDD Open Question 8
   Note 3 in practice, not just in the schema.
6. [ ] `protoc --swift_out=…` regen produces the expected
   `buttons.pb.swift` diff; `wire.pb.swift` has **no** diff (mechanical
   confirmation this slice touched no envelope message).

## Rollback

`buttons.proto` changes are additive (new oneof tag, new field tag) —
safe to `git revert` this slice's commits cleanly. Deleting
`switch_state.json` is harmless — every id resumes at its `off` default,
same as a fresh install. If a regenerated `.pb.swift` diverges further
than expected, re-run the exact `protoc` command above rather than
hand-editing the committed file, same as slice 08.
