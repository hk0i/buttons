## Implementation Notes

- **Repaint throttling is not eframe's default** — by default `eframe`/`egui`
  can redraw continuously. Must explicitly use `egui::Context::request_repaint()`
  / `request_repaint_after()` (event-driven redraw only) rather than assuming
  reactive behavior for free. This is the exact claim under test — confirm it,
  don't take it on faith.
- `egui::Grid` is fixed-rows/cols, not CSS `auto-fill`-style responsive wrap —
  the responsive layout will need to be hand-rolled (compute columns from
  available width each frame). This is the real unknown the spike exists to
  surface, not a formality.
- Idle CPU/GPU measurement (macOS): `powermetrics` (`sudo powermetrics
  --samplers cpu_power,gpu_power -i 1000 -n 30`) or Activity Monitor's
  Energy/GPU History tabs. Take the same measurement, same duration, on the
  slice-2 Tauri app (`npm run tauri dev`, window minimized) for a fair
  comparison — write both numbers down, not just this spike's.
- Whatever this spike finds — either direction — should feed back into EDD §4
  (`Why Tauri over Qt/C++`) as either reinforcement or a revision, same as the
  network POC spike's surprises were meant to feed back into §5.1/5.2.

## Findings

*(running log, filled in as the spike proceeds)*

- **Idle CPU: flat 0% for egui, matching Tauri — first reading was a
  measurement artifact, corrected after a controlled re-test.** Measured via
  `ps -o %cpu= -p <pid>`, 10 samples @ 1s.

  First pass (`Sense::click_and_drag()`, as shipped) showed a surprising
  sustained ~11.5% avg with no decay, vs. Tauri's decaying-to-0.0% pattern.
  Isolating by swapping only the `Sense` argument (`hover()` → 0%, `click()`
  → 0%, `click_and_drag()` → ~11%) initially pinned it on drag sensing
  specifically — but the user flagged they'd incidentally interacted with
  the window during that first egui run. Re-ran `click_and_drag()` with the
  machine deliberately left untouched: **flat 0.0%, all 10 samples** —
  identical to Tauri and to the earlier hover/click isolation runs. Separately,
  the user also flagged that the Tauri baseline's early non-zero samples came
  from them dragging the window to see the terminal underneath, not from app
  startup cost as first assumed — so that decay was interaction-driven too,
  not a Tauri-specific transient.

  | Build / condition | Samples (%CPU) | Pattern |
  |---|---|---|
  | Tauri (slice 3, `target/debug/desktop`) — window was dragged mid-sample | 7.5, 3.4, 1.3, 0, 0, 0, 0, 0, 0, 0 | Decays to flat **0.0%** once interaction stops |
  | egui, `click_and_drag()`, first run (machine not confirmed idle) | 12.2, 8.7, 10.0, 12.5, 4.0, 11.9, 14.3, 18.9, 11.2, 11.7 | Sustained ~11.5% — **artifact, not reproduced** |
  | egui, `Sense::hover()` (isolation) | flat **0.0%** ×10 | — |
  | egui, `Sense::click()` (isolation) | flat **0.0%** ×10 | — |
  | egui, `click_and_drag()`, re-run (machine confirmed idle) | flat **0.0%** ×10 | Matches Tauri |

  **Conclusion:** no real idle-CPU penalty from egui's drag sensing —
  `eframe-0.29.1` really does implement proper `ControlFlow::Wait`/
  `WaitUntil` reactive repaint (confirmed in its own source,
  `native/run.rs`) and it works as advertised once the measurement is
  actually controlled. Both apps behave identically and correctly: **real
  interaction (window drag, mouse activity) causes visible CPU draw in
  either framework, and both settle to flat 0% once genuinely left alone.**
  Not a framework difference — a measurement-methodology lesson (confirm the
  machine is actually idle before sampling) worth remembering for any future
  perf comparison here.
  **GPU comparison still outstanding** — `powermetrics` needs `sudo` and an
  interactive password prompt neither available in the agent's shell; handed
  to the user to run directly and report back.

- **Responsive wrap: hand-rolled, worked first try, no major friction.**
  `egui::Grid` has no `auto-fill` equivalent, so column count is computed from
  `ui.available_width()` and rows are ended manually every N items
  (`button_grid.rs`). ~15 lines total. Confirmed live-resizing down to
  ~500px — re-flows correctly. Real effort, but small — not the blocker the
  spec worried it might be.
- **Emoji icons render with tofu boxes for multi-codepoint glyphs.**
  E.g. `⏺️` (`U+23FA` + `U+FE0F` variation selector) shows a square for the
  selector codepoint — egui's default bundled font has no glyph for it.
  Root cause: browsers/webviews get full OS emoji-font fallback for free;
  egui does not — an emoji font has to be loaded explicitly (`egui_extras`
  has helpers for this). Real Tauri-vs-egui delta for this app's specific
  icon convention (emoji-as-glyph, per slice 2). Left unfixed per decision —
  doesn't block layout/reorder/perf testing, logged as a real cost if egui
  is ever chosen for real.
- **Drag-and-drop: full manual control, but genuinely nothing free.**
  First pass (swap-in-place on hover) worked but gave weak feedback — no
  visual signal of "a move is happening" beyond a dim/transparent tile, and
  the dim itself was initially invisible (semi-transparent white over a
  near-white panel background — a contrast bug, not a framework issue).
  Adding a cursor-following ghost (`egui::Area` at `Order::Tooltip`, ~15
  lines, reusing the tile-paint function) fixed this and felt good once in.
  Contrast with Tauri: HTML5 drag-and-drop gives a ghost cursor for free,
  but that default look isn't stylable and Tauri's own OS-level drag
  interceptor had to be explicitly disabled (`dragDropEnabled: false`) just
  to let the browser's DnD events fire at all (see slice 3). egui required
  more manual work up front, but every pixel of the drag feedback is fully
  under our control once written — no fighting a framework default.
