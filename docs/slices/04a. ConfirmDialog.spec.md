**Implements:** no EDD roadmap step directly — a slice-4 follow-up (see
`04. Folders Pages Profiles.spec.md` → Post-Implementation Notes). Treated as
its own thin vertical slice per this project's execution preference.
**TL;DR:** One reusable in-app confirmation dialog (native `<dialog>` +
`showModal()`, app-themed), mounted once, with a promise API
`await confirm({ … })` — replaces the cramped stopgap inline-confirm row in
`ProfileSwitcher` and adds a real guard to page delete and button delete,
which currently have none.

---

## Scope

**In:**
- **`ConfirmDialog.svelte`** — a single dialog component rendered once in a
  new root `+layout.svelte`, driven by a module-level store. Uses the
  platform `<dialog>` element via `showModal()` — backdrop, focus trap, and
  Esc-to-close come for free and work in Tauri 2's system WebKit.
- **`confirm.svelte.ts` store** — holds the current pending request (or
  `null`) and exposes `confirm(opts): Promise<boolean>`. Resolves `true` on
  confirm, `false` on cancel / Esc / backdrop dismiss. One request at a time
  (calls made while a dialog is already open reject or queue — see
  Implementation Notes).
- **Migrate `ProfileSwitcher.svelte`** — delete the inline `editing ===
  "delete"` branch and its markup/CSS; profile delete calls `confirm()`
  instead. The inline *name* inputs (create/rename) stay as they are —
  they're a `prompt()` substitute, out of scope here.
- **Guard `PagePager.svelte` page delete** (`×` / `removePage`) with
  `confirm()` — currently fires immediately.
- **Guard `ButtonEditor.svelte` button delete** (`remove`, line ~357) with
  `confirm()` — currently fires immediately. Also replace the two raw
  `window.confirm()` calls in `finish()` / `cancel()` (unsaved-draft
  prompts, lines ~224 / ~241) with the new `confirm()` — they silently
  return `true` in WKWebView today.
- **Shared destructive/cancel button styling** — `button.danger` already
  exists in `tokens.css`; add whatever the dialog's action row needs there
  rather than scoping it inside the component, so call sites stay consistent.
- **EDD correction** — update `01. Architecture Overview.edd.md` §7's
  WebView-constraint note: `window.confirm()` does **not** work reliably in
  Tauri's WKWebView (it silently returns `true`), contradicting what that
  note currently claims. Extend it to cover `confirm()` / `alert()`.

**Out:**
- A `prompt()` replacement / text-input dialog. The inline inputs in
  `ProfileSwitcher` and `PagePager` stay. If `ConfirmDialog` is later
  generalized to take a body snippet, that's a separate follow-up.
- Rich/marked-up dialog body — `body` is a plain string this slice (see
  Interface). The value of the component approach over `plugin-dialog` is
  that a body snippet *can* be added later without touching call sites; not
  built now.
- Any new confirm call sites beyond the four named above (drag-drop
  discards, folder-toggle-off data loss, etc.) — flag if noticed, don't add.
- A generic `UIAlertController`-style dialog (dynamic action array,
  `Promise<actionId>`) — evaluated and rejected: all five current call sites
  are boolean, and the known future need (`prompt()` replacement) is a
  body-content change, not a button-shape change. The dialog shell
  (mount-once, `<dialog>`/`showModal()`, singleton store, promise resolve on
  confirm/cancel/Esc/backdrop, focus handling) is ~90% of the code and
  identical either way, so generalizing later is a contained migration of
  one component + its call sites, not a rewrite. The one place a third
  button is plausible — the two `ButtonEditor` draft guards ("add draft &
  finish" / "discard & finish" / "cancel") — is the moment to revisit, not
  now.
- `plugin-dialog`'s native `ask()`/`confirm()` — evaluated and rejected:
  plain-text only, native OS chrome clashes with the Stream-Deck-style dark
  UI, and diverges per platform once mobile lands. `plugin-dialog` stays a
  dependency for its file picker (`LaunchAppField`), nothing else changes.
- Animations / transitions on the dialog beyond what `<dialog>` gives free.
- Light-mode styling — still deferred project-wide (slice 2's note stands).

## Interface / Data Contract

```ts
// $lib/stores/confirm.svelte.ts

export interface ConfirmOptions {
  title: string;
  body?: string;          // plain text; rendered as textContent, not HTML
  confirmLabel?: string;  // default "OK", or "Delete" when destructive
  cancelLabel?: string;   // default "Cancel"
  destructive?: boolean;  // default false — styles the confirm button as danger
}

/** Resolves true on confirm; false on cancel, Esc, or backdrop dismiss. */
export function confirm(opts: ConfirmOptions): Promise<boolean>;
```

Call-site shape:

```ts
if (await confirm({
  title: "Delete profile?",
  body: `"${profile.name}" and all its pages will be removed. This can't be undone.`,
  confirmLabel: "Delete",
  destructive: true,
})) {
  configStore.deleteProfile(profile.id);
}
```

## Implementation Notes

- **Why `confirm()` needs replacing at all:** `window.confirm()` has no
  working implementation in Tauri's WKWebView — it silently returns `true`,
  so a guarded destructive action fires with no dialog. Same root cause as
  the `window.prompt()` no-op documented in EDD §7; the EDD currently claims
  `confirm()` "works fine," which is wrong and gets corrected this slice.
- **One dialog, one instance.** Mount `<ConfirmDialog />` exactly once in
  `+layout.svelte`. The store is module-level singleton state — importing
  `confirm` anywhere talks to that one instance.
- **Concurrent calls:** a second `confirm()` while one is open should be rare
  (dialogs are modal and block interaction). Simplest correct behavior:
  reject/resolve-`false` the new call immediately, or queue it. Pick queue
  only if a real call site needs it — otherwise resolve `false` and move on.
- **Focus:** `showModal()` moves focus into the dialog. Default focus to the
  **cancel** button (safer for destructive prompts). `<dialog>` restores
  focus to the invoker on close automatically.
- **Dismiss = cancel.** The native `cancel` event (Esc) and a backdrop click
  both resolve `false`. For outside-click: backdrop clicks land on the
  `<dialog>` element itself, so `event.target === dialogEl` detects them —
  **but** any padding on the dialog element is also part of `dialogEl`, so a
  click on that padding would wrongly close it. Put all padding/layout on an
  inner wrapper `<div>` and keep the `<dialog>` itself box-only, or
  bounds-check the click against `dialogEl.getBoundingClientRect()`.
- **`user-select: none` is set globally on `body`** (`+page.svelte`) — the
  dialog body text should stay unselectable to match, no override needed.
- Keep the component dumb: no knowledge of profiles/pages/buttons. It renders
  `ConfirmOptions` and reports a boolean.

## Post-Implementation Notes

Walked 2026-09-10. `npm run check` green (0 errors). Dialog mechanism
verified against the running frontend with headless Chromium driving the
real `confirm.svelte.ts` module: themed modal (`--neutral-600` panel, dimmed
backdrop), default focus on Cancel, Esc / backdrop / Cancel all resolve
`false`, confirm resolves `true`, non-destructive shows "OK" primary /
destructive "Delete" danger, a second `confirm()` while one is open resolves
`false` immediately and the first stays. Page-delete, button-delete, and the
draft-discard guard walked manually in `tauri dev` and pass.

- **Focus containment:** native `<dialog>` `showModal()` keeps focus off all
  background controls, as intended. Chromium's tab cycle inserts one stop on
  `<body>` between wraps (`Cancel → Delete → body → Cancel …`); harmless —
  focus never reaches app content — and not necessarily present in
  WKWebView. Left as-is; a ~8-line Tab-wrap handler is the fix if it ever
  bothers anyone.
- **`window.confirm()`/`prompt()` limitation** now documented accurately in
  EDD §7 (was previously claiming `confirm()` "works fine").
- **Deferred, still open:** a `prompt()`-style text-entry dialog. The inline
  name inputs in `ProfileSwitcher`/`PagePager` stay until then. `ConfirmDialog`
  could grow a body snippet to cover it without breaking call sites — see the
  Out section's note on the rejected generic-dialog design.

## Rollback

Low risk — additive (one new component, one new store, one new layout file)
plus four small call-site edits and a doc correction. If the dialog
misbehaves, revert the four call sites to their prior state (profile delete
back to the inline row from commit `b118955`; page/button delete back to
unguarded) and delete the new files; nothing else depends on them.
