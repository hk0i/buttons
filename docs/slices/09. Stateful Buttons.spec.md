**Implements:** `01. Architecture Overview.edd.md`, Testing & Rollout Plan
step 9; Open Questions → "Stateful buttons — `state_push` design."
**TL;DR:** A button gains a persisted `isActive` flag, editable on desktop
independent of any press. Editing it there pushes a `state_push` to the
paired mobile client and both UIs re-render live — the first out-of-band
(not press-triggered) update on the wire.

## Scope

**In:**

1. `wire.proto`: `StatePush` (D→M) message, added to `Envelope`'s oneof.
2. `buttons.proto`: `Button` gains `bool is_active = 7`.
3. Desktop: `Button.isActive`, editable via a new checkbox in
   `ButtonEditor`, flowing through the existing autosave path (same
   debounce as `label`/`icon` — no new persistence mechanism).
4. Desktop: `save_config` diffs incoming `Config` against what's on disk
   and broadcasts one `StatePush` per button whose `isActive` actually
   changed, to whichever mobile client is currently connected. Generic —
   fires for a diff caused by any future caller, not only this slice's
   checkbox.
5. Desktop: `DeckButton.svelte` (editor preview + `PreviewPane`) shows
   `isActive` visually — lets DoD verification happen without a paired
   phone.
6. Mobile: `DeckButton` shows `isActive` on its **background** channel —
   the channel slice 08 (Out #7) reserved for this — composing with the
   existing press-flash icon overlay unchanged.
7. Mobile: a `state_push` for a button not currently on screen is still
   recorded (not dropped) — the next time that Page/folder is visible,
   it renders correctly with no extra round trip.

**Out:**

1. Any real Tier 1/2/3 trigger that flips `isActive` itself (OS mute
   state, OBS record state, …) — no Tier 1 use case produces real
   external state (EDD Open Question 8); the desktop editor checkbox is
   the only v1 source. A future Tier 2 integration (step 13) calls the
   same diff-and-broadcast path this slice builds; wiring one up is not
   this slice.
2. `profile_switch` — step 10, unrelated message.
3. Live nav-cursor mirroring — unrelated wire channel, still step 7's own
   deferred design (EDD §5.2 Open Question 3).
4. The edit-churn `config_sync` debounce/dirty-check (EDD §5.2 Corollary
   #2) — `state_push` is a narrower, purpose-built channel that
   sidesteps needing that machinery, not a step toward building it.
5. Per-button "which actions changed the state" semantics — `isActive` is
   a plain flag on `Button`, not a new `Action` variant. See EDD Open
   Question 8, Note 1.
6. A real design-token/color palette — same placeholder-tint approach as
   slice 08's `StatusColors.swift`, extended, not replaced.
7. Any UI to show *why* a button is active (a tooltip, a detail panel) —
   the background tint alone is the whole v1 signal.

> **Rule for agent:** stay inside this scope. If something out of scope
> blocks you, stop and flag it — don't silently expand scope to route around
> it.

## Interface / Data Contract

`protocol/buttons.proto` — additive field, next free tag on `Button`:

```proto
message Button {
  string id = 1;
  optional string label = 2;
  optional string icon = 3;
  // 1. new — see wire.proto's StatePush
  bool is_active = 7;
  oneof content {
    ActionList actions = 4;
    FolderContent folder = 5;
    Back back = 6;
  }
}
```

1. Plain `bool`, not `optional` — proto3's default-`false` presence is
   exactly right for a flag with no meaningful "unset" state, unlike
   `label`/`icon`'s real absent-vs-empty distinction.

`protocol/wire.proto` — new message, next free `Envelope` tag:

```proto
message Envelope {
  string protocol_version = 1;
  oneof message {
    PairRequest pair_request = 2;
    PairResponse pair_response = 3;
    ConfigSync config_sync = 4;
    ButtonPress button_press = 5;
    ActionResult action_result = 6;
    // 2. new — unsolicited D→M
    StatePush state_push = 7;
  }
}

message StatePush {
  string button_id = 1;
  bool is_active = 2;
}
```

2. `state_push`, D→M, unsolicited — no request it answers, unlike
   `action_result`. Field names mirror `Button.is_active` exactly (wire
   name == in-code name, CLAUDE.md).

**Desktop-side signatures** — pinned here for the same reason slice 08
pinned its mobile ones: each settles a decision the prose alone leaves
ambiguous.

```rust
// config.rs
pub struct Button {
    pub id: String,
    pub label: Option<String>,
    pub icon: Option<String>,
    // 3. new — old config.json files predate this field
    #[serde(default)]
    pub is_active: bool,
    pub content: ButtonContent,
}

impl Config {
    // 4. new — flat id -> is_active map over every Profile (not just
    // active), for save_config's diff. Same depth-first shape as
    // find_actions (slice 08), generalized to collect instead of search.
    pub fn active_states(&self) -> std::collections::HashMap<String, bool> { ... }
}

// server.rs
// 5. new — one D→M state change, whatever triggered it
pub struct StateChange {
    pub button_id: String,
    pub is_active: bool,
}
// 6. new — v1 has one connection; broadcast (not a per-connection
// unicast registry) is the simplest thing that's still correct at N=1
// and requires no rework to reach multiple connected devices later.
pub type StatePushTx = tokio::sync::broadcast::Sender<StateChange>;
```

3. `#[serde(default)]`, not a migration script — matches this project's
   existing tolerance for additive config fields (no versioned-migration
   machinery exists anywhere in `config.rs` yet).
4. Walks every Profile, not just `active_profile_id` — the desktop editor
   can edit a Profile that isn't currently active, and its `isActive`
   edits must still diff correctly.
5. Deliberately generic over the caller — `save_config`'s diff constructs
   these from whatever changed, not from "the checkbox specifically."
   Keeps step 13's future Tier 2 integrations free to flip `isActive`
   through the same `save_config` path with zero new plumbing.
6. `broadcast`, not a `Mutex<Option<Sender<...>>>` unicast slot mirroring
   `ConnSlot` — `state_push` has no per-recipient payload (unlike
   `nav_cursor`'s future per-device cursor, EDD Open Question 3.4), so
   there is nothing a broadcast-to-everyone-connected model gets wrong,
   even once N>1 (deferred, §2 Non-Goals). A lagging receiver drops
   old events (`RecvError::Lagged`) rather than blocking the sender —
   acceptable for a UI-refresh signal that's about to be superseded by
   whatever state is current anyway.

**Mobile-side signatures:**

```swift
// Connection.swift
// 7. new — button_id -> is_active, deltas since the last configSync
private(set) var stateOverrides: [String: Bool] = [:]

// PageGrid.swift / ButtonGrid.swift / DeckButton.swift
// 8. new — PageGrid's lookup, threaded through ButtonGrid same shape
// pressFlash used in slice 08
var isActive: (Buttons_Button) -> Bool = { _ in false }
```

7. Cleared to `[:]` in the `.configSync` case of `handle(envelope:)` —
   the precedence rule (EDD Open Question 8, Note 4): a fresh
   `config_sync` already embeds current truth, so any standing override
   is either confirmed (harmless to drop and re-derive) or stale
   (must be dropped). No sequence counter needed here (unlike
   `ActionResultEvent`) — `isActive(for:)` (below) is read directly in a
   view's `body`, and `@Observable`'s mutation tracking fires
   unconditionally on assignment, not gated on `Equatable` inequality
   the way `.onChange(of:)` is.
   ```swift
   func isActive(for button: Buttons_Button) -> Bool {
       stateOverrides[button.id] ?? button.isActive
   }
   ```
8. A closure, not a `Set<String>`/`[String: Bool]` passed by value down
   three views — `DeckButton` takes a plain `Bool` (like `pressFlash`
   defaults `nil`) so its `#Preview` stays trivial; `ButtonGrid` calls
   the closure once per row in its own `ForEach`, same place it already
   resolves `pressFlash` per row. Default `{ _ in false }` keeps every
   existing `#Preview` in all three files compiling unchanged.

## Implementation Notes

1. **`save_config` is the only write path that ever changes `isActive`
   this slice** — the checkbox is a normal `$state` var in
   `ButtonEditor`, included in the existing 500ms-debounced `$effect`
   alongside `label`/`icon`/`isFolder`/`actions`, going through the same
   `configStore.saveButtonAt` → `persist()` → `invoke("save_config", …)`
   round trip everything else already uses. No new frontend
   invoke, no bypassing the debounce — a checkbox flip is cheap enough
   that piggybacking the existing 500ms window is fine, not worth a
   special-cased immediate call.
2. **The diff happens in the `save_config` Tauri command, comparing the
   config already on disk to the incoming one**, via `active_states()`
   on each side. For every id present in either map with a different
   (or newly-`true`) value, broadcast a `StateChange`. Deleted buttons
   (present in old, absent from new) emit nothing — no id left on mobile
   to update.
3. **Broadcast happens before the new config is written**, not after —
   there is no correctness reason either order matters (the write is
   local disk, the broadcast is a different process's WebSocket), but
   diffing against a config that's already been overwritten is a
   use-after-free of the comparison, not just a style choice.
4. **`server::run`'s signature changes** to accept the `StatePushTx`
   created in `lib.rs`'s `run()`; `handle_connection` calls
   `.subscribe()` once per connection and adds a third
   `tokio::select!` arm alongside `ws.next()` and `evict_rx`:
   ```rust
   change = state_push_rx.recv() => match change {
       Ok(change) => { let _ = send_envelope(&mut ws, state_push_envelope(&change)).await; }
       Err(tokio::sync::broadcast::error::RecvError::Lagged(_)) => {} // drop, not fatal
       Err(tokio::sync::broadcast::error::RecvError::Closed) => {}    // sender outlives the app; unreachable in practice
   }
   ```
5. **Mobile records a `state_push` for an off-screen button too** —
   `stateOverrides` is keyed by `button_id` globally, not scoped to
   whatever Page/folder is currently rendered, so nothing needs to
   change about how `PageGrid`/`ButtonGrid` decide what's on screen.
6. **Desktop's own `DeckButton.svelte` gets the same visual treatment as
   mobile** — a background tint via a new `--active` CSS custom property
   (placeholder value, not a real token), `class:active={isActive}`. This
   is what makes the DoD below verifiable without a paired phone.
7. **Not reusing `.selected`'s border-highlight styling** for `isActive`
   — `selected` means "the editor has this button open," an unrelated
   transient UI-focus concept that already exists and must keep working
   independent of `isActive`; a button can be both, neither, or either
   independently.

   shows the current on-disk `isActive` state correctly, including for a

   than requiring delivery of every intermediate `state_push`.

   emit a spurious `state_push` for that button — confirms the diff is
   keyed on an actual `isActive` change, not "this button was touched."
