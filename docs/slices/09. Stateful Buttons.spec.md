**Implements:** `01. Architecture Overview.edd.md`, Testing & Rollout Plan
step 9; Open Questions → "Stateful buttons — `state_push` design."
**TL;DR:** A button gains a live, in-memory (never persisted) `isActive`
flag. A test affordance on desktop flips it; that pushes a `state_push` to
the paired mobile client and both UIs re-render live — the first
out-of-band (not press-triggered) update on the wire.

## Scope

**In:**

1. `wire.proto`: `StatePush` (D→M) message, added to `Envelope`'s oneof.
2. `buttons.proto`: `Button` gains `bool is_active = 7` — wire-only, not
   mirrored on `config::Button` (see Note below, and EDD Open Question 8
   Note 1).
3. Desktop: an in-memory `ActiveStates` map (`button_id -> bool`), held in
   Tauri-managed state, reset empty on every launch. Never touches
   `buttons.json` and never rides `save_config`.
4. Desktop: a `set_button_active` Tauri command mutates that map and
   broadcasts one `StatePush` to whichever mobile client is connected.
   Generic over the caller — a future Tier 2 integration (step 13) calls
   the same command/broadcast path.
5. Desktop: a "Toggle Active (test)" affordance in `ButtonEditor`, next to
   the existing `Test` button — v1's only caller of Scope → In #4, until a
   real Tier 2 reporter exists.
6. Desktop: its own grid (`DeckButton.svelte` in the editor preview and
   `PreviewPane`) shows the live `ActiveStates` value — lets DoD
   verification happen without a paired phone. New `get_active_states`
   query command + a Tauri event the frontend subscribes to.
7. Desktop: `config_sync` is built by merging the live `ActiveStates` map
   into a freshly-built proto `Config` at send time (`proto.rs`), so a
   newly-connected (or reconnecting) mobile client sees current state
   immediately, not just "false until the next flip."
8. Mobile: `DeckButton` shows `isActive` on its **background** channel —
   the channel slice 08 (Out #7) reserved for this — composing with the
   existing press-flash icon overlay unchanged.
9. Mobile: a `state_push` for a button not currently on screen is still
   recorded (not dropped) — the next time that Page/folder is visible, it
   renders correctly with no extra round trip.

**Out:**

1. Any real Tier 1/2/3 trigger that flips `isActive` itself (OS mute
   state, OBS scene/record state, a soundboard's playing sound, …) — no
   Tier 1 use case produces real external state (EDD Open Question 8);
   the desktop test affordance is the only v1 source. Wiring up a real
   reporter is step 13's (or a later slice's) work, not this one's.
2. **Persisting `isActive` anywhere** — not in `config::Button`, not in
   `buttons.json`, not in an exported Profile. See Scope → In #2 and the
   Implementation Notes below for why; this is a product decision (PRD
   Button Model 7), not an oversight to fix later.
3. `profile_switch` — step 10, unrelated message.
4. Live nav-cursor mirroring — unrelated wire channel, still step 7's own
   deferred design (EDD §5.2 Open Question 3).
5. The edit-churn `config_sync` debounce/dirty-check (EDD §5.2 Corollary
   #2) — unrelated: that corollary is about not re-pushing a full sync on
   every autosaved text-field edit. This slice's `config_sync` change
   (Scope → In #7) is a merge-at-send-time read, not a new push trigger.
6. Per-button "which actions changed the state" semantics — `isActive` is
   a plain flag on `Button`, not a new `Action` variant. See EDD Open
   Question 8, Note 2.
7. A real design-token/color palette — same placeholder-tint approach as
   slice 08's `StatusColors.swift`, extended, not replaced.
8. Any UI to show *why* a button is active (a tooltip, a detail panel) —
   the background tint alone is the whole v1 signal.

> **Rule for agent:** stay inside this scope. If something out of scope
> blocks you, stop and flag it — don't silently expand scope to route around
> it.

## Interface / Data Contract

`protocol/buttons.proto` — additive field, next free tag on `Button`:

```proto
message Button {
  string id = 1;
  optional string label = 2;
  optional string icon = 3;
  // 1. new — wire-only; no matching field on config::Button (Rust). See
  // wire.proto's StatePush and EDD Open Question 8 Note 1.
  bool is_active = 7;
  oneof content {
    ActionList actions = 4;
    FolderContent folder = 5;
    Back back = 6;
  }
}
```

1. Plain `bool`, not `optional` — proto3's default-`false` presence is
   exactly right for "no reporter for this button (yet)."

`protocol/wire.proto` — new message, next free `Envelope` tag:

```proto
message Envelope {
  string protocol_version = 1;
  oneof message {
    PairRequest pair_request = 2;
    PairResponse pair_response = 3;
    ConfigSync config_sync = 4;
    ButtonPress button_press = 5;
    ActionResult action_result = 6;
    // 2. new — unsolicited D→M
    StatePush state_push = 7;
  }
}

message StatePush {
  string button_id = 1;
  bool is_active = 2;
}
```

2. `state_push`, D→M, unsolicited — no request it answers, unlike
   `action_result`. Field names mirror `Button.is_active` exactly (wire
   name == in-code name, CLAUDE.md).

**Desktop-side signatures** — pinned here for the same reason slice 08
pinned its mobile ones: each settles a decision the prose alone leaves
ambiguous.

```rust
// server.rs
// 3. new — one D→M state change, whatever triggered it
pub struct StateChange {
    pub button_id: String,
    pub is_active: bool,
}
// 4. new — v1 has one connection; broadcast (not a per-connection
// unicast registry) is the simplest thing that's still correct at N=1
// and requires no rework to reach multiple connected devices later.
pub type StatePushTx = tokio::sync::broadcast::Sender<StateChange>;
// 5. new — button_id -> is_active, in memory only. Sparse: an id absent
// from the map has no reporter and renders inactive, same "absence is a
// real state, not a stand-in for false" shape as mobile's
// stateOverrides. Never read from or written to disk.
pub type ActiveStates = std::sync::Arc<std::sync::Mutex<
    std::collections::HashMap<String, bool>,
>>;
```

```rust
// proto.rs
// 6. new — merges live ActiveStates into an already-built proto Config,
// for ConfigSync. Deliberately not part of `impl From<&config::Config>
// for buttons::Config`: From is stateless by the trait's own contract,
// so it can only ever see persisted data — it has no way to accept a
// runtime-state parameter without ceasing to be a `From` impl. A
// separate post-pass over the built tree reuses that existing
// conversion instead of duplicating the Profile/Page/Button walk a
// second time.
pub fn apply_active_states(config: &mut buttons::Config, states: &ActiveStates) { ... }
```

3-4. Same shapes slice 08 would have used for a unicast reply, adapted
   for an unsolicited broadcast — see Interface Note 6 below for why
   broadcast, not a `ConnSlot`-style unicast registry.
5. `Mutex<HashMap<...>>`, not a `watch`/`RwLock` — writes are rare (a
   manual test click, later a Tier 2 event) and reads happen once per
   `config_sync`; no contention this design needs to optimize for.
6. **The seam this whole slice turns on.** `From<&config::Button>` stays
   pure and always emits `is_active: false` (proto default) — it has no
   access to `ActiveStates` and shouldn't gain one. `apply_active_states`
   runs immediately after, at every `config_sync` send site, mutating the
   already-built proto tree in place. A future reader reaching for "just
   thread the map into `From`" hits this note instead of rediscovering
   the wall.

**Mobile-side signatures:**

```swift
// Connection.swift
// 7. new — button_id -> is_active, deltas since the last configSync
private(set) var stateOverrides: [String: Bool] = [:]

// PageGrid.swift / ButtonGrid.swift / DeckButton.swift
// 8. new — PageGrid's lookup, threaded through ButtonGrid same shape
// pressFlash used in slice 08
var isActive: (Buttons_Button) -> Bool = { _ in false }
```

7. Cleared to `[:]` in the `.configSync` case of `handle(envelope:)` —
   the precedence rule (EDD Open Question 8, Note 5): a fresh
   `config_sync` is built by merging the live desktop-side map at send
   time, so it already embeds current truth — any standing override is
   either confirmed (harmless to drop and re-derive) or stale (must be
   dropped). No sequence counter needed here (unlike `ActionResultEvent`)
   — `isActive(for:)` (below) is read directly in a view's `body`, and
   `@Observable`'s mutation tracking fires unconditionally on assignment,
   not gated on `Equatable` inequality the way `.onChange(of:)` is.
   ```swift
   func isActive(for button: Buttons_Button) -> Bool {
       stateOverrides[button.id] ?? button.isActive
   }
   ```
8. A closure, not a `Set<String>`/`[String: Bool]` passed by value down
   three views — `DeckButton` takes a plain `Bool` (like `pressFlash`
   defaults `nil`) so its `#Preview` stays trivial; `ButtonGrid` calls
   the closure once per row in its own `ForEach`, same place it already
   resolves `pressFlash` per row. Default `{ _ in false }` keeps every
   existing `#Preview` in all three files compiling unchanged.

## Implementation Notes

1. **Why not persist — the argument in full, not just the Scope line.**
   PRD Button Model 7 makes an exported Profile a plain, shareable file.
   Every real use case for this flag (mic mute, OBS active scene, a
   soundboard sound playing, an operation in flight) is a live external
   signal, never a value the user authors and expects to travel with
   their config. A persisted `isActive` would (a) ship a snapshot of
   someone's live state inside a Profile someone else imports, which is
   simply wrong for a shared config file, and (b) mean a disk write on
   every flip for states that can change sub-second. So: no field on
   `config::Button`, no key in `buttons.json`, no participation in
   `save_config`/`get_config` at all. `ActiveStates` (in-memory,
   reset empty on launch) is the entire desktop-side source of truth.
2. **The test affordance lives next to `Test`, not as a bound checkbox.**
   `ButtonEditor.svelte`'s existing `Test` button (line ~375, pre-slice
   09) already fires a one-shot action rather than configuring a
   property — the right precedent for a control that flips transient
   state, unlike a checkbox bound into the autosave `$effect`, which
   would visually claim `isActive` is a persisted property like
   `label`/`icon`. Call `set_button_active` directly on click; no
   debounce (this isn't the `saveButtonAt`/`persist()` path at all).
   Expect this control to be removed or superseded once a real Tier 2
   reporter exists to flip the flag instead.
3. **`server::run`'s signature changes** to accept both the
   `StatePushTx` and the `ActiveStates` map created in `lib.rs`'s
   `run()`; `handle_connection` calls `.subscribe()` once per connection
   and adds a third `tokio::select!` arm alongside `ws.next()` and
   `evict_rx`:
   ```rust
   change = state_push_rx.recv() => match change {
       Ok(change) => { let _ = send_envelope(&mut ws, state_push_envelope(&change)).await; }
       Err(tokio::sync::broadcast::error::RecvError::Lagged(_)) => {} // drop, not fatal
       Err(tokio::sync::broadcast::error::RecvError::Closed) => {}    // sender outlives the app; unreachable in practice
   }
   ```
4. **The initial `config_sync` (on connect) calls `apply_active_states`**
   after building the proto `Config` via the existing `From` impl, before
   sending — so a freshly-connected (or reconnected) mobile client shows
   correct current state immediately, not "everything false until the
   next flip." This is the only `config_sync` send site that exists yet
   (the edit-churn corollary #2 live-resync path is still unbuilt, Scope
   → Out #5), so there is exactly one call site to update.
5. **Desktop's own live indicator is a genuine addition, not free** — a
   new `get_active_states` query command, a Tauri event
   (`active-state-changed`) emitted from `set_button_active`, and a small
   `activeStates.svelte.ts` store the frontend subscribes to once at
   startup (alongside `configStore.load()`). This is what makes DoD 2
   below verifiable with no paired phone; if it turns out to be more than
   this slice should carry, cut Scope → In #6 and DoD 2 folds into DoD 3
   (verify via mobile only).
6. **Broadcast, not a unicast registry.** `state_push` has no
   per-recipient payload (unlike `nav_cursor`'s future per-device cursor,
   EDD Open Question 3.4) — there is nothing a broadcast-to-everyone-
   connected model gets wrong, even once N>1 (deferred, §2 Non-Goals). A
   lagging receiver drops old events (`RecvError::Lagged`) rather than
   blocking the sender — acceptable for a UI-refresh signal that's about
   to be superseded by whatever state is current anyway.
7. **Mobile records a `state_push` for an off-screen button too** —
   `stateOverrides` is keyed by `button_id` globally, not scoped to
   whatever Page/folder is currently rendered, so nothing needs to
   change about how `PageGrid`/`ButtonGrid` decide what's on screen.
8. **Not reusing `.selected`'s border-highlight styling** for `isActive`
   on desktop — `selected` means "the editor has this button open," an
   unrelated transient UI-focus concept that already exists and must keep
   working independent of `isActive`; a button can be both, neither, or
   either independently.
