# Slice Spec: Foreground Reconnect

**Implements:** follow-up to `07. Discovery, Pairing & Config Sync.spec.md`,
Testing & Rollout Plan step 7.
**TL;DR:** foregrounding the app always re-verifies the connection and
silently reconnects to the last-paired desktop if it's dead — not just on
cold launch, and not only when `receiveLoop()` happens to notice the drop
on its own.

## Scope

**In:**
1. **A foreground check, independent of `receiveLoop()`'s own failure
   detection.** Today `RootView` (`ButtonsApp.swift`) only reacts to
   `connection.isConnected` flipping `true` → `false` — that flip depends
   on `URLSessionWebSocketTask`'s receive callback actually firing, and
   iOS suspends a backgrounded app's sockets, so the callback may not run
   until well after the drop actually happened, or not until the next read
   is attempted. Foregrounding must not assume `isConnected` is still
   trustworthy — it has to actively confirm the socket, not just read the
   cached flag.
2. **`DesktopConnection` gains an `async` probe of the live socket** —
   wraps `URLSessionWebSocketTask.sendPing(pongReceiveHandler:)` against
   the current `webSocketTask`, not a read of `isConnected`. A failed
   ping (or no task at all) is what actually means "dead," and sets
   `isConnected = false`.
3. **Trigger is `@Environment(\.scenePhase)` in `RootView`, not
   `didBecomeActiveNotification`.** `didBecomeActive` fires on every
   transient interruption (Control Center, a dismissed notification
   banner) — a real background round-trip is what should trigger a probe,
   not every momentary activation. `PairingView`'s existing
   `didBecomeActiveNotification` listener (the `cameraDenied` escape)
   stays as-is — it genuinely wants "any activation," a different need
   than this trigger. See Implementation Notes for the exact phase
   sequence to verify before writing the condition.
4. **`PairingSession` becomes `@MainActor`, and `attemptAutoReconnect`
   becomes `async` with a state-derived dedupe guard** — see Interface /
   Data Contract. This is what makes "foreground probe fails → reconnect"
   safe to call from multiple sites (the scenePhase handler and the
   existing `onChange(of: connection.isConnected)`) without a second,
   separate in-flight flag.
5. **Reconnect targets the last-paired device specifically** — this is
   already `attemptAutoReconnect`'s contract (`PairingStore.load()` +
   `discovery.endpoint(forDeviceId:)`), not new behavior; this slice's
   job is making sure foregrounding actually calls it promptly, mid-session
   included, not only at cold launch.
6. **No user-visible action required.** Foreground reconnect is silent
   unless it fails — a failed probe drops straight into the existing
   `Reconnecting` → `NotFound` states `PairingView` already renders
   (slice `07c`'s state diagram), reusing that copy rather than adding a
   parallel "reconnecting…" UI for this specific trigger.

**Out:**
1. **Combine, or converting anything to `ObservableObject`/`@Published`.**
   `@Environment(\.scenePhase)` and `.onReceive(NotificationCenter...)` are
   SwiftUI/Combine bridges already in use (`PairingView`) — using more of
   them here isn't a Combine adoption, and CLAUDE.md's SwiftUI section
   already forbids the pre-`@Observable` pattern outright.
2. **Migrating the rest of `DesktopConnection`'s pairing path
   (`pairCompletion`/`pairTimeout`/callback-based `connect`) to
   async/await.** That's the bigger completion-handler tree in this file
   and deserves its own slice with its own DoD — converting it mid-07d
   risks the buildable-state rule for a scope this spec didn't ask for.
   Only `verifyConnection` and `attemptAutoReconnect` convert here.
3. **`BGTaskScheduler`/background-refresh entitlement.** Nothing here
   needs to run *while backgrounded* — the desktop connection is only
   useful in the foreground (this is a Stream-Deck-style control surface,
   not a sync service), so there's no case for burning a background-task
   budget to keep a socket warm the user isn't looking at. If a real need
   for background keep-alive shows up later, it's a separate slice with
   its own entitlement/battery tradeoff discussion — not assumed here.
4. **Reconnect backoff/retry scheduling beyond what `attemptAutoReconnect`
   already does** (its ~5s/250ms poll). A foreground event either finds
   the desktop quickly or falls into the existing `NotFound` state with its
   existing manual "Scan QR Code" recovery — no new retry loop.
5. **Changing what counts as "last-paired device."** Still `PairingStore`'s
   single stored `device_id`/`auth_token` — no multi-device history, no
   picker. Same v1 constraint as `07c`'s Scope → Out item 2.
6. **A network-quality/heartbeat mechanism for a session that stays
   foregrounded the whole time.** This slice only fires on the foreground
   transition itself; a connection that dies while the app is already in
   front still relies on `receiveLoop()`'s own failure detection (unchanged
   from slice 07).

> **Rule for agent:** stay inside this scope. If something out of scope
> blocks you, stop and flag it — don't silently expand scope to route
> around it.

## Interface / Data Contract

Illustrative — shape to argue about before writing the real thing, per
CONTRIBUTING.md's doc-comment item 6.

**`ios/Buttons/Networking/Connection.swift`** — one `async` probe, no
`DispatchWorkItem`/`didComplete` guard needed: `withCheckedContinuation`
resumes exactly once by construction, and `Task.sleep` + a `TaskGroup`
race gives the timeout without a second manual "already fired?" flag.
Confirm `sendPing` has no native `async` overload in the target SDK before
writing this — if it does, use it directly and drop the continuation
wrapper entirely.

```swift
/// Actively confirms the socket is still alive — `isConnected` alone can
/// be stale after the app was backgrounded, since iOS may suspend the
/// task without ever delivering a receive failure. Flips `isConnected`
/// to `false` on a failed/timed-out ping.
func verifyConnection(timeout: Duration = .seconds(3)) async -> Bool {
    guard isConnected, let task = webSocketTask else { return false }
    let alive = await withCheckedContinuation { continuation in
        task.sendPing { error in continuation.resume(returning: error == nil) }
    }
    // TODO: race the continuation above against `timeout` (e.g. a
    // `TaskGroup` with a `Task.sleep` competitor) — a hung ping must not
    // hang this call forever. Sketch only; confirm the exact pattern
    // against this Swift version before implementing.
    if !alive { isConnected = false }
    return alive
}
```

**`ios/Buttons/Networking/Pairing.swift`** — `@MainActor` closes the
pre-existing bug where `attemptAutoReconnect`'s poll `Task` mutates
`autoReconnectState` off-main (nothing today isolates it), and
`isReconnectInFlight` is the single dedupe guard both call sites below
share — no separate flag in `RootView`:

```swift
@MainActor
@Observable
final class PairingSession {
    private(set) var lastError: String?
    private(set) var autoReconnectState: AutoReconnectState = .idle

    var isReconnectInFlight: Bool { autoReconnectState == .searching }

    func attemptAutoReconnect(discovery: DesktopDiscovery) async {
        discovery.start() // confirm idempotent — see Implementation Notes
        guard !isReconnectInFlight, let stored = PairingStore.load() else { return }
        autoReconnectState = .searching
        for _ in 0..<20 {
            if let endpoint = discovery.endpoint(forDeviceId: stored.deviceId) {
                autoReconnectState = .idle
                reconnect(stored: stored, endpoint: endpoint)
                return
            }
            try? await Task.sleep(for: .milliseconds(250))
        }
        autoReconnectState = .notFound
    }
}
```

**`ios/Buttons/ButtonsApp.swift`** — `RootView.body`, replacing
`didBecomeActiveNotification` with `scenePhase`. `didBecomeActive` gives
no way to distinguish "returned from background" from "returned from a
transient interruption" (Control Center, a dismissed banner) — both fire
it identically. `scenePhase` exposes `.background` as a distinguishable
case, which is the actual reason to switch triggers; a bare `(old, new)`
match on `.background → .active` is not reliable on its own, since a
Control Center pull also produces `.active → .inactive → .active` and
iOS may route the real background return through `.inactive` too — so the
`wasBackgrounded` latch below is the mechanism, not a fallback:

```swift
@Environment(\.scenePhase) private var scenePhase
@State private var wasBackgrounded = false

// ...

.onChange(of: scenePhase) { old, new in
    if new == .background { wasBackgrounded = true }
    guard new == .active, wasBackgrounded else { return }
    wasBackgrounded = false
    Task {
        if !(await connection.verifyConnection()) {
            await session.attemptAutoReconnect(discovery: discovery)
        }
    }
}
```

The existing `onChange(of: connection.isConnected)` reconnect call stays,
unchanged — `isReconnectInFlight` makes it a harmless no-op when the
scenePhase path already started a reconnect for the same drop, instead of
a second guard to maintain in two places.

## Implementation Notes

1. **Dedupe is the `isReconnectInFlight` guard on `PairingSession`, not a
   view-level flag** — see Interface / Data Contract. Both call sites
   (`RootView`'s scenePhase handler and its existing
   `onChange(of: connection.isConnected)`) go through the same
   `attemptAutoReconnect`, so there's one source of truth instead of a
   second flag to keep in sync. This also fixes a latent bug slice 07
   shipped with: nothing stopped connection flapping from spawning
   overlapping 5s poll `Task`s before this guard existed.
2. **`@MainActor` on `PairingSession` is a prerequisite for the guard to
   be race-free, not a style choice.** Under Swift 6 strict concurrency
   the existing off-main mutation in the poll loop (`Pairing.swift`'s
   `Task { autoReconnectState = ... }`, non-isolated today) is a compile
   error; under Swift 5 language mode it's a silent race the guard would
   otherwise inherit. Confirm which language mode this target builds
   under before implementing — it changes whether this is "fix a bug" or
   "fix a bug the compiler already caught."
3. **`sendPing` on a `nil`/already-cancelled task throws/crashes on some
   OS versions** — the `guard ... let task = webSocketTask` above is
   load-bearing, not defensive boilerplate.
4. **Foreground during an active pairing attempt** (`state ==
   .scanning`/`.connecting` in `PairingView`, or `pairCompletion` still
   set in `DesktopConnection`) must not be interrupted by this probe —
   `attemptAutoReconnect` only fires when `!isConnected` (now additionally
   guarded by `isReconnectInFlight`), and a fresh pair in progress hasn't
   set `isConnected` yet either, so check this doesn't race the QR-scan
   path into a spurious `NotFound` before the manual pairing attempt
   resolves.
5. **Simulator can't test the real suspend/resume socket behavior** — the
   backgrounding-then-foreground path needs a real device (lock the
   phone, wait, unlock) per DoD item 2 below.
6. **Three things to verify before writing code, not during:**
   - `discovery.start()`'s idempotency. `attemptAutoReconnect` already
     calls it unconditionally every time; this slice calls
     `attemptAutoReconnect` far more often than slice 07 assumed. If
     `start()` double-starts the underlying `NWBrowser`, that's a new bug
     this slice introduces, not a pre-existing one.
   - Whether `URLSessionWebSocketTask.sendPing` has an `async` overload on
     the target SDK — if it does, `verifyConnection` doesn't need the
     `withCheckedContinuation` wrapper at all.
   - The real `scenePhase` transition sequence on device — confirm the
     `wasBackgrounded` latch (Interface / Data Contract's `RootView`
     snippet) actually catches a real background return; a bare
     `.background → .active` match alone is known-insufficient (a Control
     Center pull produces `.active → .inactive → .active`, and iOS may
     route the real case through `.inactive` too).

## Definition of Done

1. [ ] Mid-session: kill the desktop app (or disconnect its Wi-Fi) while
       the phone is foregrounded and connected, background the phone,
       bring it back — phone silently reconnects once the desktop is back,
       without a relaunch.
2. [ ] Real device: lock the phone for >30s while connected, unlock —
       either still connected (socket survived) or silently reconnects
       within the existing `~5s` poll window, no user action needed.
3. [ ] Foregrounding while genuinely still connected does not visibly
       flicker to `PairingView` or interrupt `DeckView`.
4. [ ] Foregrounding mid-QR-scan or mid-fresh-pair does not get
       interrupted by this probe (Implementation Note 3).
5. [ ] No double reconnect attempt fires from one foreground-while-dead
       event (Implementation Note 1).

## Rollback

Revert `ButtonsApp.swift`'s new `onChange(of: scenePhase)`,
`Connection.swift`'s `verifyConnection`, and `Pairing.swift`'s
`@MainActor`/`async`/`isReconnectInFlight` changes — no persisted-state or
wire-format change, so a plain revert is safe with no migration to undo.
