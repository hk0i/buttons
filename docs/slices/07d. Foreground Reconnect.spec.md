# Slice Spec: Foreground Reconnect

**Implements:** follow-up to `07. Discovery, Pairing & Config Sync.spec.md`,
Testing & Rollout Plan step 7.
**TL;DR:** foregrounding the app always re-verifies the connection and
silently reconnects to the last-paired desktop if it's dead — not just on
cold launch, and not only when `receiveLoop()` happens to notice the drop
on its own.

## Scope

**In:**
1. **A foreground check, independent of `receiveLoop()`'s own failure
   detection.** Today `RootView` (`ButtonsApp.swift`) only reacts to
   `connection.isConnected` flipping `true` → `false` — that flip depends
   on `URLSessionWebSocketTask`'s receive callback actually firing, and
   iOS suspends a backgrounded app's sockets, so the callback may not run
   until well after the drop actually happened, or not until the next read
   is attempted. Foregrounding must not assume `isConnected` is still
   trustworthy — it has to actively confirm the socket, not just read the
   cached flag.
2. **`DesktopConnection` gains an `async` probe of the live socket** —
   wraps `URLSessionWebSocketTask.sendPing(pongReceiveHandler:)` against
   the current `webSocketTask`, not a read of `isConnected`. A failed
   ping (or no task at all) is what actually means "dead," and sets
   `isConnected = false`.
3. **Trigger is `@Environment(\.scenePhase)` in `RootView`, not
   `didBecomeActiveNotification`.** `didBecomeActive` fires on every
   transient interruption (Control Center, a dismissed notification
   banner) — a real background round-trip is what should trigger a probe,
   not every momentary activation. `PairingView`'s existing
   `didBecomeActiveNotification` listener (the `cameraDenied` escape)
   stays as-is — it genuinely wants "any activation," a different need
   than this trigger. See Implementation Notes for the exact phase
   sequence to verify before writing the condition.
4. **`PairingSession` becomes `@MainActor`, and `attemptAutoReconnect`
   becomes `async` with a state-derived dedupe guard** — see Interface /
   Data Contract. This is what makes "foreground probe fails → reconnect"
   safe to call from multiple sites (the scenePhase handler and the
   existing `onChange(of: connection.isConnected)`) without a second,
   separate in-flight flag.
5. **Reconnect targets the last-paired device specifically** — this is
   already `attemptAutoReconnect`'s contract (`PairingStore.load()` +
   `discovery.endpoint(forDeviceId:)`), not new behavior; this slice's
   job is making sure foregrounding actually calls it promptly, mid-session
   included, not only at cold launch.
6. **No user-visible action required.** Foreground reconnect is silent
   unless it fails — a failed probe drops straight into the existing
   `Reconnecting` → `NotFound` states `PairingView` already renders
   (slice `07c`'s state diagram), reusing that copy rather than adding a
   parallel "reconnecting…" UI for this specific trigger.

**Out:**
1. **Reaching for Combine for the probe or the dedupe.** Not a CLAUDE.md
   ban — `ObservableObject`/`@Published` is built on Combine, but Combine
   itself is a separate, legal tool. Excluded here on shape, not policy:
   `isConnectionAlive` is one-shot with a timeout (`Future` → `.timeout` →
   `.sink` plus a stored `AnyCancellable` is more ceremony than the
   `async` version, not less — Combine earns its weight on streams, and
   there's no stream here), and the dedupe guard needs to live in
   `@MainActor`-isolated state that a `sink` closure can't touch cleanly
   under strict concurrency without its own hop. `@Environment(\.scenePhase)`
   and `.onReceive(NotificationCenter...)` are SwiftUI/Combine bridges
   already in use (`PairingView`) and stay — that's not an adoption of
   Combine as this slice's state/async model, just the existing bridge.
   **Not a blanket rule for later slices** — a genuine stream (e.g. a
   foregrounded-session heartbeat merging a timer with connection-state
   changes, debounced) is exactly where Combine would earn its place; this
   item excludes it only because 07d has no stream to justify it.
2. **Migrating the rest of `DesktopConnection`'s pairing path
   (`pairCompletion`/`pairTimeout`/callback-based `connect`) to
   async/await.** That's the bigger completion-handler tree in this file
   and deserves its own slice with its own DoD — converting it mid-07d
   risks the buildable-state rule for a scope this spec didn't ask for.
   Only `isConnectionAlive` and `attemptAutoReconnect` convert here.
3. **`BGTaskScheduler`/background-refresh entitlement.** Nothing here
   needs to run *while backgrounded* — the desktop connection is only
   useful in the foreground (this is a Stream-Deck-style control surface,
   not a sync service), so there's no case for burning a background-task
   budget to keep a socket warm the user isn't looking at. If a real need
   for background keep-alive shows up later, it's a separate slice with
   its own entitlement/battery tradeoff discussion — not assumed here.
4. **Reconnect backoff/retry scheduling beyond what `attemptAutoReconnect`
   already does** (its ~5s/250ms poll). A foreground event either finds
   the desktop quickly or falls into the existing `NotFound` state with its
   existing manual "Scan QR Code" recovery — no new retry loop.
5. **Changing what counts as "last-paired device."** Still `PairingStore`'s
   single stored `device_id`/`auth_token` — no multi-device history, no
   picker. Same v1 constraint as `07c`'s Scope → Out item 2.
6. **A network-quality/heartbeat mechanism for a session that stays
   foregrounded the whole time.** This slice only fires on the foreground
   transition itself; a connection that dies while the app is already in
   front still relies on `receiveLoop()`'s own failure detection (unchanged
   from slice 07). **Explicitly includes Local Network permission
   revoked while foregrounded and connected** — the other half of the
   gap `Discovery.swift`'s `isLocalNetworkDenied` comment calls untested;
   this slice closes the denied-then-granted-then-foreground direction
   (DoD item 6) but not this reverse one. Left out deliberately, not
   overlooked — it's the same "no in-session heartbeat" tradeoff as the
   rest of this item, and a future heartbeat slice (Combine's
   `Timer.publish` merged with connection state — see Scope → Out item 1)
   is the natural place to pick it up.

> **Rule for agent:** stay inside this scope. If something out of scope
> blocks you, stop and flag it — don't silently expand scope to route
> around it.

## Interface / Data Contract

Illustrative — shape to argue about before writing the real thing, per
CONTRIBUTING.md's doc-comment item 6. Each snippet below changes existing
code; numbered comments mark the change points, elaborated in the list
right after — see CONTRIBUTING.md § Documentation style, "Annotating a
code snippet that changes existing code."

**`ios/Buttons/Networking/Connection.swift`** — new method on the
existing `DesktopConnection`:

```swift
/// Actively confirms the socket is still alive — `isConnected` alone can
/// be stale after the app was backgrounded, since iOS may suspend the
/// task without ever delivering a receive failure. Flips `isConnected`
/// to `false` on a failed/timed-out ping.
func isConnectionAlive(timeout: Duration = .seconds(3)) async -> Bool {
    // 1. guard against a torn-down/never-opened socket
    guard isConnected, let task = webSocketTask else { return false }
    // 2. single-resume ping, wrapped for an async caller
    let isAlive = await withCheckedContinuation { continuation in
        task.sendPing { error in continuation.resume(returning: error == nil) }
    }
    // 3. timeout still needed — sketch only, see elaboration below
    // TODO: race the continuation above against `timeout` (e.g. a
    // `TaskGroup` with a `Task.sleep` competitor).
    // 4. corrects the stale flag isConnectionAlive exists to catch
    if !isAlive { isConnected = false }
    return isAlive
}
```

1. `guard isConnected, let task = webSocketTask` — load-bearing, not
   defensive boilerplate: `sendPing` on a `nil`/already-cancelled task
   throws/crashes on some OS versions.
2. `withCheckedContinuation` — resumes exactly once by construction, so no
   `DispatchWorkItem`/`didComplete` guard is needed the way an
   `@escaping` completion-handler version would require. `sendPing` has
   no native `async` overload (confirmed — Implementation Notes), so this
   wrapper is required, not a placeholder to drop later. **Not the same
   gap as `send(_:)`/`receive()`, which do have `async throws` overloads**
   ([Apple's docs](https://developer.apple.com/documentation/foundation/urlsessionwebsockettask/send(_:))
   list them under "Sending Data," `sendPing` separately under "Sending
   Ping Frames" with no async form) — and not interchangeable with this
   probe either way: `send(_:)` writes a data/text frame the desktop's
   app code would have to know to ignore, where `sendPing` is a
   protocol-level control frame any compliant peer auto-pongs with no
   app involvement. Don't substitute one for the other.
3. A hung ping must not hang this call forever — not solved here, just
   flagged; confirm the exact timeout-racing pattern against this Swift
   version before implementing, don't invent one ad hoc.
4. `isConnected = false` on failure is what lets both call sites below
   (the new foreground probe and the existing `onChange(of:
   connection.isConnected)`) key off the same flag instead of two.

**`ios/Buttons/Networking/Pairing.swift`** — `PairingSession` gains
actor isolation, a derived guard, and an `async` reconnect:

```swift
// 1. class-level: main-actor isolation added
@MainActor
@Observable
final class PairingSession {
    private(set) var lastError: String?
    private(set) var autoReconnectState: AutoReconnectState = .idle

    // 2. new — in-flight guard, derived from existing state
    var isReconnectInFlight: Bool { autoReconnectState == .searching }

    // ... pair(scannedQR:), reconnect(stored:endpoint:) unchanged

    // 3. signature: async, replaces the internal Task { } wrapper
    //    slice 07 had inside this function
    func attemptAutoReconnect(discovery: DesktopDiscovery) async {
        discovery.start()
        // 4. new — dedupe guard, placed after start(), not before
        guard !isReconnectInFlight, let stored = PairingStore.load() else { return }
        autoReconnectState = .searching
        // ... unchanged poll loop: 20x/250ms discovery.endpoint(forDeviceId:)
        //     lookup, reconnect() on match, autoReconnectState = .notFound
        //     if the loop runs out
    }
}
```

1. `@MainActor` — closes a pre-existing bug: the poll loop mutates
   `@Observable` state off-main today, nothing isolates it. Prerequisite
   for guard 4 to be race-free, not a style choice — see Implementation
   Notes for the Swift-language-mode detail this depends on.
2. `isReconnectInFlight` — derives from `autoReconnectState` instead of a
   separate stored flag, so there's one source of truth for both call
   sites in `RootView` (next snippet) that need it.
3. `async` — lets the whole foreground chain (probe → reconnect) be one
   `await` sequence in `RootView` instead of a callback; the function
   itself is now the async context, so the `Task { }` it used to spawn
   internally moves to each caller instead.
4. Guard ordering is deliberate: restarting the browse via `discovery
   .start()` is what recovers from a Local-Network-denied-then-granted
   permission change (DoD item 6), and that has to happen even when a
   reconnect poll is already in flight — moving `start()` below this
   guard would silently break that recovery path. See Implementation
   Notes for the one residual cost this ordering accepts.

**`ios/Buttons/ButtonsApp.swift`** — `RootView` gains scene-lifecycle
state, and its existing drop-handler adapts to `attemptAutoReconnect`
going `async`:

```swift
@State private var hasAttemptedReconnect = false
// 1. new — scene lifecycle plus a one-shot latch
@Environment(\.scenePhase) private var scenePhase
@State private var wasBackgrounded = false

var body: some View {
    Group { /* ... */ }
        .onAppear(perform: attemptReconnectIfPaired)
        .onChange(of: connection.isConnected) { wasConnected, isConnected in
            if wasConnected, !isConnected {
                // 2. wrapped in Task — attemptAutoReconnect is now async
                Task { await session.attemptAutoReconnect(discovery: discovery) }
            }
        }
        // 3. new — foreground probe, only on a real background round-trip
        .onChange(of: scenePhase) { old, new in
            if new == .background { wasBackgrounded = true }
            guard new == .active, wasBackgrounded else { return }
            wasBackgrounded = false
            Task {
                if !(await connection.isConnectionAlive()) {
                    await session.attemptAutoReconnect(discovery: discovery)
                }
            }
        }
}

// ... activeProfile, attemptReconnectIfPaired() unchanged
```

1. `scenePhase`/`wasBackgrounded` — `didBecomeActiveNotification`
   (`PairingView`'s own trigger, left as-is there) can't distinguish
   "returned from background" from a transient interruption like Control
   Center; both fire it identically. `scenePhase` exposes `.background`
   as a distinguishable case, which is the actual reason to switch
   triggers — but a bare `(old, new)` match on `.background → .active`
   isn't reliable alone (a Control Center pull produces `.active →
   .inactive → .active`, and iOS may route the real case through
   `.inactive` too), so the latch is the mechanism, not a fallback.
2. `Task { await ... }` — mechanical follow-on from `attemptAutoReconnect`
   going `async` in the previous snippet; this call site predates this
   slice and must wrap the call or the build breaks.
3. New `onChange` — probes the socket (`isConnectionAlive`) rather than
   trusting a possibly-stale `isConnected`, and calls
   `attemptAutoReconnect` only on a confirmed drop. `isReconnectInFlight`
   (previous snippet, annotation 2) is what keeps this from double-firing
   against item 2 above when both observe the same drop.

## Implementation Notes

1. **`@MainActor` on `PairingSession` (Interface / Data Contract,
   annotation 1) is a prerequisite for the dedupe guard to be race-free,
   not a style choice.** Under Swift 6 strict concurrency the existing
   off-main mutation in the poll loop (`Pairing.swift`'s
   `Task { autoReconnectState = ... }`, non-isolated today) is a compile
   error; under Swift 5 language mode it's a silent race the guard would
   otherwise inherit. Confirm which language mode this target builds
   under before implementing — it changes whether this is "fix a bug" or
   "fix a bug the compiler already caught."
2. **Foreground during an active pairing attempt does get interrupted —
   confirmed on device, kept as a known v1 limitation, not fixed.**
   `attemptAutoReconnect` fires whenever `!isConnected` (a fresh pair in
   progress hasn't set it yet either), and if a previously-paired desktop
   is live on the LAN, `reconnect()` calls `connection.connect
   (toBonjourEndpoint:)`, which overwrites the QR scan's own
   `pairCompletion`/`webSocketTask` in `DesktopConnection` — there's only
   one of each. See DoD item 4 for the exact failure mode this produces
   (not a hang; a silent stale-Keychain result) and why it's deferred
   rather than fixed for v1.
3. **Simulator can't test the real suspend/resume socket behavior** — the
   backgrounding-then-foreground path needs a real device (lock the
   phone, wait, unlock) per DoD item 2 below.
4. **Residual cost of the guard-ordering decision** (Interface / Data
   Contract, `PairingSession` annotation 4): a rapid double-trigger tears
   down and rebuilds the `NWBrowser` under a running poll loop, and the
   poll reads `discovery.discovered`, which `start()` doesn't clear — a
   brief window where the poll sees stale results from the torn-down
   browser. Not addressed here; flagged for awareness, not a blocker.
5. **`sendPing` has no `async` overload — confirmed, not assumed.**
   `NSURLSession.h` declares only
   `sendPingWithPongReceiveHandler:(void (^)(NSError *))` — no
   `NS_SWIFT_ASYNC_NAME`, unlike e.g. `getTasksWithCompletionHandler:`
   just above it in the same header — and `swiftc -typecheck` against a
   bare `task.sendPing()` call confirms the importer generates no
   automatic `async throws` bridge either: only the completion-handler
   form resolves. (Checked against the macOS SDK/toolchain — Swift
   6.2.4 — not the iOS one directly, but `URLSessionWebSocketTask` is the
   same cross-platform Foundation type; re-check if `xcodebuild` disagrees
   once this actually builds against the iOS SDK.) The full
   `isConnectionAlive` snippet above `-typecheck`s clean as written — the
   `withCheckedContinuation` wrapper stays, `isAlive` really is `Bool`
   (confirms the earlier reasoning about `sendPing`'s callback shape vs.
   `withCheckedContinuation`'s inferred return type).
6. **One thing still to verify before writing code, not during:** the
   real `scenePhase` transition sequence on device — confirm the
   `wasBackgrounded` latch (Interface / Data Contract's `RootView`
   snippet) actually catches a real background return; a bare
   `.background → .active` match alone is known-insufficient (a Control
   Center pull produces `.active → .inactive → .active`, and iOS may
   route the real case through `.inactive` too). No static check settles
   this one — needs the real device pass in DoD items 1-2.
7. **Not a wrapper: three `Task { await attemptAutoReconnect(...) }` call
   sites, kept separate on purpose.** Each is the explicit boundary
   between a SwiftUI sync callback and async work — a
   `startAutoReconnect()` wrapping the `Task { }` would hide that
   boundary, give one operation two names, and block reaching in for
   cancellation later (`URLSession` doesn't wrap `data(for:) async` in a
   fire-and-forget `startData(for:)` either). Only two of the three sites
   are even alike (`onAppear`, `onChange(of: connection.isConnected)` —
   both "callback observed a condition"); the `scenePhase` site is a
   two-step sequence (`isConnectionAlive` then a conditional reconnect) a
   wrapper couldn't absorb without also wrapping the probe. **A real,
   separate cleanup exists for the `onAppear` site only:** `.task {
   await session.attemptAutoReconnect(discovery: discovery) }` in place
   of `.onAppear(perform: attemptReconnectIfPaired)` would make
   `hasAttemptedReconnect` redundant (`isReconnectInFlight` already
   guards re-entry) and add automatic cancel-on-disappear. Not done here
   — it changes launch semantics (once-per-appearance vs.
   once-per-launch, and a mid-poll view teardown would now cancel instead
   of finish) that this slice's DoD doesn't cover. Own follow-up, own DoD
   item ("launch still reconnects exactly once; a mid-poll teardown
   doesn't strand state"), not a tidy-up to fold in here.

## Definition of Done

1. [x] Mid-session: kill the desktop app (or disconnect its Wi-Fi) while
       the phone is foregrounded and connected, background the phone,
       bring it back — phone silently reconnects once the desktop is back,
       without a relaunch.
2. [x] Real device: lock the phone for >30s while connected, unlock —
       either still connected (socket survived) or silently reconnects
       within the existing `~5s` poll window, no user action needed.
3. [x] Foregrounding while genuinely still connected does not visibly
       flicker to `PairingView` or interrupt `DeckView`.
4. [x] **Revised from the original wording** — foregrounding mid-QR-scan
       *does* fire auto-reconnect, and it can win a race against the QR
       pair for `DesktopConnection`'s single `pairCompletion`/
       `webSocketTask` slots. Accepted for v1, but precisely: this only
       triggers with a previously-paired desktop D live on the LAN while
       scanning a different desktop C's QR — squarely `07c`'s Out item 2/3
       territory (single stored credential, no multi-device support). The
       actual failure mode isn't a visible hang (`isConnected` flips true
       regardless of which response wins the `pairCompletion` slot, so
       `RootView` always moves off `PairingView`) — it's that if D's
       reconnect resolves the slot first, C's later `PairResponse` fires
       its completion on `nil`, so `PairingStore.save()` for C never runs.
       Live session is C; Keychain still holds D. The next drop searches
       for D, not C, and fails into `NotFound` with no error surfaced.
       Deferred, not fixed — single-desktop v1 doesn't hit this without
       deliberately keeping two desktops live to test it.
5. [x] **Verified by construction, not by manual test** — no interleaving
       point exists to double-fire through. The guard
       (`autoReconnectState == .searching`) is read-then-set synchronously
       before `attemptAutoReconnect`'s first `await`, and both call sites
       are `@MainActor`-isolated, so there's no point between "check" and
       "set" where a second caller's check can land. Manual testing
       can't distinguish this from "got lucky" — this is the actual proof.
6. [x] Local Network denied at launch → tap "Open Settings" → grant →
       return to app: browse restarts, `isLocalNetworkDenied` clears, and
       reconnect succeeds without a relaunch. Closes the gap
       `Discovery.swift`'s `isLocalNetworkDenied` comment flags as
       untested ("since `start()` isn't currently re-invoked on
       app-foreground") — after this slice, it is.

## Rollback

Revert `ButtonsApp.swift`'s new `onChange(of: scenePhase)`,
`Connection.swift`'s `isConnectionAlive`, and `Pairing.swift`'s
`@MainActor`/`async`/`isReconnectInFlight` changes — no persisted-state or
wire-format change, so a plain revert is safe with no migration to undo.
