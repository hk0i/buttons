**Implements:** `01. Architecture Overview.edd.md`, Testing & Rollout Plan step 0
— a spike, not a shippable vertical slice.
**TL;DR:** Prove desktop mDNS-advertise + iOS mDNS-discover + a two-way WebSocket
message exchange works on a real LAN across two physical devices, and prove a QR
code can be rendered from a Tauri-less Rust CLI — both throwaway, deleted once
proven.

---

## Scope

**In:**
- **Desktop** (standalone `cargo run` binary, no Tauri):
  - mDNS-advertises a service, reusing the EDD's `_streamdeck._tcp.local` naming
    (§5.1) for realism.
  - Renders a QR code to the terminal (Unicode block QR) encoding a placeholder
    payload (device ID + address) — proves the generation technique in isolation,
    not wired to an actual scan-to-pair flow in this POC.
  - Runs a minimal WebSocket server. Once a client connects, sends it an
    `"enable"` message.
  - Logs to stdout whatever message it receives back from the client.
- **iOS** (minimal SwiftUI app):
  - Local Network permission handling (`NSLocalNetworkUsageDescription` +
    `NSBonjourServices` in Info.plist) — confirming this flow actually works is
    itself part of what's being tested.
  - Discovers the desktop via `NWBrowser` (no manual IP entry).
  - One `Button`, labeled "Send It!", **disabled** until the desktop's `"enable"`
    message arrives over the WebSocket connection.
  - On tap, sends a fixed message (e.g. `"Send It!"`) to the desktop.

This exercises the channel in both directions — desktop→mobile (enable) and
mobile→desktop (button press) — mirroring the real protocol's `config_sync` and
`button_press` roles (EDD §5.2) without needing the schema itself.

**Out:**
- Protobuf/schema — plain UTF-8 strings only, no JSON/protobuf envelope.
- QR *scanning* on iOS — generation is tested standalone in this POC.
- Real pairing/auth/token exchange.
- Tauri, or any UI beyond the one button.
- Reconnect logic, retries, or error handling beyond what's needed to observe
  success or failure.
- Persistence of any kind.

## Interface / Data Contract

Deliberately not a real schema — plain strings, since testing the schema isn't
the point here:

| Message | Direction | Payload |
|---|---|---|
| (mDNS advertisement) | D→M | Service type `_streamdeck._tcp.local`, instance name |
| (QR, terminal-only) | — | Placeholder string: device ID + `IP:port` |
| `"enable"` | D→M, over WebSocket | Fixed string, sent once on connect |
| `"Send It!"` | M→D, over WebSocket | Fixed string, sent on button tap |

## Implementation Notes

- iOS: `Network` framework's `NWBrowser` for discovery, `URLSessionWebSocketTask`
  for the connection — the same APIs the real EDD design calls for (§5.1/5.2), so
  this POC genuinely tests the intended approach, not a shortcut.
- Rust QR rendering: `qrcode` crate's Unicode renderer
  (`render::unicode::Dense1x2`) prints a scannable code directly to stdout — no
  image viewer needed.
- Confirm the iOS Local Network permission prompt appears and that discovery
  proceeds correctly once granted.
- If anything here surprises you (permission quirks, mDNS flakiness, etc.), note
  it — it likely needs to feed back into EDD §5.1 before Slice 1 starts.

## Definition of Done

- [ ] Desktop binary runs, advertises via mDNS, and prints a terminal QR code.
- [ ] iOS app discovers the desktop service via mDNS — no manual IP entry.
- [ ] iOS Local Network permission prompt appears; once granted, discovery and
      connection proceed.
- [ ] On WebSocket connect, desktop sends `"enable"` and the iOS button becomes
      tappable.
- [ ] Tapping "Send It!" delivers a message the desktop visibly logs.
- [ ] Confirmed on **two real physical devices** on the same LAN — not two
      processes on one machine. That's the actual point of this POC.

**Verification:**
```
# terminal 1
cd spikes/network-poc/desktop && cargo run
# then run the iOS app on a physical device on the same LAN,
# confirm the button enables, tap it, confirm the desktop logs the message
```

> **Rule for agent:** run the verification above on real hardware before
> declaring this done. Report the actual observed output, not an assumption
> that it passed.
