**Implements:** `01. Architecture Overview.edd.md`, Testing & Rollout Plan step 0
— a spike, not a shippable vertical slice.
**TL;DR:** Prove desktop mDNS-advertise + iOS mDNS-discover + a two-way WebSocket
message exchange works on a real LAN across two physical devices, prove the
protobuf toolchain works across Rust/Swift, and prove a QR code can be rendered
from a Tauri-less Rust CLI — all throwaway, kept in the repo afterward only as an
unmaintained reference.

---

## Scope

**In:**
1. **Desktop** (standalone `cargo run` binary, no Tauri):
   1. mDNS-advertises a service using `_buttonspoc._tcp.local` — deliberately
      distinct from the EDD's real service type (§5.1, `_buttons._tcp.local`) so
      this throwaway spike is never mistaken for, or collides with, the real
      product's future mDNS presence on the same LAN. Otherwise mirrors the EDD's
      approach for realism.
   2. Renders a QR code to the terminal (Unicode block QR) encoding a placeholder
      payload (device ID + address) — proves the generation technique in isolation,
      not wired to an actual scan-to-pair flow in this POC.
   3. Runs a minimal WebSocket server. Once a client connects, sends it a `Ping`.
   4. Logs to stdout whatever `Ping` it receives back from the client.
2. **iOS** (minimal SwiftUI app):
   1. Local Network permission handling (`NSLocalNetworkUsageDescription` +
      `NSBonjourServices` in Info.plist) — confirming this flow actually works is
      itself part of what's being tested.
   2. Discovers the desktop via `NWBrowser` (no manual IP entry).
   3. A `Text` view displaying the `text` field of the `Ping` received from
      desktop.
   4. One `Button`, **disabled** until that `Ping` arrives.
   5. On tap, sends a `Ping` back whose `text` is `"Reply To: <original
      message>"`, substituting the desktop's original message text.
3. **Protobuf toolchain:** a single trivial message, `Ping { text: string }`, in
   `/spikes/network-poc/proto/`, generated for both Rust (`prost`) and Swift
   (`swift-protobuf`) and sent as WebSocket binary frames. This is a throwaway
   message purely to prove the codegen/build toolchain works end-to-end across
   both languages — it is **not** the real schema, which still waits for EDD
   roadmap step 6, informed by the UI work in steps 2-5.

This exercises the channel in both directions — desktop→mobile (enable-style
`Ping`) and mobile→desktop (button-press-style `Ping`) — mirroring the real
protocol's `config_sync` and `button_press` roles (EDD §5.2) without needing the
real schema.

**Out:**
1. The real button/grid/Profile schema — only a throwaway `Ping` message exists
   here.
2. QR *scanning* on iOS — generation is tested standalone in this POC.
3. Real pairing/auth/token exchange.
4. Tauri, or any UI beyond the one button.
5. Reconnect logic, retries, or error handling beyond what's needed to observe
   success or failure.
6. Persistence of any kind.

> **Rule for agent:** stay inside this scope. If something out of scope blocks
> you, stop and flag it — don't silently expand scope to route around it.

## Interface / Data Contract

```protobuf
// spikes/network-poc/proto/ping.proto — throwaway, not the real schema
syntax = "proto3";
message Ping {
  string text = 1;
}
```

| Message | Direction | Payload |
|---|---|---|
| (mDNS advertisement) | D→M | Service type `_buttonspoc._tcp.local`, instance name |
| (QR, terminal-only) | — | Placeholder string: device ID + `IP:port` |
| `Ping` | D→M, WebSocket binary frame | Sent once on connect; `text` is shown in the iOS `Text` view and enables the button |
| `Ping` | M→D, WebSocket binary frame | Sent on button tap; `text` is `"Reply To: <desktop's original message>"` |

## Implementation Notes

1. iOS: `Network` framework's `NWBrowser` for discovery, `URLSessionWebSocketTask`
   for the connection — the same APIs the real EDD design calls for (§5.1/5.2), so
   this POC genuinely tests the intended approach, not a shortcut.
2. Rust QR rendering: `qrcode` crate's Unicode renderer
   (`render::unicode::Dense1x2`) prints a scannable code directly to stdout — no
   image viewer needed.
3. Protobuf codegen: `prost-build` in the desktop's `build.rs`; the
   `swift-protobuf` Xcode plugin (or a manual `protoc --swift_out` build step) on
   iOS. Send `Ping` messages as WebSocket **binary** frames, not text — confirm
   both `tokio-tungstenite` and `URLSessionWebSocketTask` handle binary frames
   correctly, since the real protocol will need this too.
4. Confirm the iOS Local Network permission prompt appears and that discovery
   proceeds correctly once granted.
5. If anything here surprises you (permission quirks, mDNS flakiness, protobuf
   toolchain friction), note it — it likely needs to feed back into EDD §5.1/5.2
   before Slice 1 starts.

## Definition of Done

1. [x] Desktop binary runs, advertises via mDNS, and prints a terminal QR code.
2. [x] `Ping` compiles and generates working types on both Rust and Swift.
3. [x] iOS app discovers the desktop service via mDNS — no manual IP entry.
4. [x] iOS Local Network permission prompt appears; once granted, discovery and
       connection proceed.
5. [x] On WebSocket connect, desktop sends a `Ping`; its `text` appears in the
       iOS `Text` view and the button becomes tappable.
6. [x] Tapping the button sends a `Ping` with `text` = `"Reply To: <original
       message>"`, which the desktop visibly logs.
7. [x] Confirmed on **two real physical devices** on the same LAN — not two
       processes on one machine. That's the actual point of this POC.

**Verification:**

```
cd spikes/network-poc/desktop && cargo run

```
