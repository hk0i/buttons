**Implements:** `01. Architecture Overview.edd.md`, Testing & Rollout Plan step 3.
**TL;DR:** Turn the static mock grid (slice 2) into a real, editable, persisted
grid — add/remove/reorder buttons, assign each an ordered Tier 1 action array,
and actually execute those actions on press — proving the action engine and
editing UX end-to-end before any networking or schema work (EDD §5.2 sequencing).

---

## Scope

**In:**
- Add / remove / reorder buttons via the desktop UI.
- Per-button icon (text/emoji glyph, per slice 2's [[mockButtons.ts]] convention)
  and label editing.
- Per-button ordered action array (0+ actions), each one of the Tier 1 set (PRD
  Use Cases):
  - Launch an application or run a local script.
  - Simulate a keyboard shortcut/hotkey — multi-key macro strings, including the
    F13–F24 range.
  - Media key control (play/pause, mute, next/previous track).
- Pressing a configured button in the desktop UI runs its action array in order —
  this is what "proves the action engine end-to-end" per the roadmap, since no
  mobile/network press path exists yet.
- Persistence: plain Rust struct + `serde_json` to a local JSON config file
  (EDD §5.3), loaded on startup, saved on every edit. Survives an app restart.

**Out:**
- Folders, pages, Profiles — roadmap step 4.
- Networking, protobuf, mobile changes of any kind — roadmap steps 5+.
- Stateful/live-updating buttons (`state_push`) — roadmap step 9.
- Tier 2+ actions (OBS, audio mixer) — roadmap step 13.
- Animated icons — PRD allows them eventually, not required here; static
  text/emoji glyph only, same as slice 2.
- Light/dark theme switching — still deferred (slice 2's note stands).
- Variable-size (cell-spanning) buttons — open question in the EDD, undecided.

> **Rule for agent:** stay inside this scope. If something out of scope blocks
> you, stop and flag it — don't silently expand scope to route around it.

## Interface / Data Contract

Still provisional/frontend-and-desktop-only — informs but does not commit the
future `.proto` schema (EDD §5.2). Rust and TS shapes must mirror each other
field-for-field.

```rust
#[derive(Serialize, Deserialize, Clone)]
#[serde(rename_all = "camelCase")]
struct Button {
    id: String,
    label: Option<String>,
    icon: Option<String>, // text/emoji glyph — see slice 2's note
    actions: Vec<Action>,
}

#[derive(Serialize, Deserialize, Clone)]
#[serde(tag = "type", rename_all = "camelCase")]
enum Action {
    LaunchApp { path: String },
    Hotkey { keys: Vec<String> },       // e.g. ["cmd", "shift", "s"]; F13-F24 by name
    MediaKey { key: MediaKeyKind },
}

#[derive(Serialize, Deserialize, Clone)]
#[serde(rename_all = "camelCase")]
enum MediaKeyKind { PlayPause, Mute, NextTrack, PreviousTrack }
```

JSON crossing the Tauri IPC boundary and the config file thus uses camelCase
throughout (`"type": "launchApp"`, `"key": "playPause"`) — matches idiomatic
TS/JSON, not raw Rust identifier casing. Convention: same pattern
`tauri-specta` defaults to for Rust↔TS type generation.

Tauri commands:

| Command | Signature | Purpose |
|---|---|---|
| `list_buttons` | `() -> Vec<Button>` | Load current grid on app start |
| `save_button` | `(button: Button) -> ()` | Create or update one button |
| `delete_button` | `(id: String) -> ()` | Remove a button |
| `reorder_buttons` | `(order: Vec<String>) -> ()` | Persist new button order |
| `press_button` | `(id: String) -> Result<(), String>` | Execute the button's action array in order |

## Implementation Notes

- Config file location: use Tauri's `app_handle.path().app_config_dir()` (no
  new dependency needed) rather than hand-rolling a path — matches
  `gg.pekk.buttons` (`tauri.conf.json` identifier, fixed to the `com.buttons.*`
  → real-domain convention alongside iOS/Android).
- Drag-and-drop reorder: native HTML5 drag-and-drop is enough — no need for a
  library at this scale (single flat list, no folders yet).
- `press_button` in this slice is purely a local desktop-UI affordance (click a
  button in the editor to test it fires) — it is *not* the real cross-device
  press path, which arrives in roadmap step 8 over `button_press`.
- **Keep the Rust core Tauri-agnostic — architecture principle, applies
  beyond this slice.** `config.rs`, `actions.rs`, and any future protocol/
  networking code (roadmap step 6+) should take plain Rust types (`&Path`,
  our own `Button`/`Action` structs), never `tauri::AppHandle` or
  `#[tauri::command]`, in their own signatures. Confine Tauri-specific glue
  (resolving `app_config_dir()`, the `#[tauri::command]` wrappers themselves)
  to a thin adapter layer in `lib.rs` that just calls into the core. Motivated
  by the egui spike (`00b. egui Desktop UI Spike.spec.md`) — if this
  discipline holds, a future Tauri→egui migration is a UI-only rewrite
  (Svelte frontend + the thin Tauri glue get replaced; `config.rs`/
  `actions.rs`/protocol code port over untouched). `config.rs` now takes
  `&Path` (not `&AppHandle`) — fixed before `actions.rs` landed, per this
  principle. `actions.rs` itself is also fully Tauri-agnostic (plain Rust,
  `enigo` + `std::process::Command`, no Tauri types) — only `press_button`'s
  thin wrapper in `lib.rs` touches Tauri.
- **macOS Accessibility permission, not yet handled — flagged, not fixed
  here.** `enigo` posts synthetic keyboard/media-key events via `CGEvent`,
  which requires the Accessibility permission (System Settings → Privacy &
  Security → Accessibility). The first real hotkey/media-key press triggers
  the system prompt — worse than a typical iOS-style inline alert, since
  granting it often means a trip to System Settings and relaunching the app.
  Genuinely disruptive if that first trigger happens mid-stream from a phone
  press, not during setup. Apple's HIG permission guidance ("request in
  context, when the feature is used") is platform-general, not iOS-specific
  — but literal just-in-time here means the worst timing, since presses are
  phone-triggered and unpredictable. Better reading: treat *configuring* a
  hotkey/media-key action in the desktop editor as the contextual moment,
  and request/trigger the permission then — not deferred to the first real
  press. Not implemented in this slice; logged so it isn't lost before
  roadmap step 8 (real button-press round trip) makes the timing risk real.
  **Also worth exploring:** a "soft capture" of permission state — check
  whether the grant was later revoked and be able to re-prompt on demand,
  similar to patterns common on mobile. Unclear whether/how this carries to
  macOS's Accessibility model (`AXIsProcessTrusted()` can be polled, but
  macOS doesn't have an iOS-style in-app re-request flow) — genuinely
  unresearched, may not be necessary. Noted, not investigated further here.
- **Hotkey editor UX: typing key names as free text (`cmd, shift, s`) is a
  known-bad interim UI, shipped as-is for this slice.** Two distinct
  follow-ups, worth keeping separate since they're different-sized:
  - **Key-capture widget** (UI-only) — a field that records actual keys
    pressed instead of typed names. Fixes the immediate UX gap, no data
    model change needed (still produces the same `keys: Vec<String>`).
  - **Key *sequences*** (press A, release, then press B — as opposed to a
    single simultaneous chord) — `Hotkey`'s current shape only represents
    "hold these together," not a sequence. Supporting real sequences likely
    needs a new `Action` variant or a restructured `Hotkey`, not just a UI
    change — a data-model question, not only a widget. Needs its own design
    thought before committing to a shape (per the multi-action array
    precedent: get this right up front rather than retrofit later).

## Definition of Done

- [x] Add a new button from the desktop UI; it appears in the grid.
- [x] Edit a button's icon and label.
- [x] Delete a button.
- [x] Reorder buttons via drag-and-drop.
- [x] Assign an ordered action array to a button, mixing all three Tier 1
      types (launch app, hotkey, media key) — confirmed: a 3-action button
      (Launch Calculator → Cmd+Space → Mute) ran all three in order. F13
      confirmed separately (no default macOS binding, so no visible effect,
      but the Test button's success response confirms the key press itself
      went through) — covers the PRD's F13-F24 callout, modulo the
      documented F21-F24 macOS gap.
- [x] Clicking **Test** in the editor executes a button's actions, with
      observable real effects — confirmed for all three action types
      (Launch App, Hotkey, Media Key), individually and combined in one
      array. Note: execution is triggered from a **Test** button inside the
      editor, not by clicking the grid tile itself (tile click opens the
      editor; matches this slice's Implementation Notes). Two real bugs
      found and fixed along the way: `actions::run` aborted the whole array
      on the first failed action instead of running the rest (fixed to
      aggregate errors instead); `parse_key` only recognized modifiers,
      F13-F24, and single characters — common named keys (space, enter, tab,
      arrows, F1-F12) were simply missing, not a permissions issue as first
      suspected.
- [x] Quit and relaunch the app — grid/config persists exactly as left,
      confirmed with the real 3-action button attached (not just empty
      buttons as in an earlier check).

## Rollback

Low-medium risk — first slice writing to local disk and executing real OS-level
side effects (process spawn, key injection). If the config file format changes
mid-implementation and corrupts earlier test data, delete the app's config file
(path from Implementation Notes) and relaunch — no real user data exists yet,
so this is safe to do freely during development.
