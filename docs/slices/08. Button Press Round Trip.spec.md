## Scope

**In:**

1. `wire.proto`: `ButtonPress` (M→D) and `ActionResult` (D→M) messages,
   added to `Envelope`'s oneof.
2. Desktop: on `ButtonPress`, look up the button by id in the active
   Profile, run its actions via the existing `actions::run`, reply with
   `ActionResult`.
3. Mobile: tapping a `.actions` button (currently a documented no-op in
   `PageGrid.handleTap`) sends `ButtonPress`, fires an immediate local
   haptic, and reflects the `ActionResult` when it arrives.
4. Mobile: the pressed cell flashes its background — success green on
   `ok: true`, failure red on `ok: false` — using two placeholder `Color`
   constants (below), not a real design-token palette.

**Out:**

1. `state_push` (stateful/toggle buttons) — step 9.
2. `profile_switch` — step 10.
3. Live nav-cursor mirroring (`nav_cursor`/`nav_request`, EDD §5.2 Open
   Question 3) — designed but not implemented on the wire; not this slice.
4. The edit-churn `config_sync` debounce/dirty-check (EDD §5.2 Corollary
   #2) — unrelated push path, not touched here.
5. Any toast/notification system for the result — the flashed cell is
   enough for v1.
6. **The real design-token/color palette.** This slice adds exactly two
   placeholder `Color` values (success/failure) for its own use, not a
   palette system — no theming, no dark-mode-specific tuning beyond
   whatever `Color(hex:)`/asset-catalog default falls out, no other UI
   restyled to use them. Flagged in code for replacement once a real
   palette lands.

> **Rule for agent:** stay inside this scope. If something out of scope
> blocks you, stop and flag it — don't silently expand scope to route around
> it.

## Interface / Data Contract

`protocol/wire.proto` — new messages, flat tag numbering on `Envelope`
(don't restart at 1, same rule `buttons.proto`'s `Button` oneof already
follows):

```proto
message Envelope {
  string protocol_version = 1;
  oneof message {
    PairRequest pair_request = 2;
    PairResponse pair_response = 3;
    ConfigSync config_sync = 4;
    // 1. new — M→D press
    ButtonPress button_press = 5;
    // 2. new — D→M reply
    ActionResult action_result = 6;
  }
}

message ButtonPress {
  string button_id = 1;
}

message ActionResult {
  // 3. echoed, not a request id — see below
  string button_id = 1;
  bool ok = 2;
  optional string error = 3;          // present iff !ok — mirrors PairResponse
}
```

1. `button_press`, M→D — the tapped button's id, nothing else this slice
   (no nav cursor, no timestamp).
2. `action_result`, D→M — one reply per press.
3. **Correlation is the echoed `button_id`**, not a request/sequence id —
   sufficient for v1's single-paired-device, unique-ids-within-a-Profile
   setup. Mobile matches an incoming `ActionResult` to the cell it just
   pressed by id.

Field naming follows `PairResponse`'s existing precedent exactly (`ok` +
`optional string error` present iff `!ok`) — not a new `success` field;
CLAUDE.md's wire-naming rule (in-code name == wire name) plus "match an
established pattern already on this same wire" leaves nothing to invent
here.

**Mobile-side signatures** — pinned here, not left to the executing turn,
because each one settles a decision the prose alone left ambiguous:

```swift
// Connection.swift
// 1. new — wraps the result so repeats still trigger .onChange
struct ActionResultEvent: Equatable {
    let result: Buttons_ActionResult
    let sequence: Int
}
// 2. new — replaces a bare Buttons_ActionResult?
private(set) var lastActionResult: ActionResultEvent?

// PageGrid.swift / ButtonGrid.swift / DeckButton.swift
// 3. new — not a bare Bool, see below
enum PressFeedback { case success, failure }

struct PageGrid: View {
    let page: Buttons_Page
    @Binding var isFolderOpen: Bool
    // 4. new param — needed to send the press
    let connection: DesktopConnection

    @State private var pressedButtonId: String?
    @State private var feedback: PressFeedback?
    // 5. new — .sensoryFeedback's trigger value
    @State private var pressTrigger = 0
}

struct ButtonGrid: View {
    let buttons: [Buttons_Button]
    var onTap: (Buttons_Button) -> Void
    // 6. new — passes PageGrid's feedback state through to DeckButton
    var feedback: (buttonId: String, state: PressFeedback)?
}

struct DeckButton: View {
    let button: Buttons_Button
    // 7. new — defaults nil so the existing #Preview still compiles
    var feedback: PressFeedback? = nil
}
```

1. `DesktopConnection` publishes the result wrapped with a `sequence`
   counter, not the bare `Buttons_ActionResult`. `swift-protobuf` makes
   `Buttons_ActionResult` `Equatable`, and `.onChange(of:)` only fires on
   *inequality* — pressing the same button twice with the same outcome
   would otherwise produce a value-identical second result and no second
   flash. `sequence` (bumped on every incoming `ActionResult`, matching
   result or not) guarantees the observer always sees a change.
2. Replaces the plain `Buttons_ActionResult?` sketched in Note 6 below —
   same "single in-flight value, no Combine/AsyncStream" reasoning, just
   wrapped per point 1.
3. `PressFeedback` (not `result: Bool?`) two-case enum — `nil`/`.success`/
   `.failure` as a `Bool?` is exactly the ambiguous-tri-state read site
   CLAUDE.md's boolean-naming rule exists to prevent; a named enum reads
   at the call site instead of requiring the reader to know what `true`
   means here. Also keeps `DeckButton`'s param off a bare, unprefixed
   `Bool`.
4. `PageGrid` takes `connection` (not `ButtonGrid` — `PageGrid` is where
   the tap is dispatched and where the pending-press/feedback state
   already lives per Note 6).
5. `pressTrigger` is the `.sensoryFeedback(.impact, trigger:)` driver —
   incremented on every `.actions` tap (including repeats of the same
   button), since `.sensoryFeedback` also only fires on a changing
   `trigger` value.
6. `ButtonGrid` gains a pass-through param — `DeckButton` is built inside
   `ButtonGrid`'s own `ForEach`, so `PageGrid`'s feedback state has to
   cross that boundary too, not just reach `PageGrid` itself.
7. Defaults to `nil` — every existing `#Preview` in `PageGrid.swift`,
   `ButtonGrid.swift`, and `DeckButton.swift` constructs these types
   positionally; `DeckButton`'s default keeps its own preview compiling
   unchanged. `PageGrid`/`DeckView`/`ButtonGrid`'s previews take the new
   non-optional `connection`/`feedback` params explicitly — construct a
   bare `DesktopConnection()` (no pairing, all stored properties already
   have defaults) rather than making the whole app depend on an optional
   connection just to keep three preview blocks short.

## Implementation Notes

1. **Haptic fires on tap, not on result.** EDD §5.5's Testing note ("tap →
   `button_press` + haptic feedback → reflect `action_result`") is more
   specific than the roadmap line's "shows result + haptic feedback" and
   is the better UX: immediate physical confirmation the press registered,
   independent of round-trip latency. Use SwiftUI's `.sensoryFeedback`
   modifier (iOS 17+ deployment target, no `UIImpactFeedbackGenerator`
   needed) — this is this codebase's first haptic, so the choice is
   recorded here rather than picked ad hoc mid-edit.
2. **`actions::run` is blocking** (`Enigo::new`, `Command::spawn`) and must
   not run inline inside `server.rs`'s `tokio::select!` loop — wrap in
   `tokio::task::spawn_blocking`, `.await` the `JoinHandle`, then send the
   result. Directly relevant to §5.4's sub-50ms round-trip target.
3. **Re-load `config.rs`'s `Config` from disk on every `ButtonPress`**,
   rather than trusting the snapshot loaded once at connect
   (`server.rs:167`). The file is small (§5.3's own sizing argument for why
   it's a flat JSON file at all) and this removes a staleness invariant
   instead of maintaining it — same reasoning §5.2 already used to justify
   syncing the whole `Config` on `config_sync`. An edit made on desktop
   after connect must be visible to the very next press, not just the next
   reconnect.
4. **Button lookup lives in `config.rs`, over `config::Config`/`Action`,
   not the proto types.** `actions::run` already takes `&[config::Action]`.
   Add something like:
   ```rust
   impl Config {
       /// Depth-first search over the active Profile's Pages (and nested
       /// folders) for a Button by id. Returns its actions, or `None` if
       /// the id doesn't exist (deleted since connect, or from a stale
       /// mobile cache) or isn't an `.actions` button.
       pub fn actions_for_button(&self, button_id: &str) -> Option<&[Action]> { ... }
   }
   ```
   A recursive walk: Profile (matched by `active_profile_id`) → Pages →
   Buttons, descending into `FolderContent.buttons` wherever a Button's
   content is a folder.
5. **Unknown button id is `ActionResult { ok: false, error: Some(...) }`,
   not a dropped frame or a panic.** Covers the stale-mobile-cache case
   directly (point 3's second half) — a real, user-visible failure mode
   once config-push debouncing (out of scope, EDD §5.2 Corollary #2) isn't
   built yet to keep mobile perfectly in sync.
6. **`DesktopConnection` exposes the result as `lastActionResult:
   ActionResultEvent?`** (pinned above, with the `sequence` field's
   repeat-press fix) — no Combine/AsyncStream needed for a single
   in-flight value. `PageGrid` reacts via `.onChange(of:)`, matches
   `result.buttonId` against `pressedButtonId`, sets `feedback` to
   `.success`/`.failure`, and clears both back to `nil` after a short
   fixed delay (e.g. 400ms) — no toast/queue system (Scope → Out).
7. **`DeckView` currently takes only `profile:` — add `connection:
   DesktopConnection` as a second plain `let`**, same shape as
   `PairingSession`'s existing `connection` dependency in
   `ButtonsApp.swift`. Pass it down to `PageGrid`, which owns the tap
   dispatch and feedback state (pinned above) and passes `feedback`
   through `ButtonGrid` to the matching `DeckButton`.
8. **Result flash: two placeholder `Color` constants, not the real
   palette.** `StatusColors.swift` defines `Color.actionSuccess` (green)
   and `Color.actionFailure` (red) as literal stand-ins — `Color(red:
   green: blue:)` or a plain SwiftUI system color (`.green`/`.red`) is
   fine, whichever reads better against `.quaternary`'s default look.
   Doc-comment both with a note that they're placeholders for a real
   design-token palette, not a finished decision. `DeckButton` switches
   its `background(...)` fill on `feedback` (pinned above): `.success` →
   `.actionSuccess`, `.failure` → `.actionFailure`, `nil` → today's
   `.quaternary`.

## Definition of Done

1. [ ] Tapping an `.actions` button on mobile (paired, connected) fires
   haptic feedback immediately.
2. [ ] The desktop actually runs the button's actions (observable effect —
   e.g. an app launches, a hotkey fires) and the pressed cell on mobile
   flashes green on success / red on failure shortly after.
3. [ ] Pressing a button whose id doesn't exist in the active Profile
   (simulate via a stale mobile cache, or `websocat` with a garbage id)
   returns `ActionResult{ok: false}` and does not crash or hang the
   connection.
4. [ ] Editing `buttons.json` on disk, then pressing a button whose action
   just changed, runs the *new* action — no stale-snapshot reload of the
   app or the connection needed.
5. [ ] `protocol/verify-kotlin`'s existing build still compiles against
   the updated `wire.proto` (schema-lock check, same as slice 07 DoD 15).
