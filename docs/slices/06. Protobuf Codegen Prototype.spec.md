**Implements:** `01. Architecture Overview.edd.md`, Testing & Rollout Plan step 6.
**TL;DR:** Write the real `.proto` schema in `/protocol` — translating the
`Config`/`Profile`/`Page`/`Button` shape slices 2-5 already validated in both
the desktop and iOS UIs — then prove it generates and compiles in all three
target languages (Rust/`prost`, Swift/`swift-protobuf`, Kotlin/`wire`,
per the EDD roadmap) with a standalone round-trip check in each. Nothing in
`/desktop` or `/ios` depends on the generated types yet, and Android has no
app to depend on it either — that's step 7 (and step 12 for Android), per the
EDD's own sequencing ("before depending on it in a cross-device slice").

---

## Scope

**In:**

1. **`protocol/buttons.proto`** — the data-model schema only: `Config`,
   `Profile`, `Page`, `Button` (with its `content` `oneof` inline — no
   separate `ButtonContent` message, see finding 5), `Action`,
   `MediaKeyKind`. Translates `desktop/src/lib/types/button.ts` and
   `ios/Buttons/Models/ButtonModel.swift`'s top-level fields (see Interface)
   — not a literal 1:1 structural mirror where protobuf idiom pulls the
   other way (finding 5); both are scaffolding this schema outlives.
2. **Rust codegen + round-trip check** — a standalone `protocol/verify-rust`
   crate: `prost-build` compiles `buttons.proto` at build time, `cargo test`
   constructs a `Config` literal (mirroring the shape of
   `ios/Buttons/Data/MockConfig.swift`, just enough to exercise every message
   and the `oneof`s), encodes it, decodes it back, asserts equality — plus
   two dedicated presence cases (see Implementation Notes item 4): one
   `Button` with `label` absent and another with `label: Some("")`,
   asserting the two stay distinguishable after the round trip; and one
   `Button` with its `content` `oneof` set to `.back` (a real, empty
   message) versus one constructed with the `oneof` left unset, asserting
   those two also stay distinguishable — `.back` means "no action payload,"
   not "no case selected."
3. **Swift codegen + round-trip check** — a standalone `protocol/verify-swift`
   SPM package: a committed, manually-regenerated `buttons.pb.swift` (SwiftPM
   has no protoc build step), `swift test` doing the same round-trip
   (including both presence cases, item 2 above) via the generated
   `Buttons_Config`.
4. **Kotlin codegen + round-trip check** — a standalone `protocol/verify-kotlin`
   Gradle project using `com.squareup.wire` (provisional pick — see
   Implementation Notes item 6; not a final decision, revisitable at step 12
   when the real Android slice starts), generating at build time like
   `prost`, same round-trip (including both presence cases) via `gradle test`.
5. All three `verify-*` packages depend only on their protobuf runtime
   (`prost`/`swift-protobuf`/`wire`) — no Tauri, no SwiftUI, no Compose, no
   networking.

**Out:**

1. **Wire envelope messages** — `pair_request`, `pair_response`,
   `config_sync`, `button_press`, `action_result`, `state_push`,
   `profile_switch`, the step-7 `nav_request`/`nav_cursor` pair, and the
   `protocol_version` field (EDD §5.2) — none of these were validated by a UI
   yet; they're designed alongside the real connection code at step 7, not
   guessed at here.
2. **Which Kotlin library ships in the real Android app.** `verify-kotlin`
   picks `com.squareup.wire` provisionally to satisfy the EDD roadmap's "all
   three languages" requirement at schema-lock time (§ Files to Touch item 4)
   — it proves the *schema* is expressible in a Kotlin toolchain, not that
   `wire` is the final choice. The EDD's Open Question ("`wire` vs.
   `protobuf-kotlin`") stays open and gets decided for real at step 12, once
   there's Android UI code to weigh the choice against.
3. **Repointing `desktop/src-tauri/src/config.rs` or
   `ios/Buttons/Models/ButtonModel.swift` / `Data/MockConfig.swift` / any view
   code onto the generated types.** Both apps keep their existing
   hand-written models unchanged. This is deliberate, not an oversight — see
   Implementation Notes.
4. Exported-Profile JSON, binary wire encoding, or any actual message
   send/receive — no transport exists yet (step 7+).
5. `.proto` package/message versioning strategy beyond a plain `buttons`
   package — versioning is the wire envelope's job (`protocol_version`,
   step 7), not this data-shape schema.

> **Rule for agent:** stay inside this scope. If something out of scope
> blocks you, stop and flag it — don't silently expand scope to route around
> it.

## Interface / Data Contract

```proto
syntax = "proto3";
package buttons;

message Config {
  repeated Profile profiles = 1;
  string active_profile_id = 2;
}

message Profile {
  string id = 1;
  string name = 2;
  repeated Page pages = 3;
}

message Page {
  string id = 1;
  optional string name = 2;
  repeated Button buttons = 3;
}

message Button {
  string id = 1;
  optional string label = 2;
  optional string icon = 3; // emoji/text glyph, per slice 2's convention
  oneof content {          // flat numbering space with id/label/icon above —
    ActionList actions = 4; // don't restart the oneof at 1, it'd collide
    FolderContent folder = 5;
    Back back = 6;
  }
}
message ActionList { repeated Action actions = 1; } // doubled key on purpose — see finding 6
message FolderContent { repeated Button buttons = 1; } // buttons[0] is always Back
message Back {} // no payload; pops one nav level

message Action {
  oneof action {
    LaunchApp launch_app = 1;
    Hotkey hotkey = 2;
    MediaKeyKind media_key = 3;
  }
}
message LaunchApp { string path = 1; }
message Hotkey { repeated string keys = 1; } // e.g. ["cmd","shift","s"]; F13-F24 by name

enum MediaKeyKind {
  MEDIA_KEY_KIND_UNSPECIFIED = 0;
  MEDIA_KEY_KIND_PLAY_PAUSE = 1;
  MEDIA_KEY_KIND_MUTE = 2;
  MEDIA_KEY_KIND_NEXT_TRACK = 3;
  MEDIA_KEY_KIND_PREVIOUS_TRACK = 4;
}
```

**Deliberate step-6 evidence this slice produces** (not caveats — findings,
same convention as slice 5):

1. **`oneof` can't hold a `repeated` field directly** — `Button.content`'s
   `actions` and `folder` cases needed wrapper messages (`ActionList`,
   `FolderContent`) that don't exist in either hand-written union
   (`button.ts`'s `ButtonContent`, `ButtonModel.swift`'s `ButtonContent`
   enum). Purely a protobuf mechanical constraint, not a shape change —
   `prost`/`swift-protobuf` both unwrap it back to something ergonomic (a
   `Vec<Action>`/`[Action]` one level down), but the schema itself carries
   the extra message. This is the *only* forced wrapper — see finding 5 for
   why `Button.content` isn't wrapped in its own containing message.
2. **proto3 enums require a zero value.** Neither `MediaKeyKind` union (TS
   string-literal type, Swift `enum` with 4 cases) has an "unspecified" case
   — `MEDIA_KEY_KIND_UNSPECIFIED = 0` is new, forced by the wire format, not
   the domain. `SCREAMING_SNAKE_CASE` values prefixed with the enum name
   follow the proto3 style guide (protobuf enum values aren't C++-scoped to
   their enum, so an unprefixed `MUTE` would collide package-wide the moment
   a second enum wants that name).
3. **`optional` on `Page.name` / `Button.label` / `Button.icon`** — confirms
   slice 5's finding: nil-vs-empty-string is load-bearing (the `.back` cell's
   fallback fires on nil), so these are marked `optional` to get explicit
   field presence instead of proto3's default empty-string-means-absent
   behavior. **Not yet confirmed what shape each language generates for
   it** — `prost` is known to give `Option<String>`, but `swift-protobuf`'s
   usual pattern for proto3 `optional` is a non-optional `var label: String`
   plus generated `hasLabel`/`clearLabel()`, not Swift `String?` as slice 5
   assumed; `wire`'s shape isn't checked either. This is exactly what the
   round-trip test's presence case (see Scope/DoD) is for — report what each
   toolchain actually generates rather than assuming `String?`/`Option<String>`
   uniformly. If `swift-protobuf` does give `hasLabel`-style presence, iOS's
   eventual repoint (step 7) won't be the clean `String?` slice 5 assumed —
   flag that as a new finding when confirmed, don't quietly paper over it.
4. **`Back {}` is a local empty message, not `google.protobuf.Empty`** —
   avoids pulling in the well-known-types import for one marker type, and
   keeps all three `verify-*` packages dependency-free beyond their protobuf
   runtime.
5. **`Button.content`'s `oneof` is inline on `Button`, not wrapped in a
   separate `ButtonContent` message.** Earlier draft mirrored `button.ts`'s
   `Button.content: ButtonContent` field-for-field, giving `Button` a
   `ButtonContent content = 4` field whose only job was holding the `oneof`.
   Reverted: a `oneof` *is* protobuf's tagged union already — it needs no
   containing message to be one, and `ButtonContent` carried no fields of
   its own and nothing else referenced it. `google.protobuf.Value` follows
   the same pattern (`oneof kind` inline on `Value`), reaching for a
   separate message (`ListValue`) only where `repeated` forces one — exactly
   `ActionList`/`FolderContent`'s situation here (finding 1), not
   `ButtonContent`'s. **Why the deviation from `button.ts` is deliberate,
   not an oversight:** `button.ts` and `ButtonModel.swift` are both explicit
   scaffolding — slice 5's Type-lifecycle section says outright that both
   get superseded once the generated types land. The `.proto` schema is the
   one hand-maintained model meant to outlive them and lock as the real
   wire/export shape (EDD §5.2) — fidelity to a throwaway mirror shouldn't
   drive a frozen schema where the two pull in different directions. Scope
   item 1's "field-for-field" still holds at the top level (`Config`/
   `Profile`/`Page`/`Button`'s own fields); it doesn't extend to keeping a
   structurally pointless intermediate message.
6. **`ActionList.actions` doubles the (now-inline) `oneof` field name on
   purpose.** proto3 canonical JSON of `Button{actions: ActionList{actions:
   [...]}}` renders as `{"actions":{"actions":[...]}}` — doubled, still a
   little ugly, one level shallower than before flattening. Considered
   renaming the inner field (`items`) to dodge it; reverted — real protobuf
   schemas keep the wrapper's field named after what it holds regardless of
   outer collisions (`google.protobuf.ListValue { repeated Value values =
   1; }` is the same shape), so `items` would've been the non-idiomatic
   choice, trading a cosmetic export-JSON nit for a name that doesn't say
   what it holds. The remaining one level of doubling (`actions` →
   `actions`) is what `repeated`-in-`oneof` genuinely forces (finding 1) —
   nothing left to flatten out.

## Implementation Notes

1. **`protoc-gen-swift` isn't installed by default** — `protoc` is (checked:
   `/opt/homebrew/bin/protoc`), but the Swift plugin isn't. `brew install
   swift-protobuf` gets both the plugin and a runtime — but whatever version
   brew currently ships, almost certainly not the spike's pinned `1.38.1`.
   Generated files carry a runtime-version check that's a **build error**,
   not a silent mismatch, so pin `Package.swift`'s `SwiftProtobuf` to
   `protoc-gen-swift --version`'s actual output, checked at generation time —
   don't copy the spike's pin blind.
2. **Swift codegen is a manual, committed step — Rust's isn't.** `prost-build`
   regenerates from `buttons.proto` on every `cargo build` automatically
   (`build.rs`); SwiftPM has no protoc build-plugin step wired up here, so
   `buttons.pb.swift` can silently drift from `buttons.proto` if the schema
   changes without rerunning `protoc --swift_out=Sources/ButtonsProto/Generated
   buttons.proto` by hand. Same posture as slice 5's `xcodegen generate`
   after every new file — a manual regen step, not automatic — which is why
   the DoD has an explicit no-drift check for it.
3. **Why standalone `verify-*` packages instead of wiring into
   `desktop`/`ios` directly:** the EDD is explicit that step 6 proves
   generation/compilation "before depending on it in a cross-device slice."
   Touching `desktop/src-tauri`'s `Cargo.toml`/`build.rs`/`config.rs` or
   `ios/Buttons`'s `project.yml`/model files now would start that dependency
   early, in a slice that has no cross-device code to justify it yet, and
   would mean either running two Config representations side by side in the
   same app or a half-finished swap — worse than a clean, isolated prototype
   this slice's name already says it is. The real swap is real work
   (`config.rs`'s `serde_json` (de)serialization moves to protobuf's own
   JSON mapping per EDD §5.2; iOS's `ButtonModel.swift`/`MockConfig.swift`
   and every view that reads them get repointed at `Buttons_*` types) —
   sized as its own step-7-adjacent slice, not folded in here.
4. **Round-trip check, not a full fuzz/property test — but two presence
   cases are required.** One hand-built `Config` literal exercising every message
   type and both `oneof`s (at least one `.actions` button, one `.folder`
   button nested one level, one `.back`, all four `MediaKeyKind` values
   across different buttons) is enough to prove the toolchain works
   end-to-end in all three languages — this slice is about the codegen
   pipeline, not exhaustive schema testing. Two required exceptions (see
   Scope item 2): a `label`-absent vs. `label: ""` pair (finding 3) — a plain
   equality assertion on the whole `Config` wouldn't catch a toolchain that
   silently collapses "absent" into empty string, which is the exact
   property `optional` exists to protect — and a `.back`-set vs.
   `oneof`-unset pair, for the same class of reason: `prost` types the
   `oneof` as `Option<ButtonContentOneof>` (name illustrative), so a decoded
   `Button` can legitimately have no case set at all, distinct from a case
   set to the empty `Back{}` message. Both are presence checks a bare
   equality assertion on a "happy path" `Config` wouldn't exercise.
5. Package name is plain `buttons`, no version segment (e.g. not
   `buttons.v1`) — see Scope, Out, item 5.
6. **`wire` is the name of Square's Kotlin library** (`com.squareup.wire`) —
   distinct from this project's own "wire protocol"/"wire format"
   terminology used throughout the EDD. Referred to here by its fully
   qualified package to avoid confusion.
7. **Open, empirically-checked risk: `wire`'s `oneof` representation.**
   Whether `wire` generates a sealed-class (exhaustive-`when`) shape for
   `Button.content`/`Action.action` or older nullable-fields-with-
   manual-exclusivity depends on the plugin version and config — not
   confirmed here. `verify-kotlin`'s round-trip test is exactly where this
   gets discovered; if it lands on the nullable-fields shape, note it as a
   finding (parallel to the `oneof`-can't-hold-`repeated` finding above) —
   don't silently work around it by hand-adding sealed wrappers in this
   prototype.
8. **`verify-kotlin` uses system `gradle`, not a committed wrapper.** No
   `gradlew`/`gradlew.bat`/`gradle/wrapper/` in Files to Touch — adding the
   wrapper is more files for a package this slice keeps deliberately minimal
   (§ Scope). Verification assumes a `gradle` binary on `PATH`; if the
   executing agent doesn't have one, install it first rather than silently
   generating a wrapper as a workaround — that's a scope decision to flag,
   not make unilaterally.

## Definition of Done

- [ ] `protocol/buttons.proto` exists with the shapes in Interface — no
      hand-added fields beyond what's listed there.
- [ ] `cd protocol/verify-rust && cargo test` passes — round-trip `Config`
      encodes and decodes back equal via `prost`, including both presence
      cases (label-absent vs. `label: ""`, and `.back`-set vs. `oneof`-unset
      — Impl Note 4).
- [ ] `cd protocol/verify-swift && swift test` passes — same round-trip,
      including both presence cases, via the generated `Buttons_Config`.
- [ ] `cd protocol/verify-kotlin && gradle test` passes (system `gradle`, no
      committed wrapper — see Implementation Notes item 8) — same round-trip
      via `wire`'s generated Kotlin types. Note in Post-Implementation Notes
      whether `oneof` landed as sealed classes or nullable fields
      (Implementation Notes item 7), and what the `optional` fields'
      generated shape is (item 4/finding 3). Includes both presence cases
      too.
- [ ] `buttons.pb.swift` matches a fresh `protoc --swift_out=...` run against
      the committed `buttons.proto` — no drift between schema and generated
      file.
- [ ] `git diff --stat` shows changes only under `protocol/` and
      `docs/slices/`/`docs/01. Architecture Overview.edd.md` — nothing in
      `/desktop` or `/ios` touched.

## Rollback

Low risk — all three `verify-*` packages and `buttons.proto` are new, isolated
under `/protocol`, and nothing in `/desktop` or `/ios` references them. If any
toolchain doesn't cooperate, `git checkout protocol/` (or `rm -rf
protocol/verify-rust protocol/verify-swift protocol/verify-kotlin`) fully
reverts with no cross-cutting cleanup.
