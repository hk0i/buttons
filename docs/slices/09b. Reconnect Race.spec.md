**Implements:** `01. Architecture Overview.edd.md`; a bugfix to step 7/7d's
reconnect design, found live during step 9a verification.
**TL;DR:** `DesktopConnection.connect(...)` has no reentrancy guard — two
overlapping reconnect triggers (a dropped-connection retry and a
foreground-liveness retry can land close together) each start a fresh
`NetService`/`URLSessionWebSocketTask` without checking one's already in
flight. Both eventually authenticate as real, separate connections against
desktop, each evicting whichever is currently holding the slot — including
whichever one just won and is already showing `DeckView`. Symptom: the
app flickers between `DeckView` and `PairingView` on reconnect.

## Root Cause

**Status: unconfirmed.** The theory below explains a *plausible* race
(two same-process triggers overlapping) and the guard below closes it,
but it does not explain the actual observed repro — killing and
relaunching the app, a fresh process, which starts with no in-flight
attempt for any same-process guard to block. The original log (five
ports, each authenticating before the next evicts it) reads as a
**sequential drop→reconnect flap**, not concurrent racing sockets — see
Definition of Done for what's still open. The guard is kept regardless:
it's cheap, correct, and closes a real hole even if it isn't *the* hole
that produced the reported flicker.

`ButtonsApp.swift`'s `RootView` has two independent triggers that can each
call `PairingSession.attemptAutoReconnect`:

1. `.onChange(of: connection.isConnected)` — fires when a live connection
   drops.
2. `.onChange(of: scenePhase)` — fires on foreground-from-background, if
   `isConnectionAlive()` says the socket's dead.

`attemptAutoReconnect` derives its own dedupe guard
(`isReconnectInFlight`) from `autoReconnectState`, but flips that state
back to `.idle` *before* calling `reconnect()` — so by the time
`reconnect()`'s async chain (`NetService.resolve` → WebSocket handshake)
is still running, a second trigger sees `.idle` and starts its own
`reconnect()` call. `DesktopConnection.connect(toBonjourEndpoint:)` /
`connect(host:port:)` then unconditionally overwrite `netService` /
`webSocketTask` / `pendingToken` / `pairCompletion` with no check for an
attempt already in flight. Both keep resolving/handshaking; whichever one
authenticates *last* evicts whatever's currently holding desktop's
connection slot, even a session that already succeeded.

## Scope

**In:**

1. Both `connect(...)` overloads early-return if an attempt is already
   unresolved or a connection is already live — enforces "at most one
   socket exists," not "at most one socket wins." `pairCompletion != nil`
   is already the exact sentinel for "an attempt is in flight" (set at the
   top of a call, cleared only on success/failure/timeout), so no new
   state is needed.
2. `disconnect()` clears `pairCompletion`/`pendingToken` alongside what it
   already cancels — today's one call site (the timeout closure) already
   nils `pairCompletion` first, so this changes no current behavior, but
   without it any *future* caller of `disconnect()` (a manual "Disconnect"
   button, floated but unbuilt) would wedge the guard above permanently:
   `pairCompletion` staying non-nil with nothing left running to ever
   clear it.

**Out:**

1. Any generation-counter / cancel-and-replace machinery. A refused
   reconnect attempt against a now-stale endpoint blocks a good one for up
   to 10s (`scheduleTimeout`'s existing bound, unchanged) — acceptable for
   v1; don't build preemption to recover those seconds.
2. `@MainActor` on `DesktopConnection` — not needed. Both `connect(...)`
   call sites already live inside `PairingSession`, which is `@MainActor`
   (07d), so the guard's check-then-set is already race-safe.
3. `PairingSession.attemptAutoReconnect`'s own `isReconnectInFlight`
   coarse guard — left as-is, still a reasonable outer debounce; the real
   fix belongs at the connection layer that actually owns the socket
   (our SwiftUI rule: "a layer that owns a live connection is
   `@Observable` from the start," which already makes `DesktopConnection`
   the one place responsible for its own lifecycle).
4. `ButtonsApp.swift`'s two separate triggers — both are independently
   justified (documented inline: dropped-connection retry vs.
   foreground-liveness retry) and become harmless once `DesktopConnection`
   itself refuses a second concurrent attempt. Not touched.
5. Desktop's single-connection-slot eviction design (slice 07's
   `ConnSlot`) — correct as-is. The bug is mobile creating multiple real
   connections, not desktop mishandling one.

## Interface / Data Contract

```swift
// Connection.swift
// 1. new — the single gate both connect(...) overloads check before
// starting a second attempt.
private var isConnectingOrConnected: Bool { isConnected || pairCompletion != nil }

func connect(
    toBonjourEndpoint endpoint: NWEndpoint,
    token: String,
    onPairResult: ((PairResult) -> Void)? = nil
) {
    // 2. new — at most one socket exists at a time; a second concurrent
    // request is dropped, not queued or superseded.
    guard !isConnectingOrConnected else { return }
    guard case let .service(name, type, domain, _) = endpoint else {
        pairError = "not a Bonjour service endpoint"
        onPairResult?(.failure("not a Bonjour service endpoint"))
        return
    }
    pendingToken = token
    ...
}
```

The `connect(host:port:)` overload gets the identical guard as its first
line. `isConnectingOrConnected`, not a bare `isConnecting`, because the
guard must also reject a second call while already fully connected — a
name covering only the in-flight half would silently miss that case.

```swift
func disconnect() {
    pairTimeout?.cancel()
    pairTimeout = nil
    netService?.stop()
    webSocketTask?.cancel(with: .goingAway, reason: nil)
    isConnected = false
    // 1. new — without this, any caller of disconnect() while an attempt
    // is still unresolved leaves pairCompletion set with nothing left
    // running to ever clear it, wedging Note 1's guard permanently.
    pairCompletion = nil
    pendingToken = nil
}
```

1. `pairCompletion != nil` is the existing in-flight sentinel — set at the
   top of every `connect(...)` call, cleared exactly once by whichever of
   success/failure/timeout resolves first. No new stored field, only the
   computed property naming the combined condition.

## Implementation Notes

1. **Silently dropping a refused attempt is correct here, not a swallowed
   error** — the caller that lost the race (an `attemptAutoReconnect` that
   fired moments after another already started) has nothing broken to
   report; the attempt already in flight will itself resolve into success,
   failure, or the 10s timeout, and any of those three already drives
   `pairError`/`isConnected` for the UI to react to.
2. **Why this doesn't deadlock**: `scheduleTimeout()` runs at the top of
   every attempt that gets past the guard, and unconditionally clears
   `pairCompletion` after 10s regardless of what happens to the socket —
   so the guard can never stay closed longer than that, even against a
   `NetService.resolve` that never calls back at all.
