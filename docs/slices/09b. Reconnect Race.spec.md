**Implements:** `01. Architecture Overview.edd.md`; a bugfix to step 7/7d's
reconnect design, found live during step 9a verification.
**TL;DR:** `DesktopConnection.connect(...)` has no reentrancy guard — two
overlapping reconnect triggers (a dropped-connection retry and a
foreground-liveness retry can land close together) each start a fresh
`NetService`/`URLSessionWebSocketTask` without checking one's already in
flight. Both eventually authenticate as real, separate connections against
desktop, each evicting whichever is currently holding the slot — including
whichever one just won and is already showing `DeckView`. Symptom: the
app flickers between `DeckView` and `PairingView` on reconnect.

## Root Cause

**Two distinct bugs found in the same file, confirmed in this order:**

**1. Confirmed cause of the actual reported flicker — NetService
re-firing its resolve delegate.** A timestamped repro (`server.rs`'s new
`log_time()` output) showed four connections landing 88–995ms apart, each
fully authenticating before the next evicted it — a **sequential
drop→reconnect flap**, not concurrent racing sockets. The phone's own
screen showed the literal string `"invalid resolved address"` during one
flicker — `netServiceDidResolveAddress`'s own failure message when
`URL(string:)` rejects a resolved host (e.g. an unbracketed IPv6
link-local literal). `NetService.resolve(withTimeout:)` is documented to
call its delegate's resolve method more than once per resolve as
addresses arrive in separate batches — nothing in this code ever called
`.stop()` or cleared `netService` after acting on the first firing, and
neither failure branch cleared `pendingToken`. So: a first firing with
only an IPv6 address fails and reports the error the user saw, but leaves
`netService` and `pendingToken` both still set; a second firing moments
later, now with a good IPv4 address, runs `connectWebSocket(to:)`
*unguarded* and sends a real `PairRequest` with the still-valid
`pendingToken` — a second genuine connection, entirely outside
`connect(...)`, which is why Bug 2's guard (below) has no effect on it.
See Scope → In #3.

**2. A second, independent hole found first, while investigating —
`connect(...)` itself has no reentrancy guard.** `ButtonsApp.swift`'s
`RootView` has two triggers that can each call
`PairingSession.attemptAutoReconnect` close together (a dropped-connection
retry and a foreground-liveness retry); `attemptAutoReconnect` clears its
own dedupe flag *before* `reconnect()`'s async chain finishes, so a second
trigger can call `connect(...)` again while the first is still resolving.
Doesn't explain the kill-and-relaunch repro on its own — a fresh process
starts with no in-flight attempt for a same-process guard to block — but
it has its own concrete trigger, found separately: **unlocking the phone
after the socket died while backgrounded.** `scenePhase` → `.active`
calls `isConnectionAlive()`, which pings, fails, and sets `isConnected =
false`, then that same task falls through to call `attemptAutoReconnect`
directly — but that same `isConnected` flip *also* fires
`ButtonsApp.swift`'s separate `.onChange(of: connection.isConnected)`
handler, which calls `attemptAutoReconnect` again, independently. Two
calls from one unlock. Real repro requires the socket to actually be
dead when unlocking, not just backgrounded (a quick lock/unlock where the
connection survives never reaches `isConnectionAlive()`'s failure path).

## Scope

**In:**

1. Both `connect(...)` overloads early-return if an attempt is already
   unresolved or a connection is already live — enforces "at most one
   socket exists," not "at most one socket wins." `pairCompletion != nil`
   is already the exact sentinel for "an attempt is in flight" (set at the
   top of a call, cleared only on success/failure/timeout), so no new
   state is needed.
2. `disconnect()` clears `pairCompletion`/`pendingToken` alongside what it
   already cancels — today's one call site (the timeout closure) already
   nils `pairCompletion` first, so this changes no current behavior, but
   without it any *future* caller of `disconnect()` (a manual "Disconnect"
   button, floated but unbuilt) would wedge the guard above permanently:
   `pairCompletion` staying non-nil with nothing left running to ever
   clear it.
3. **Amended 2026-09-15 — the confirmed fix.** `disconnect()` also nils
   `netService` (previously only `.stop()`'d it, leaving the property
   still pointing at a stopped instance). Both `NetServiceDelegate`
   methods gain `guard sender === netService else { return }` at the top,
   and both failure branches in `netServiceDidResolveAddress` plus
   `didNotResolve` call `disconnect()` instead of manually clearing
   `pairTimeout`/`pairError`/`pairCompletion` inline — reusing it is what
   also clears `pendingToken` and `netService`, closing the exact gap that
   let a second delegate firing complete a real connection.

**Out:**

1. Any generation-counter / cancel-and-replace machinery. A refused
   reconnect attempt against a now-stale endpoint blocks a good one for up
   to 10s (`scheduleTimeout`'s existing bound, unchanged) — acceptable for
   v1; don't build preemption to recover those seconds.
2. `@MainActor` on `DesktopConnection` — not needed. Both `connect(...)`
   call sites already live inside `PairingSession`, which is `@MainActor`
   (07d), so the guard's check-then-set is already race-safe.
3. `PairingSession.attemptAutoReconnect`'s own `isReconnectInFlight`
   coarse guard — left as-is, still a reasonable outer debounce; the real
   fix belongs at the connection layer that actually owns the socket
   (our SwiftUI rule: "a layer that owns a live connection is
   `@Observable` from the start," which already makes `DesktopConnection`
   the one place responsible for its own lifecycle).
4. `ButtonsApp.swift`'s two separate triggers — both are independently
   justified (documented inline: dropped-connection retry vs.
   foreground-liveness retry) and become harmless once `DesktopConnection`
   itself refuses a second concurrent attempt. Not touched.
5. Desktop's single-connection-slot eviction design (slice 07's
   `ConnSlot`) — correct as-is. The bug is mobile creating multiple real
   connections, not desktop mishandling one.

> **Rule for agent:** stay inside this scope. If something out of scope
> blocks you, stop and flag it — don't silently expand scope to route around
> it.

## Interface / Data Contract

```swift
// Connection.swift
// 1. new — the single gate both connect(...) overloads check before
// starting a second attempt.
private var isConnectingOrConnected: Bool { isConnected || pairCompletion != nil }

func connect(
    toBonjourEndpoint endpoint: NWEndpoint,
    token: String,
    onPairResult: ((PairResult) -> Void)? = nil
) {
    // 2. new — at most one socket exists at a time; a second concurrent
    // request is dropped, not queued or superseded.
    guard !isConnectingOrConnected else { return }
    guard case let .service(name, type, domain, _) = endpoint else {
        pairError = "not a Bonjour service endpoint"
        onPairResult?(.failure("not a Bonjour service endpoint"))
        return
    }
    pendingToken = token
    ...
}
```

The `connect(host:port:)` overload gets the identical guard as its first
line. `isConnectingOrConnected`, not a bare `isConnecting`, because the
guard must also reject a second call while already fully connected — a
name covering only the in-flight half would silently miss that case.

```swift
func disconnect() {
    pairTimeout?.cancel()
    pairTimeout = nil
    netService?.stop()
    // 1. new — not just .stop(): a NetService can still deliver a queued
    // delegate callback after being stopped, and nil is what the
    // sender === netService guard below actually checks against.
    netService = nil
    webSocketTask?.cancel(with: .goingAway, reason: nil)
    isConnected = false
    // 2. new — without this, any caller of disconnect() while an attempt
    // is still unresolved leaves pairCompletion set with nothing left
    // running to ever clear it, wedging Note 1's guard permanently.
    pairCompletion = nil
    pendingToken = nil
}
```

1. `pairCompletion != nil` is the existing in-flight sentinel — set at the
   top of every `connect(...)` call, cleared exactly once by whichever of
   success/failure/timeout resolves first. No new stored field, only the
   computed property naming the combined condition.

**`NetServiceDelegate`'s two methods — the confirmed fix:**

```swift
extension DesktopConnection: NetServiceDelegate {
    func netServiceDidResolveAddress(_ sender: NetService) {
        // 1. new — NetService can call this more than once per resolve as
        // addresses arrive in separate batches; a firing for an instance
        // this connection has already stopped and forgotten (via
        // disconnect(), below or elsewhere) must not start a second real
        // connection.
        guard sender === netService else { return }
        let parsed = (sender.addresses ?? []).compactMap(Self.parseSocketAddress)
        guard let resolved = parsed.first(where: { $0.isIPv4 }) ?? parsed.first else {
            let message = "resolved service has no usable addresses"
            pairError = message
            pairCompletion?(.failure(message))
            // 2. new — disconnect(), not manual field-clearing: it also
            // nils netService/pendingToken, which is what actually
            // prevents a later firing on this same resolve (e.g. a good
            // IPv4 address arriving after a bad IPv6 one) from completing
            // a real connection with the stale token.
            disconnect()
            return
        }
        guard let url = URL(string: "ws://\(resolved.host):\(resolved.port)") else {
            let message = "invalid resolved address"
            pairError = message
            pairCompletion?(.failure(message))
            disconnect()
            return
        }
        netService?.stop()
        netService = nil
        connectWebSocket(to: url)
    }

    func netService(_ sender: NetService, didNotResolve errorDict: [String: NSNumber]) {
        guard sender === netService else { return }
        let message = "failed to resolve desktop: \(errorDict)"
        pairError = message
        pairCompletion?(.failure(message))
        disconnect()
    }
}
```

1. The success path only stops+nils `netService` manually, not the full
   `disconnect()` — it still needs `pairTimeout` running (until the real
   `PairResponse` arrives) and `pendingToken` set (for `sendPairRequest`).
   Only the two failure paths can afford the full teardown.

## Implementation Notes

1. **Silently dropping a refused attempt is correct here, not a swallowed
   error** — the caller that lost the race (an `attemptAutoReconnect` that
   fired moments after another already started) has nothing broken to
   report; the attempt already in flight will itself resolve into success,
   failure, or the 10s timeout, and any of those three already drives
   `pairError`/`isConnected` for the UI to react to.
2. **Why this doesn't deadlock**: `scheduleTimeout()` runs at the top of
   every attempt that gets past the guard, and unconditionally clears
   `pairCompletion` after 10s regardless of what happens to the socket —
   so the guard can never stay closed longer than that, even against a
   `NetService.resolve` that never calls back at all.
