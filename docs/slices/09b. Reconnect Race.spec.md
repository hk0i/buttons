**Implements:** `01. Architecture Overview.edd.md`; a bugfix to step 7/7d's
reconnect design, found live during step 9a verification.
**TL;DR:** `DesktopConnection.connect(...)` has no reentrancy guard — two
overlapping reconnect triggers (a dropped-connection retry and a
foreground-liveness retry can land close together) each start a fresh
`NetService`/`URLSessionWebSocketTask` without cancelling the other. Both
eventually authenticate as real, separate connections against desktop,
each evicting whichever is currently holding the slot — including
whichever one just won and is already showing `DeckView`. Symptom: the
app flickers between `DeckView` and `PairingView` on reconnect.

## Root Cause

`ButtonsApp.swift`'s `RootView` has two independent triggers that can each
call `PairingSession.attemptAutoReconnect`:

1. `.onChange(of: connection.isConnected)` — fires when a live connection
   drops.
2. `.onChange(of: scenePhase)` — fires on foreground-from-background, if
   `isConnectionAlive()` says the socket's dead.

`attemptAutoReconnect` derives its own dedupe guard
(`isReconnectInFlight`) from `autoReconnectState`, but flips that state
back to `.idle` *before* calling `reconnect()` — so by the time
`reconnect()`'s async chain (`NetService.resolve` → WebSocket handshake)
is still running, a second trigger sees `.idle` and starts its own
`reconnect()` call. `DesktopConnection.connect(toBonjourEndpoint:)` /
`connect(host:port:)` then unconditionally overwrite `netService` /
`webSocketTask` / `pendingToken` / `pairCompletion` with no check for an
attempt already in flight, and never cancel the one they're replacing.
The abandoned attempt keeps resolving/handshaking in the background;
whichever one authenticates *last* evicts whatever's currently holding
desktop's connection slot, even a session that already succeeded.

## Scope

**In:**

1. `DesktopConnection` gains a private monotonic `connectionAttempt: Int`,
   incremented at the top of both `connect(...)` overloads. Every async
   continuation that can outlive its attempt — `NetServiceDelegate`'s two
   methods, the `pairTimeout` `DispatchWorkItem`, `receiveLoop`'s
   `.failure` branch, `send`'s error branch — captures the attempt id at
   schedule time and no-ops if `self.connectionAttempt` has since moved
   on, instead of acting on stale state.
2. Both `connect(...)` overloads call `disconnect()` first if a previous
   attempt is still unresolved (`pairCompletion != nil`) or a connection
   is already live (`isConnected`) — cancels the old socket/timeout/
   `NetService` immediately rather than leaving it to resolve into a
   second real connection.

**Out:**

1. `PairingSession.attemptAutoReconnect`'s own `isReconnectInFlight`
   coarse guard — left as-is, still a reasonable outer debounce; the real
   fix belongs at the connection layer that actually owns the socket
   (our SwiftUI rule: "a layer that owns a live connection is
   `@Observable` from the start," which already makes `DesktopConnection`
   the one place responsible for its own lifecycle).
2. `ButtonsApp.swift`'s two separate triggers — both are independently
   justified (documented inline: dropped-connection retry vs.
   foreground-liveness retry) and become harmless once `DesktopConnection`
   itself can't run two attempts at once. Not touched.
3. Desktop's single-connection-slot eviction design (slice 07's
   `ConnSlot`) — correct as-is. The bug is mobile creating multiple real
   connections, not desktop mishandling one.

> **Rule for agent:** stay inside this scope. If something out of scope
> blocks you, stop and flag it — don't silently expand scope to route around

## Interface / Data Contract

```swift
// Connection.swift
final class DesktopConnection: NSObject {
    // 1. new — incremented at the top of both connect(...) overloads;
    // every attempt-scoped callback captures its value and checks it
    // before acting.
    private var connectionAttempt = 0
    ...
}
```

1. Plain `Int`, not a `UUID` — only used for equality against "am I still
   the current attempt," never persisted or logged; overflow isn't a
   practical concern for a value bumped once per user-triggered reconnect.

## Implementation Notes

Two guard mechanisms, not one, because the six call sites split into two
shapes: four are closures that can capture the counter directly; two are
`NetServiceDelegate` methods whose signature is fixed by the protocol, so
they compare instance identity against the live `netService` property
instead — equivalent, since both overloads always repoint that property
(directly or via `disconnect()`) before a new attempt's resolve is even
requested.

**Both `connect(...)` overloads — cancel-or-replace, then bump the
counter:**

```swift
func connect(
    toBonjourEndpoint endpoint: NWEndpoint,
    token: String,
    onPairResult: ((PairResult) -> Void)? = nil
) {
    guard case let .service(name, type, domain, _) = endpoint else {
        pairError = "not a Bonjour service endpoint"
        onPairResult?(.failure("not a Bonjour service endpoint"))
        return
    }
    // 1. new — an attempt still unresolved, or a live connection being
    // replaced, gets torn down before this one starts; disconnect()
    // cancels pairTimeout/netService/webSocketTask, so a stale delegate
    // or timeout callback has already lost its match by the time it fires.
    if pairCompletion != nil || isConnected { disconnect() }
    // 2. new
    connectionAttempt += 1
    pendingToken = token
    pairCompletion = onPairResult
    scheduleTimeout()
    let fullType = type.hasSuffix(".") ? type : "\(type)."
    let service = NetService(domain: domain, type: fullType, name: name)
    service.delegate = self
    netService = service
    service.resolve(withTimeout: 5)
}
```

The `connect(host:port:)` overload gets the identical two lines in the
same place, right before `pendingToken = token`.

1. Order matters: `disconnect()` runs *before* `connectionAttempt` bumps,
   so anything it cancels still belonged to the old generation — a
   `pairTimeout` work item cancelled here never even reaches its own
   staleness check below.

**`scheduleTimeout`'s `DispatchWorkItem` — closure captures the counter:**

```swift
private func scheduleTimeout(after seconds: TimeInterval = 10) {
    pairTimeout?.cancel()
    // 1. new — captured now, checked when the timeout actually fires
    let attempt = connectionAttempt
    let work = DispatchWorkItem { [weak self] in
        guard let self, self.connectionAttempt == attempt else { return }
        let message =
            "Couldn't reach Buttons desktop — check it's on the same network, and that Local Network access is allowed for this app in Settings"
        self.pairError = message
        self.pairCompletion?(.failure(message))
        self.pairCompletion = nil
        self.disconnect()
    }
    pairTimeout = work
    DispatchQueue.main.asyncAfter(deadline: .now() + seconds, execute: work)
}
```

**`send`'s error completion — same pattern:**

```swift
private func send(_ envelope: Buttons_Envelope) {
    // 1. new
    let attempt = connectionAttempt
    do {
        let json = try envelope.jsonString()
        webSocketTask?.send(.string(json)) { [weak self] error in
            guard let self, let error else { return }
            // 2. new
            guard self.connectionAttempt == attempt else { return }
            print("DesktopConnection: failed to send Envelope: \(error)")
            DispatchQueue.main.async {
                guard self.pairCompletion != nil else { return }
                self.pairTimeout?.cancel()
                self.pairTimeout = nil
                let message = Self.pairingFailureMessage(for: error)
                self.pairError = message
                self.pairCompletion?(.failure(message))
                self.pairCompletion = nil
            }
        }
    } catch {
        print("DesktopConnection: failed to encode Envelope: \(error)")
    }
}
```

**`receiveLoop`'s `.failure` branch — same pattern:**

```swift
private func receiveLoop() {
    // 1. new
    let attempt = connectionAttempt
    webSocketTask?.receive { [weak self] result in
        guard let self else { return }
        switch result {
        case .success(let message):
            self.handle(message)
            self.receiveLoop()
        case .failure(let error):
            // 2. new
            guard self.connectionAttempt == attempt else { return }
            print("DesktopConnection: receive error: \(error)")
            DispatchQueue.main.async {
                self.isConnected = false
                guard self.pairCompletion != nil else { return }
                self.pairTimeout?.cancel()
                self.pairTimeout = nil
                let message = Self.pairingFailureMessage(for: error)
                self.pairError = message
                self.pairCompletion?(.failure(message))
                self.pairCompletion = nil
            }
        }
    }
}
```

1. `.success` isn't guarded — a stale attempt's socket delivering a real
   message is already unreachable in practice (its `NetService` never got
   to `connectWebSocket`, since `disconnect()` cancelled it first), and
   even if it somehow did, routing a stray message through `handle(_:)`
   is harmless — the guard exists for the *failure* branch specifically
   because that's the one that mutates `isConnected`/`pairCompletion` and
   can wrongly fail the attempt that actually won.

**`NetServiceDelegate`'s two methods — identity check, not the counter:**

```swift
extension DesktopConnection: NetServiceDelegate {
    func netServiceDidResolveAddress(_ sender: NetService) {
        // 1. new — a superseded attempt's NetService is no longer the
        // instance stored on self; connect() already repointed
        // `netService` (via disconnect() or direct reassignment) before
        // this could fire for a real, still-current attempt.
        guard sender === netService else { return }
        let parsed = (sender.addresses ?? []).compactMap(Self.parseSocketAddress)
        ...
    }

    func netService(_ sender: NetService, didNotResolve errorDict: [String: NSNumber]) {
        // 2. new
        guard sender === netService else { return }
        ...
    }
}
```

1. Identity, not the counter, because these are delegate protocol methods
   — their signature is fixed by `NetServiceDelegate`, so there's no
   closure scope to capture `connectionAttempt` into at schedule time.
   `sender === netService` is the equivalent check: both overloads always
   repoint the `netService` property (directly, or via `disconnect()`)
   before a new attempt's `resolve` is even requested, so a callback for
   an old instance can no longer match the live property.

## Definition of Done

1. [ ] Rapidly backgrounding/foregrounding the app (or locking/unlocking)
   several times in a row while paired no longer produces more than one
   `server: … authenticated, holding the connection slot` line per real
   reconnect — no back-to-back eviction burst in desktop's console.
2. [ ] The app never visibly flickers to `PairingView` and back during a
   reconnect that ultimately succeeds.
3. [ ] A normal single reconnect (kill and relaunch the app) still works
   exactly as before — this is a concurrency guard, not a behavior change
   for the non-racing path.
