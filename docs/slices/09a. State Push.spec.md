## Scope

**In:**

1. `wire.proto`: `StatePush` (D→M, `repeated StateChange`) added to
   `Envelope`'s oneof.
2. Desktop: a broadcast `StatePushTx`, created once at startup, threaded
   through `server::run`/`handle_connection` (each connection
   subscribes) — same shape slice 08's `ConnSlot` established for
   per-connection plumbing, but broadcast rather than unicast (see EDD
   Open Question 8, Note 6, for why broadcast is correct even once N>1).
3. Desktop: the single shared flip path slice 09 built (real
   `ButtonPress` and `Test` alike) also broadcasts a `StatePush` after
   saving `switch_state.json` — **every successful flip, whatever
   triggered it**, not just the ones a press didn't already explain. One
   path, no branch on origin: simpler than special-casing "only
   broadcast when the actor isn't the same device that pressed," and at
   v1's N=1 a redundant confirmation to the pressing device's own
   optimistic guess is a no-op, not a bug.
4. Mobile: a `.statePush` case in `Connection.swift`'s `handle(envelope:)`
   — applies each `StateChange` in the batch to `isActiveByButtonId`
   unconditionally (overwrite, not toggle: this is authoritative
   correction, not another optimistic guess).
5. **Amended 2026-09-15** — Mobile: `DeckButton` renders a background tint
   when a `.switchContent` button's `isActive` is true — the generic
   "active" indicator slice 09's Out #4 reserved and named this slice as
   the natural place to pick up ("still available later if 09a ... ever
   wants an indicator"). Reads the same `isActive` already driving
   icon/label (`currentSwitchState`), so it's covered by the existing
   `applyOptimisticFlip`/`StatePush` paths with no new state to track.
   Desktop stays untouched — Out #2 still holds, this is mobile-only.

**Out:**

1. Any real Tier 1/2/3 integration writing into this path — step 13's
   work. This slice only wires the channel; `Test` is its only caller
   until then.
2. Any desktop-side UI change — slice 09's `switchStates.svelte.ts` store
   already updates the desktop's own preview via a local Tauri event;
   `StatePush` is purely the wire/mobile half.
3. Per-device unicast — `state_push` carries no per-recipient payload, so
   broadcast is correct at N=1 and stays correct past it (EDD Open
   Question 8, Note 6). Don't build a `ConnSlot`-style registry for this.

## Interface / Data Contract

`protocol/wire.proto` — new message, next free `Envelope` tag (already
pinned in EDD Open Question 8, Note 6 — repeated here as the canonical
copy for implementation):

```protobuf
message Envelope {
  string protocol_version = 1;
  oneof message {
    PairRequest pair_request = 2;
    PairResponse pair_response = 3;
    ConfigSync config_sync = 4;
    ButtonPress button_press = 5;
    ActionResult action_result = 6;
    // 1. new — unsolicited D→M, batched
    StatePush state_push = 7;
  }
}

message StatePush {
  repeated StateChange changes = 1;
}

message StateChange {
  string button_id = 1;
  bool is_active = 2;
}
```

1. `repeated`, not a single `{button_id, is_active}` pair — decided in
   EDD Open Question 8, Note 6: reshaping single→repeated later is a
   non-additive schema change, and there's a real case for batching (a
   future OBS scene-switch integration flips two buttons — old scene
   off, new scene on — as one external event, and must never render a
   frame where both or neither look active). One element costs nothing
   at today's N=1 caller.

**Desktop-side signatures:**

```rust
// server.rs
// 1. new — v1 has one connection; broadcast is the simplest thing
// that's still correct at N=1 and needs no rework past it (Scope → Out
// #3).
pub type StatePushTx = tokio::sync::broadcast::Sender<Vec<StateChange>>;
// 2. new — mirrors wire.proto's StateChange
pub struct StateChange {
    pub button_id: String,
    pub is_active: bool,
}
```

1. `StatePushTx` broadcasts, not unicasts — v1 has one connection, and
   broadcast needs no rework once that's no longer true (Scope → Out #3).
2. Sent as a `Vec<StateChange>` per broadcast, not one `StateChange` sent
   N times — the batching decision (Interface Note 1) only holds if the
   internal channel preserves "these changes happened together" as one
   value; sending them individually would let two changes interleave
   with an unrelated broadcast on a lagging receiver and reintroduce the
   torn-frame problem the `repeated` field exists to prevent.

**Mobile-side:**

```swift
// Connection.swift, handle(envelope:)
case .statePush(let push):
    // 1. new — overwrite, not toggle: this is a correction, not a guess
    for change in push.changes {
        isActiveByButtonId[change.buttonID] = change.isActive
    }
```

1. Overwrite unconditionally, same precedence rule slice 09 already
   states for `config_sync` — no "is my own optimistic flip newer" check.
   A `StatePush` this device caused itself (Scope → In #3's "every
   successful flip broadcasts") just confirms what `isActiveByButtonId`
   already says; harmless.

## Implementation Notes

1. **`handle_connection`'s third `tokio::select!` arm**, alongside
   `ws.next()` and `evict_rx` (slice 07's `ConnSlot` eviction):
   ```rust
   changes = state_push_rx.recv() => match changes {
       Ok(changes) => { let _ = send_envelope(&mut ws, state_push_envelope(changes)).await; }
       Err(tokio::sync::broadcast::error::RecvError::Lagged(_)) => {} // drop, not fatal
       Err(tokio::sync::broadcast::error::RecvError::Closed) => {}    // sender outlives the app; unreachable in practice
   }
   ```
   A lagging receiver drops old batches rather than blocking the
   sender — acceptable for a UI-refresh signal that's about to be
   superseded by whatever state is current anyway (same reasoning the
   generic design this slice replaces already used).
2. **The flip function's new last step is "send if anyone's listening,
   ignore if not"** — `StatePushTx::send` returns an error only when
   there are zero subscribers (no connection open), which is a normal,
   expected state, not a fault to log or retry.
