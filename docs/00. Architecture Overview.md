# Architecture Overview — Open-Source Stream Deck Alternative

**Author:** Gregory McQuillan
**Date:** 2026-09-04
**Status:** Draft

---

## Context and Scope

This project is an open-source alternative to the Elgato Stream Deck: a desktop app
that renders a grid of configurable, dynamically creatable action buttons, paired
with native mobile apps (iOS/Android) that act as a remote control surface mirroring
that grid — replacing a physical Stream Deck device with a phone. The central
technical problem this doc addresses is how the mobile app finds and connects to the
desktop app on the local network without the user manually entering an IP address,
and what stack keeps the desktop app cheap to run continuously in the background.

## Goals

- Discover and pair a mobile device with a desktop instance on the same LAN without
  manual IP entry.
- Keep the desktop app lightweight enough to run indefinitely in the background.
- Support a dynamically editable grid of buttons, each bound to a pluggable action.
- Ship as open source, with a sustainable path to funding mobile app store costs.

## Non-Goals (v1)

- Remote/off-LAN connectivity (phone on cellular, desktop on a different network).
  This requires a relay/signaling server for NAT traversal and is deferred.
- A plugin marketplace or third-party action ecosystem — the action engine should be
  designed to allow this later, but it's not built in v1.

## Design

### Stack Decisions

| Component | Choice | License |
|---|---|---|
| Desktop | Tauri (Rust backend + HTML/CSS/JS frontend) | GPLv3 |
| iOS | Native Swift/SwiftUI | MIT |
| Android | Native Kotlin/Jetpack Compose | MIT |
| Protocol | Shared JSON schema (docs only, no linked code) | MIT |

**Why Tauri over Electron:** Tauri uses the OS-native webview (WKWebView/WebView2/
WebKitGTK) instead of bundling Chromium, giving it a much smaller idle memory
footprint — important for an app that runs continuously in the background.

**Why Tauri over Qt/C++:** Qt with native QWidgets has no webview overhead at all and
can be marginally leaner at idle, but it has no strong first-party mDNS support —
integration would mean shelling out to `dns-sd`/Avahi/the Bonjour SDK per platform.
Rust's `mdns-sd` crate (pure-Rust, no OS Bonjour/Avahi dependency) plus the `tokio`
async ecosystem substantially de-risks the discovery and concurrent-connection-
handling work. The dynamic, reorderable button-grid editor is also considerably
cheaper to build in CSS Grid + JS drag-and-drop than in QWidgets/QML.

**Licensing:** GPLv3 (desktop) and MIT (mobile) are compatible here because the two
only ever communicate over a network protocol (WebSocket/JSON) — no linked or shared
code — so GPL's copyleft doesn't propagate across that boundary. Qt's LGPL would have
required either dynamic linking or a GPL license for the whole app to statically
link; since we're choosing GPL for the desktop app regardless, this is moot either
way. Mobile MIT + paid store distribution (source open, App Store/Play Store listing
paid) funds Apple/Google developer fees; the known tradeoff is that MIT permits
anyone to build and distribute the client for free themselves — accepted for now,
revisit only if it becomes an actual problem.

### Discovery and Pairing

1. **Discovery:** mDNS/DNS-SD. The desktop app advertises a service (e.g.
   `_streamdeck._tcp.local`) with an instance name and stable device ID on launch,
   via the `mdns-sd` crate. The mobile app browses for that service type using
   native APIs (`NWBrowser`/`NetServiceBrowser` on iOS, `NsdManager` on Android).
2. **Pairing:** mDNS alone proves reachability, not trust, so first-time pairing uses
   a QR-code handshake. The desktop app generates a one-time pairing token and shows
   it as a QR code (device ID, LAN address hint, token). The phone scans it and
   exchanges the token for a persistent per-device auth token (stored in Keychain on
   iOS, EncryptedSharedPreferences/Keystore on Android).
3. **Reconnect:** on later launches, the mobile app re-browses mDNS for the
   previously-paired device ID and reconnects using the stored token — no re-scan.

### Transport

Persistent WebSocket: `tokio-tungstenite` on the desktop server,
`URLSessionWebSocketTask` on iOS, `OkHttp`/`ktor-client` on Android. JSON messages,
versioned from day one (`protocol_version` field) since desktop and mobile releases
will inevitably drift out of sync.

Message types (sketch, to be formalized in a protocol doc):
- `pair_request` / `pair_response` — token exchange
- `config_sync` — desktop → mobile: full button grid state
- `button_press` — mobile → desktop: button ID
- `action_result` — desktop → mobile: success/failure/state update

### Components

**Desktop (`/desktop`, Rust + Tauri)**
- mDNS advertiser
- WebSocket server (pairing/auth, config sync, button press handling)
- Action engine: button ID → pluggable action (launch app/shortcut, run script,
  media key, HTTP webhook/OBS control), designed as a registry so new action types
  are additive
- Frontend: CSS Grid button editor with drag-and-drop reordering, live icon/label
  editing, talking to the Rust backend over Tauri's IPC (separate from the mobile
  WebSocket channel)

**Mobile (`/ios`, `/android`, native)**
- mDNS discovery + QR pairing + persistent reconnect
- Grid UI mirroring the synced button config (SwiftUI `LazyVGrid`, Compose
  `LazyVerticalGrid`)
- Button tap → `button_press` message → reflect `action_result`

### Repo Layout

```
/desktop        Tauri app (Rust + web frontend)   — LICENSE: GPLv3
/ios            Native SwiftUI app                — LICENSE: MIT
/android        Native Kotlin/Compose app         — LICENSE: MIT
/protocol       Shared JSON message schema + docs — LICENSE: MIT
/docs           Design docs (this doc and future ones)
```

## Alternatives Considered

- **Electron (desktop):** rejected — bundles Chromium, too heavy for an always-on
  background app.
- **Qt/C++ (desktop):** rejected for v1 — leanest possible memory use and zero web
  tech, but weaker mDNS story and more implementation work for the dynamic grid
  editor. Worth revisiting if Tauri's webview dependency causes platform-specific
  pain later.
- **React Native / Flutter (mobile):** rejected in favor of fully native Swift/
  Kotlin, per product preference for platform-native integration and performance.
- **Cloud relay for connectivity:** deferred rather than rejected — needed only if
  off-LAN support becomes a requirement; adds a relay/signaling server and NAT
  traversal complexity not justified for v1.

## Open Questions

- Exact set of v1 action types beyond a basic launch-app/run-script/media-key set.
- Whether `/protocol` should be formalized as JSON Schema files or stays markdown
  prose for now.
- Local storage format for desktop button config and per-device auth tokens (flat
  JSON file vs. embedded SQLite).

## Milestones

1. Repo scaffold (this doc, per-directory LICENSE files, empty Tauri/iOS/Android
   project shells, `/protocol` stub).
2. Desktop networking skeleton (mDNS advertisement + WebSocket echo server).
3. Desktop pairing flow (QR generation, token issuance/storage).
4. Desktop grid UI, static then dynamic (add/remove/reorder, persist config, wire to
   one action type).
5. Mobile discovery + pairing on one platform first (suggest iOS), then the second
   (Android) once the protocol is validated.
6. Mobile grid UI + button-press round trip.
7. Action plugin system hardening.
8. Packaging & distribution (Tauri bundler; App Store/Play Store submission).
