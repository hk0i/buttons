## Problem Statement

Physical macro-pad hardware (Elgato Stream Deck and similar) is expensive,
proprietary, and single-purpose. Most people already own a touchscreen-capable
smartphone that is more than capable of serving as the same kind of programmable
control surface — it's idle on a desk or in a pocket most of the day anyway. There
is no widely-used, open-source way to turn that phone into a Stream-Deck-style
controller for a nearby computer without manual network configuration.

## Goals

1. Let a user turn their existing smartphone into a programmable button-grid remote
   for their computer, with no dedicated hardware purchase required.
2. Make setup effectively zero-configuration: discover and pair over the local
   network without the user ever typing an IP address.
3. Keep the desktop component lightweight enough to run continuously in the
   background without being a resource concern.
4. Ship as open source (source-available, inspectable, self-buildable) and keep the
   app and every functional feature free forever — never gate functionality behind
   payment. Sustain the real costs of mobile distribution (Apple/Google developer
   fees) through optional in-app purchases only: tipping the developer, and cosmetic
   theme packs.

## Non-Goals (v1)

1. Remote/off-LAN control (phone on cellular, desktop on a different network).
2. A general home-automation platform — this is a computer control surface, not a
   smart-home hub, though individual buttons may trigger webhooks that reach one.
3. A hardware product.
4. A third-party plugin marketplace or ecosystem (the action engine should be
   designed to allow this later — see the EDD — but it is not user-facing in v1).
5. Any form of paywalled functionality, feature-gating, or subscription — see
   Monetization below.
6. USB tethering as a Wi-Fi/mDNS pairing fallback — considered (see Network
   Assumptions) but deferred past v1, primarily because iOS restricts arbitrary
   USB-IP tethering for third-party apps without MFi accessory certification, which
   would make it Android-only for a long time.

## Competitive Positioning

Elgato's Stream Deck is proprietary hardware with a subscription-gated mobile
companion app and a software suite that's historically weak on Linux and iPadOS.
This project's differentiation:

1. **No hardware purchase required** — uses a device the user already owns.
2. **Fully open source**, GPLv3 desktop / MIT mobile (see the EDD).
3. **Always free**, no subscription, no feature paywall.
4. **Cross-platform strength where Elgato is weak**: first-class Linux desktop
   support (via Tauri) and first-class iPadOS support (native SwiftUI runs on iPad
   by default) are explicit targets, not afterthoughts.

## Monetization

The app and every functional feature are free forever, on both desktop and mobile
— there is no premium tier and no feature-gating. Revenue, if any, comes entirely
from optional in-app purchases that don't affect functionality:

1. **Tipping** the developer.
2. **Cosmetic theme packs.** A default light theme and a default dark theme ship
   free with the app; additional color themes may be added later as optional paid
   cosmetic purchases.

## Target Users

1. **Streamers / content creators** who want Stream-Deck-style scene, recording, and
   media control without buying dedicated hardware.
2. **Developers / power users** who want quick-action buttons for launching apps,
   running scripts, or triggering local dev workflows from their phone.
3. **Open-source-first users** who want a transparent, self-hostable alternative to
   closed commercial tools, and are comfortable with a LAN-only v1.

## Use Cases

Researched against common Stream Deck usage (Elgato's own plugin marketplace,
streamer community sources — see links at the end of this doc) and the author's own
usage. Use cases are tiered by implementation cost, since each tier beyond the
first requires integrating against a separate third-party system:

### Tier 1 — MVP (no third-party integration; OS-level only)
1. Launch an application or run a local script.
2. Simulate a keyboard shortcut / hotkey, including multi-key macro strings and
   the F13–F24 range specifically — those keys exist mainly so software can bind to
   them without colliding with real keyboard input, since most physical keyboards
   don't have them.
3. Media key control (play/pause, mute, next/previous track).

This tier is the MVP slice: it validates the entire pipeline (grid UI → discovery →
pairing → button press → action → result) end-to-end using only OS APIs, before any
third-party integration work begins.

### Tier 2 — high-value integrations (single external protocol each)
1. OBS control: scene switching, start/stop recording, start/stop streaming, replay
   buffer trigger — via the obs-websocket v5 protocol. The author's own top use
   case; requires OBS running with its websocket server enabled.
2. Per-app volume mixer (fader-style control) — via platform audio APIs (Core Audio
   / WASAPI / PulseAudio). No external network integration, but platform-specific
   code per OS. Matches the author's Stream Deck+ dial usage.

### Tier 3 — deferred (heavier integration cost relative to value)
1. Stream metadata updates (Twitch/YouTube title + game/category) and chat mode
   toggles (sub-only/follower-only/emote-only) — requires the platform's API plus
   an OAuth flow (app registration, token refresh). Common among streamers but the
   highest integration overhead of any use case here.
2. Discord control (mute/deafen/push-to-talk) — matters mainly for co-hosted
   streams. Deferred indefinitely rather than scheduled — revisit if there's
   actual user demand, rather than building ahead of it.

### Tier 4 — long tail / generic escape hatch
1. Trigger a custom HTTP webhook (e.g. a smart-home action, a CI job, a home
   server command) — also serves as a generic extension point for use cases not
   explicitly built in.

## Button Model

Researched against how Elgato's own software actually organizes configuration
(Profiles, Folders, Multi-Actions — see Sources), adapted to a touchscreen surface
instead of fixed hardware. Core concepts that apply across desktop and mobile:

1. **Customizable appearance:** every button has a user-set icon and/or text label
   — not a fixed icon set. Icons may be animated (GIF-style), and a button's face
   may render live/dynamic text (e.g. CPU usage, a clock) in addition to a static
   label.
2. **Stateful buttons:** a button's icon/label can update dynamically to reflect
   live state rather than staying static — e.g. a mic-mute button showing
   muted/unmuted, a record button showing recording/idle. State changes that
   originate outside the app (e.g. recording stopped directly in OBS, not via this
   app) must still be reflected — the desktop pushes state updates to mobile
   independent of button presses, not just in response to them.
3. **Multi-actions:** a button holds an ordered array of zero or more actions,
   executed in sequence on press — not a single action slot. This is Elgato's most
   loved feature (e.g. one press starts the stream, switches scene, and unmutes the
   mic together); modeling it as an array from the start costs little and avoids a
   later data-model migration.
4. **Folders:** a button may act as a folder — tapping it navigates into a nested
   grid of its own buttons, with a way back to the parent. Folders may nest, and
   may optionally auto-return to the parent grid after a configurable idle timeout
   (off by default).
5. **Profiles, distinct from pages:** a **Profile** is a complete, independently
   switchable named configuration (its own buttons/folders/pages) — e.g. one
   Profile for OBS, another for video editing. Profiles can be switched manually
   from mobile, and the desktop can **auto-switch the active Profile based on which
   application has OS focus**, mirroring Elgato's "Smart Profiles." Unlike Elgato,
   our desktop app is always a background process rather than a foreground editor
   window, so auto-switching can stay live at all times — there's no "must minimize
   the app first" limitation to inherit. **Pages** remain the flat, swipeable,
   lateral complement *within* a Profile, distinct from both Folders (hierarchical)
   and Profiles (a different configuration entirely).
6. **Adaptive grid:** grid dimensions are user-configurable and scale fluidly by
   screen size (compact on phone, larger on tablet) rather than being locked to a
   fixed layout. Two independent controls: how many cells are visible on screen at
   once (density), and whether a given button can span multiple columns/rows
   (variable sizing) — e.g. a wide button for a fader-style control. Mobile clients
   target phones and tablets (iPad, Android tablets) as first-class form factors.
   Multi-cell spanning is well-supported by CSS Grid on desktop but may be
   significantly harder on native mobile grids (SwiftUI/Compose) — flagged as a
   technical investigation in the EDD, not assumed free.
7. **Shareable, open configs:** exported/imported Profiles are plain, human-
   readable files (not an opaque or proprietary format) so the community can share
   and customize each other's setups freely — matching the project's open-source
   ethos. This holds regardless of what wire format the live sync protocol uses
   (see the EDD) — export format and live wire format are independent decisions.
8. **Haptic feedback:** tapping a button on mobile gives tactile (vibration)
   feedback, mimicking the physical click of a hardware deck.

### Future Vision (beyond v1)

Explicitly out of v1 scope, but noted so the data model/protocol isn't designed in
a way that forecloses it later: control elements beyond simple tap-buttons, to
turn this into a virtual control surface for creative/pro tools — e.g. a jog wheel
or dial for scrubbing timelines in DaVinci Resolve or adjusting parameters in
Logic Pro, or brush-size/color-palette controls for Aseprite. Elgato's Stream
Deck+ hardware already validates the interaction shape worth borrowing: a dial
("Encoder") isn't one action but up to four independent triggers — rotate
clockwise, rotate counter-clockwise, press, and a touch-strip tap — each bindable
to its own action sequence. If/when this is built, a control element should be
modeled as a named set of trigger channels (of which a plain button is the
one-trigger case), not as a button-only hierarchy retrofitted later.

## Functional Requirements

### Desktop
1. Runs continuously in the background (tray/menu-bar app), not a foreground window
   the user must keep open.
2. Advertises itself on the local network so it can be discovered without a manual
   IP entry.
3. Provides a UI to create, edit, delete, and reorder buttons across Profiles,
   pages, and folders (see Button Model).
4. Each button holds an ordered array of zero or more actions (multi-action),
   each chosen from a defined set of action types (see Use Cases above for the v1
   set), or is a folder.
5. Supports a customizable icon (static or animated) and/or text label per button,
   including live/dynamic text where applicable.
6. Persists button configuration (including pages, folders, and appearance) across
   restarts.
7. Accepts a pairing request from a new mobile device via a one-time QR code /
   token exchange, and stores paired-device credentials for future reconnects.
8. Pushes button state updates (icon/label/live-value changes) to mobile
   independent of button presses, to keep stateful buttons in sync.
9. Ships a default light theme and a default dark theme; additional theme packs
   are a future paid cosmetic option (see Monetization).
10. Can redisplay its pairing QR code on demand, not just during first-time setup
    — this is the primary recovery path if mDNS discovery ever fails (see Network
    Assumptions).
11. Supports multiple Profiles (independently switchable full configurations) and
    can auto-switch the active Profile based on which application currently has OS
    focus.
12. Can export a Profile to, and import one from, a plain human-readable file for
    sharing (see Button Model).

### Mobile

1. Discovers nearby desktop instances on the same network without the user typing
   an IP address (see Network Assumptions below).
2. Pairs with a discovered desktop instance by scanning a QR code shown by the
   desktop app.
3. Reconnects automatically to a previously-paired desktop instance on app launch,
   without re-pairing.
4. Displays a grid mirroring the desktop's current button configuration, adapting
   layout to phone or tablet screen size, with folder navigation (in/back),
   swipe-between-pages, and manual Profile switching (see Button Model).
5. Sends a button-press event to the desktop when a button is tapped, triggers
   haptic feedback on tap, and reflects the resulting success/failure state back
   to the user.
6. Reflects live button state/appearance changes pushed from desktop without
   requiring a manual refresh.
7. If discovery/pairing fails, offers rescanning the desktop's QR code as the
   primary recovery path (works even if mDNS itself is broken, since the QR
   encodes the address directly), with manual IP entry as a secondary fallback for
   devices without a usable camera.

## Network Assumptions

The primary supported topology is a **wired desktop and a Wi-Fi mobile device on
the same router/subnet** — e.g. the computer plugged into Ethernet, the phone on
the household Wi-Fi. Discovery and pairing must work by default in this topology,
not just when both devices happen to be on Wi-Fi.

This is a known risk area, not a solved problem: some routers/access points apply
client isolation, VLAN segmentation, or IGMP snooping configurations that block
multicast traffic (which mDNS relies on) from crossing between the wired and
wireless segments, even though both devices are technically "on the same network."
v1 targets typical home/small-office router setups; it does not attempt to work
around enterprise-grade network segmentation. If mDNS discovery fails outright, the
QR code itself is the primary recovery path, not a text field: it already encodes
the desktop's address directly, so re-displaying and re-scanning it recovers a
connection without depending on multicast discovery at all. Manual IP entry is a
secondary fallback, only for mobile devices without a usable camera (e.g. some
tablets).

USB tethering (phone physically connected via cable) was considered as a stronger
fallback than manual IP entry, but is explicitly deferred past v1 — see Non-Goals.

## Success Metrics

Since this is an open-source project rather than a funded product, "success" is
framed accordingly:

1. Button-press round-trip latency on LAN feels as responsive as a physical key
   press (target: well under 50ms end-to-end on typical LAN conditions — lag
   becomes perceptible to users somewhere in the 100-200ms range, and the goal is
   to stay comfortably clear of that threshold, not just under it).
2. Desktop app's idle background resource usage stays low enough that a user has no
   reason to quit it (qualitative target set once the Tauri skeleton exists — see
   the EDD).
3. Pairing succeeds without the user ever needing to type an IP address or consult
   documentation, in first-run testing.
4. Tip and theme-pack revenue ideally covers the Apple Developer Program and Google
   Play registration fees on an ongoing basis — but this is not a requirement for
   the app to keep shipping, since it's never gated behind payment.
5. The app, and every functional feature in it, stays free forever (see
   Monetization).

## Decisions

1. **Device pairing scope (v1):** single mobile device paired per desktop instance.
   Multi-device support is deferred.
2. **Grid authority:** desktop-authoritative. Mobile is read/press-only — editing the
   grid from mobile would add setup complexity without serving the product's goal of
   controlling the desktop machine.
3. **Minimum OS versions:**
   1. **iOS/macOS:** Apple requires apps to be *built* with the iOS 26 / Xcode 26 SDK
      as of April 28, 2026, but this does not force a minimum deployment target — that
      stays a developer choice. Recommend targeting the last ~2 major OS versions
      (iOS/macOS 17+) for broad reach without excess legacy-support burden; revisit
      once mobile development actually starts.
   2. **Android:** not expected to be a significant constraint given Android's app
      compatibility layer; pick a reasonable minimum API level once Android
      development starts rather than fixing it now.
   3. **Windows:** 11 minimum (Microsoft ended Windows 10 support in October 2025).
   4. **Linux:** no fixed minimum; support whatever the Tauri toolchain and Rust mDNS/
      audio crates support.
4. **MVP slice:** Tier 1 use cases (generic system actions: launch app, run script,
   hotkey, media key) — see Use Cases above for the full tiering and rationale.
